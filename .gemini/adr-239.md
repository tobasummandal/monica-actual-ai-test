# Adopt Domain-Driven Test Organization with Mirrored Directory Structure: Test Directory Root

## Policies

1. The test directory root MUST be located at tests/Unit/ for unit tests, with integration and functional tests in separate parallel hierarchies

## Status

Proposed

## Context

Test organization significantly impacts maintainability, discoverability, and alignment with domain boundaries. A mirrored directory structure that reflects the source code organization while maintaining clear separation of test types enables teams to locate and manage tests efficiently.

## Decision

Adopt a domain-driven test organization strategy with mirrored directory structures across separate test type hierarchies:

- **Unit tests**: `tests/Unit/`
- **Integration tests**: `tests/Integration/`
- **Functional tests**: `tests/Functional/`

Each hierarchy mirrors the domain structure of the source code, allowing tests to be organized by the domain concepts they validate rather than by test infrastructure or framework concerns.

## Consequences

### Positive

- Tests are co-located with the domains they validate, improving discoverability
- Clear separation of test types prevents mixing concerns and enables targeted test execution
- Mirrored structure makes it intuitive to locate tests for a given source module
- Supports scaling as domains grow and new test types are introduced

### Negative

- Requires discipline to maintain mirror structure as code evolves
- May result in deeper directory hierarchies in large systems
- Initial setup overhead to establish and document the convention

## Alternatives Considered

1. **Flat test directory**: All tests in a single directory—loses domain context and becomes unwieldy at scale
2. **Test-type-first organization**: `tests/unit/`, `tests/integration/` without domain mirroring—loses alignment with source structure
3. **Co-located tests**: Tests alongside source code—mixes concerns and complicates deployment

## Implementation Notes

- Establish a naming convention for test files (e.g., `*Test.php`, `*Spec.js`)
- Document the structure in the project's testing guide
- Use CI/CD configuration to run test types independently
- Consider tooling to validate structure compliance
