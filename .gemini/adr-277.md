# Adopt Domain-Driven Service Layer Pattern for Journal Management: Web Controllers Managejournals

## Status
Proposed

## Context
The ManageJournals module requires a clear separation of concerns between HTTP request handling and business logic. Web controllers currently risk implementing domain logic directly, leading to code duplication, reduced testability, and tight coupling between presentation and domain layers.

## Decision
Adopt a domain-driven service layer pattern where web controllers in ManageJournals/Web/Controllers delegate all business logic to dedicated service classes. Controllers remain responsible only for HTTP concerns (routing, request/response mapping, status codes), while services encapsulate domain operations, validation, and orchestration.

## Rationale
- **Separation of Concerns**: Controllers handle HTTP semantics; services handle business rules
- **Testability**: Service logic can be tested independently of HTTP frameworks
- **Reusability**: Services can be consumed by multiple controllers, APIs, or background jobs
- **Maintainability**: Domain logic is centralized and easier to locate and modify
- **Domain-Driven Design**: Aligns with DDD principles by making domain operations explicit

## Policies

1. Web controllers in the ManageJournals/Web/Controllers directory MUST delegate business logic to service classes rather than implementing logic directly

## Consequences
- Controllers become thin, focused, and easier to review
- Service layer becomes the primary location for domain logic and business rules
- Requires consistent naming and organization of service classes
- May introduce additional abstraction layers that need careful design
