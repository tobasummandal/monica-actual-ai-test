# Adopt Domain-Driven Module Boundaries with External API Integration Layers: Each External Integration

## Status
Proposed

## Context
As the system grows and integrates with multiple external APIs (e.g., DAV, payment processors, notification services), the codebase risks becoming tightly coupled to protocol-specific implementation details. Without clear boundaries, domain logic becomes intertwined with HTTP clients, authentication mechanisms, and API-specific error handling, making the system difficult to test, maintain, and evolve.

## Decision
We adopt domain-driven module boundaries with dedicated external API integration layers. Each external integration MUST provide a dedicated client service layer that encapsulates all protocol-specific communication logic, allowing domain modules to depend on stable, domain-oriented abstractions rather than external API details.

## Policies

1. Each external API integration MUST provide a dedicated client service layer (e.g., DavClient/Services) that encapsulates all protocol-specific communication logic

## Consequences

### Positive
- Domain modules remain independent of external API implementation details
- Integration layers can be tested, mocked, and replaced independently
- Protocol changes (HTTP → gRPC, API version upgrades) are isolated to integration layers
- Clear separation of concerns improves code maintainability and readability
- Enables parallel development of domain logic and external integrations

### Negative
- Additional abstraction layer introduces slight performance overhead
- Requires discipline to maintain boundaries across the codebase
- More files and modules to manage and document

## Implementation Notes
- Each integration layer should expose domain-oriented interfaces, not API-specific contracts
- Use dependency injection to provide integration layers to domain services
- Document the contract between domain modules and integration layers
