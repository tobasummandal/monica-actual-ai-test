# Adopt Domain-Driven DAV/CardDAV Integration Pattern for External Contact Synchronization: Data Transfer Between

## Status
Proposed

## Context
External contact synchronization via DAV/CardDAV protocols requires clear boundaries between external system representations and internal domain models. Without explicit data transfer patterns, domain logic risks contamination from protocol-specific concerns and external schema variations.

## Decision
Adopt a domain-driven integration pattern using dedicated Data Transfer Objects (DTOs) for all DAV/CardDAV data exchange. External contact data MUST be transformed into domain-specific DTOs before crossing the integration boundary.

## Policies

1. Data transfer between external DAV systems and internal domains MUST use dedicated DTO objects (ContactDto, ContactDeleteDto) to enforce boundary isolation

## Rationale
- **Boundary Protection**: DTOs create an explicit contract between external systems and domain logic
- **Schema Independence**: Domain models remain decoupled from DAV/CardDAV protocol variations
- **Testability**: DTO transformation logic can be tested independently of protocol handlers
- **Maintainability**: Changes to external schemas require only DTO mapping updates, not domain model changes

## Consequences

### Positive
- Clear separation of concerns between protocol handling and business logic
- Reduced coupling to external system schemas
- Easier to add new synchronization sources
- Simplified unit testing of domain operations

### Negative
- Additional mapping layer introduces slight performance overhead
- Requires maintenance of DTO definitions alongside domain models
- Team must understand DTO transformation patterns

## Implementation Notes
- Create `ContactDto` for standard contact data transfer
- Create `ContactDeleteDto` for deletion operations
- Implement dedicated mapper service for DTO ↔ Domain conversions
- Validate DTO data before domain model instantiation
