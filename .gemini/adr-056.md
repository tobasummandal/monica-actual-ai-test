# Adopt Domain-Driven Module Boundaries with External API Integration Layers: Core Domain Entities

## Status
Proposed

## Context
As our system grows in complexity, core domain logic becomes increasingly entangled with external API clients, HTTP libraries, and protocol-specific implementations. This coupling makes domain logic difficult to test, reason about, and evolve independently of infrastructure concerns.

## Decision
We adopt domain-driven module boundaries that strictly separate core domain entities and business logic from external API integration layers. Core domain modules will define contracts (interfaces/ports) that integration layers implement, following the Dependency Inversion Principle.

## Policies

1. Core domain entities and business logic MUST NOT directly depend on external protocol implementation classes or libraries

## Rationale
- **Testability**: Domain logic can be tested without external dependencies or mocks of HTTP clients
- **Maintainability**: Changes to external APIs do not ripple into core business logic
- **Clarity**: Domain boundaries are explicit and enforced at the module level
- **Reusability**: Domain logic can be integrated via multiple protocols or transports

## Implementation Guidelines

### Module Structure
```
src/
├── domain/
│   ├── entities/
│   ├── value-objects/
│   ├── services/
│   └── ports/  (interfaces only)
├── application/
│   └── use-cases/
└── infrastructure/
    ├── adapters/  (API clients, HTTP implementations)
    └── repositories/
```

### Port Definition
Domain modules define ports as interfaces representing external dependencies:
```typescript
// domain/ports/user-repository.ts
export interface UserRepository {
  findById(id: string): Promise<User>;
  save(user: User): Promise<void>;
}
```

### Adapter Implementation
Infrastructure adapters implement ports using external libraries:
```typescript
// infrastructure/adapters/http-user-repository.ts
import axios from 'axios';
import { UserRepository } from '../../domain/ports/user-repository';

export class HttpUserRepository implements UserRepository {
  // Implementation using axios
}
```

## Consequences

### Positive
- Domain logic remains independent and testable
- Clear separation of concerns
- Easier to swap implementations (e.g., REST → gRPC)
- Reduced cognitive load when reasoning about business rules

### Negative
- Additional abstraction layers increase initial development time
- More interfaces to maintain
- Requires discipline to prevent violations
