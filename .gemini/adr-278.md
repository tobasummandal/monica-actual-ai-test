# Adopt Domain-Driven Service Layer Pattern for Journal Management: Service Classes Follow

## Status
Accepted

## Context
Journal management requires clear separation of concerns and maintainable service layer architecture. Service classes need explicit responsibility boundaries to ensure testability, reusability, and domain clarity.

## Decision
Adopt a domain-driven service layer pattern where each service class encapsulates a single primary operation aligned with domain concepts.

## Policies

1. Service classes MUST follow single-responsibility principle with one primary operation per class (e.g., CreatePostMetric, DestroySliceOfLife, UpdateJournalMetric)

## Consequences

**Positive:**
- Clear, predictable service class naming and structure
- Easier to test individual operations in isolation
- Reduced cognitive load when understanding service responsibilities
- Improved code reusability across different contexts
- Better alignment with domain language

**Negative:**
- Potential increase in number of service classes
- May require careful orchestration when operations depend on each other
- Requires discipline to maintain single-responsibility boundaries

## Implementation Notes
- Each service class should have a descriptive name reflecting its domain operation
- Constructor injection for dependencies (repositories, validators, event publishers)
- Public execute() or __invoke() method as primary interface
- Consider factory or builder patterns for complex service composition
