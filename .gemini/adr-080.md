# Adopt Domain-Driven DAV/CardDAV Integration Pattern for External Contact Synchronization: Domain Services Implement

## Status

Accepted

## Context

External contact synchronization requires integration with DAV/CardDAV protocols. A domain-driven approach ensures that domain logic remains decoupled from protocol-specific implementation details, improving maintainability and testability.

## Decision

We adopt a domain-driven DAV/CardDAV integration pattern where domain services implement contact synchronization logic independently of transport and protocol concerns. Domain services will orchestrate VCard transformations, validation, and contact lifecycle management while delegating protocol-specific operations to dedicated infrastructure adapters.

## Rationale

- **Separation of Concerns**: Domain services focus on business rules; infrastructure adapters handle DAV/CardDAV protocol specifics
- **Testability**: Domain logic can be tested without requiring live DAV/CardDAV servers
- **Maintainability**: Changes to RFC 6350 compliance or business rules remain isolated within domain services
- **Reusability**: Domain services can support multiple synchronization backends through different adapters
- **Clarity**: Domain model explicitly represents contact synchronization concepts

## Policies

1. Domain services MAY implement additional validation layers for VCard data to ensure compliance with RFC 6350 specifications

## Consequences

**Positive:**
- Domain logic remains protocol-agnostic and highly testable
- Clear separation between business rules and infrastructure concerns
- Easier to add support for additional DAV variants or contact formats

**Negative:**
- Additional abstraction layer may introduce slight performance overhead
- Requires careful design of adapter interfaces to prevent domain leakage

## Implementation Notes

- Domain services should define clear contracts for VCard input/output
- Infrastructure adapters translate between domain models and DAV/CardDAV wire formats
- Validation logic should be co-located with domain services, not in adapters
