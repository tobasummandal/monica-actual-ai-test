# Adopt Domain-Driven DAV/CardDAV Integration Pattern for External Contact Synchronization: Viewhelper Classes Used

## Status

Accepted

## Context

When integrating external contact synchronization via DAV/CardDAV protocols, domain models must be transformed for presentation to clients and UI layers. Direct exposure of domain entities risks leaking internal implementation details, violating domain-driven design principles and creating tight coupling between domain and presentation concerns.

## Decision

We will adopt a ViewHelper class pattern to mediate between domain models and presentation layers during DAV/CardDAV contact synchronization operations.

ViewHelper classes will:
- Transform domain Contact and SyncState entities into presentation-safe data structures
- Encapsulate formatting, filtering, and serialization logic required by DAV/CardDAV clients
- Remain stateless and focused solely on data transformation
- Never contain business logic or domain rules

## Policies

1. ViewHelper classes SHOULD be used to prepare domain data for presentation layers without exposing internal domain logic

## Consequences

**Positive:**
- Domain models remain pure and focused on business rules
- Presentation concerns are cleanly separated from domain logic
- Changes to UI/API contracts do not ripple into domain layer
- ViewHelpers are easily testable and reusable across multiple presentation contexts

**Negative:**
- Additional layer introduces minor performance overhead in data transformation
- Developers must maintain discipline to keep ViewHelpers free of business logic
- Requires clear naming conventions to distinguish ViewHelpers from other utility classes

## Implementation Notes

- ViewHelper classes should be co-located with their corresponding presentation endpoints
- Use composition over inheritance for ViewHelper design
- Document expected input domain types and output presentation formats
- Consider using builder patterns for complex transformations
