# Adopt Inertia.js for Server-Driven Single Page Application Rendering: Controllers Return Inertia

## Status
Accepted

## Context
Our application requires a modern approach to server-driven single page application rendering that bridges server-side logic with client-side interactivity. We need a solution that allows controllers to seamlessly return reactive components without building separate API endpoints.

## Decision
We adopt Inertia.js as our server-driven SPA rendering framework. Controllers will return Inertia responses, enabling server-side routing and data handling while maintaining a reactive frontend experience.

## Policies

1. Controllers MUST return Inertia responses using the Inertia::render() method with a component name and props array

## Consequences

### Positive
- Eliminates the need for separate API layer for page rendering
- Server maintains control over routing and authorization
- Props passed from controller to component are type-safe and auditable
- Reduces complexity of state management on the frontend
- Enables progressive enhancement and server-side validation

### Negative
- Requires learning Inertia.js conventions and patterns
- Tightly couples server framework with frontend component structure
- May require refactoring existing API-driven architectures
- Additional dependency management for Inertia adapters

## Alternatives Considered
- Traditional server-side rendering with template engines
- Fully decoupled REST/GraphQL API with separate SPA
- Next.js or similar full-stack frameworks
