# Organize Domain Logic Using Domain-Driven Design Bounded Contexts: Each Domain Separate

## Status
Accepted

## Context
As applications grow in complexity, organizing code by technical layers (controllers, services, models) across the entire codebase leads to tight coupling, unclear domain boundaries, and difficulty in understanding business logic. Domain-Driven Design (DDD) provides a structured approach to organize code around business domains, making each domain's logic self-contained and independently maintainable.

## Decision
We will organize domain logic using Domain-Driven Design bounded contexts, where each domain is separated into its own directory structure with clear separation of concerns.

## Policies

1. Each domain MUST separate concerns into distinct subdirectories: Services for business logic, Web/Controllers for HTTP handling, and Models for data structures

## Rationale
- **Clear Boundaries**: Bounded contexts create explicit boundaries around related business logic, reducing cognitive load and preventing unintended coupling
- **Scalability**: Teams can work independently on different domains without constant coordination
- **Maintainability**: Business logic is co-located with its related models and controllers, making changes easier to reason about
- **Testability**: Domain-isolated code is simpler to unit test in isolation
- **Ubiquitous Language**: Each domain can develop and maintain its own vocabulary and models aligned with business terminology

## Implementation Guidelines

### Directory Structure
```
src/
├── domains/
│   ├── users/
│   │   ├── models/
│   │   ├── services/
│   │   └── web/
│   ├── orders/
│   │   ├── models/
│   │   ├── services/
│   │   └── web/
│   └── payments/
│       ├── models/
│       ├── services/
│       └── web/
└── shared/
    └── infrastructure/
```

### Domain Components
- **Models**: Data structures and entities specific to the domain
- **Services**: Business logic, use cases, and domain operations
- **Web/Controllers**: HTTP endpoints and request/response handling

## Consequences

### Positive
- Improved code organization and discoverability
- Reduced coupling between domains
- Easier to scale teams and assign ownership
- Better alignment with business structure

### Negative
- Requires discipline to maintain boundaries
- May introduce duplication if shared logic is not properly abstracted
- Initial setup complexity for small projects
