# Standardize Eloquent Models as Primary Data Access Layer with Public API Contracts: Business Logic Not

## Status
Proposed

## Context
Laravel applications require a consistent approach to data access patterns. Without standardization, business logic may bypass Eloquent models and access the database directly through raw queries, leading to maintainability issues, reduced testability, and inconsistent data handling across the codebase.

## Decision
Eloquent models SHALL be the primary data access layer for all business logic. Public API contracts on models define the interface for data operations. Direct database access via raw queries is prohibited except for documented, performance-critical operations.

## Policies

1. Business logic MUST NOT bypass models to access database directly via raw queries except for performance-critical operations with documented justification

## Consequences

**Positive:**
- Consistent data access patterns across the application
- Improved testability through model mocking
- Enhanced maintainability and code clarity
- Centralized business logic enforcement
- Better query optimization opportunities

**Negative:**
- Performance overhead in some scenarios (mitigated by documented exceptions)
- Learning curve for developers unfamiliar with Eloquent patterns
- Potential constraints on complex query scenarios

## Exceptions
Performance-critical operations requiring raw queries must:
- Include inline documentation explaining the justification
- Be reviewed and approved during code review
- Include performance benchmarks or metrics
- Be isolated in dedicated query methods with clear naming conventions
