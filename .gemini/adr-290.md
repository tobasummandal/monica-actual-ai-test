# Adopt PHPUnit for Unit Testing in Domain-Driven Architecture: Each Service Class

## Status
Accepted

## Context
In a domain-driven architecture, service classes encapsulate business logic and domain operations. Without comprehensive unit testing, these critical components are vulnerable to regressions, making it difficult to maintain code quality and ensure reliable behavior across refactoring and feature additions.

## Decision
We adopt PHPUnit as the standard unit testing framework for all service classes, controllers, and view helpers in our domain-driven architecture.

## Rationale
- PHPUnit is the de facto standard testing framework for PHP, with mature tooling and broad ecosystem support
- Unit tests at the service layer provide fast feedback on business logic correctness
- Comprehensive test coverage reduces defect escape rates and supports safe refactoring
- Consistent testing practices across all service classes improve maintainability and onboarding

## Policies

1. Each service class, controller, and view helper SHOULD have a corresponding unit test file

## Consequences

### Positive
- Increased confidence in service layer behavior and business logic correctness
- Faster feedback loops during development and continuous integration
- Reduced defect rates in production
- Improved code maintainability through regression prevention

### Negative
- Initial time investment in writing and maintaining test suites
- Ongoing effort required to keep tests synchronized with code changes
- Potential for brittle tests if not designed with care

## Implementation Notes
- Test files should follow the naming convention `{ClassName}Test.php`
- Tests should be organized in a `tests/` directory mirroring the source structure
- Use PHPUnit's assertion methods and mocking capabilities to isolate units under test
- Aim for meaningful test coverage focused on business logic rather than 100% line coverage
