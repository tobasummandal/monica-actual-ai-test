# Standardize Logging with Laravel Log Facade in DAV and Job Components: Background Jobs Handling

## Status
Proposed

## Context
The DAV (Distributed Authoring and Versioning) and Job components handle critical operations on VCard and VCalendar resources through background jobs. Currently, logging practices are inconsistent across these components, making it difficult to trace job execution, diagnose failures, and audit resource modifications. A standardized logging approach using Laravel's Log Facade will improve observability and maintainability.

## Decision
We will standardize logging across DAV and Job components using Laravel's Log Facade, with mandatory logging of job lifecycle events (start, completion, failure) and contextual data including resource identifiers.

## Policies

1. Background jobs handling VCard/VCalendar operations MUST log job start, completion, and failure events with contextual data including resource identifiers

## Rationale
- **Consistency**: Unified logging approach across all background job handlers
- **Traceability**: Resource identifiers enable tracking of specific VCard/VCalendar operations
- **Debuggability**: Comprehensive job lifecycle logging facilitates rapid issue diagnosis
- **Auditability**: Complete event logs support compliance and operational reviews
- **Laravel Native**: Leverages built-in Log Facade, reducing external dependencies

## Implementation Guidelines

### Job Start Logging
```php
Log::info('Background job started', [
    'job_id' => $this->job->getJobId(),
    'job_class' => get_class($this),
    'resource_id' => $resourceId,
    'resource_type' => 'vcard|vcalendar',
]);
```

### Job Completion Logging
```php
Log::info('Background job completed', [
    'job_id' => $this->job->getJobId(),
    'job_class' => get_class($this),
    'resource_id' => $resourceId,
    'duration_ms' => $duration,
]);
```

### Job Failure Logging
```php
Log::error('Background job failed', [
    'job_id' => $this->job->getJobId(),
    'job_class' => get_class($this),
    'resource_id' => $resourceId,
    'error' => $exception->getMessage(),
    'attempts' => $this->attempts(),
]);
```

## Consequences
- **Positive**: Enhanced observability, easier debugging, audit trail for compliance
- **Negative**: Slight performance overhead from logging I/O; requires log storage management
- **Neutral**: Developers must follow logging conventions consistently

## Alternatives Considered
- Custom logging service: Rejected in favor of Laravel's native Log Facade
- No standardization: Rejected due to operational visibility requirements
