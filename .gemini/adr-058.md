# Adopt Domain-Driven Module Boundaries with External API Integration Layers: Resource Handler Classes

## Status
Proposed

## Context
External API integrations and data import/export operations require clear architectural boundaries to maintain domain integrity and system maintainability. Resource handler classes provide a dedicated pattern for managing these cross-boundary concerns without polluting core domain logic.

## Decision
We will adopt resource handler classes as the primary pattern for managing external data import/export operations. These classes serve as integration layers that translate between external API contracts and internal domain models, maintaining clear separation of concerns.

## Policies

1. Resource handler classes (e.g., ImportResource, ImportVCardResource) SHOULD be used to manage external data import/export operations with clear single responsibilities

## Rationale
- **Single Responsibility**: Each resource handler focuses exclusively on one import/export operation type
- **Domain Protection**: External API contracts remain isolated from core domain logic
- **Testability**: Integration concerns can be tested independently from business logic
- **Maintainability**: Changes to external APIs require modifications only in handler classes
- **Reusability**: Handlers can be composed and reused across different contexts

## Consequences

### Positive
- Clear architectural boundaries between domain and integration layers
- Reduced coupling between external systems and core business logic
- Easier to add new import/export operations without affecting existing code
- Simplified testing of integration logic

### Negative
- Additional abstraction layer may introduce slight performance overhead
- Requires discipline to prevent handlers from accumulating business logic
- Team must maintain consistency across multiple handler implementations

## Implementation Guidelines

- Each resource handler should have a single, well-defined responsibility
- Handlers should translate external data formats to domain models
- Error handling and validation should occur at the handler level
- Handlers should not contain business logic; they coordinate between external systems and domain services
- Consider using factory patterns for handler instantiation
