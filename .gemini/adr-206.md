# Adopt Eloquent ORM Models as Standard Data Access Layer: Each Model Correspond

## Status
Proposed

## Context
Our application requires a consistent, maintainable approach to data access across all layers. Multiple data access patterns have created inconsistency and increased cognitive load for developers.

## Decision
We adopt Laravel Eloquent ORM Models as the standard data access layer. Each Model will correspond to a single database table with explicit or conventional table name mapping.

## Policies

1. Each model MUST correspond to a single database table with explicit or conventional table name mapping

## Rationale
- Eloquent provides a unified, expressive query interface
- One-to-one model-to-table mapping ensures clarity and reduces confusion
- Explicit table name mapping allows flexibility while maintaining convention
- Standardization improves code maintainability and team velocity

## Consequences
- All data access must route through Eloquent Models
- Developers must follow Laravel conventions or explicitly define table mappings
- Raw SQL queries should be avoided in favor of Eloquent methods
- Model relationships become the primary mechanism for data associations

## Alternatives Considered
- Query Builder only (less abstraction, more boilerplate)
- Repository pattern wrapper (additional abstraction layer)
- Mixed approach (rejected due to inconsistency)
