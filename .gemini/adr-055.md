# Adopt Domain-Driven Module Boundaries with External API Integration Layers: Integration Modules Include

## Status
Accepted

## Context
As the system grows with multiple external API integrations, we need clear architectural boundaries that separate domain logic from integration concerns. Integration modules must handle protocol-specific operations, data transformations, and API communication while maintaining clean separation from core domain logic.

## Decision
We adopt domain-driven module boundaries with dedicated external API integration layers. Integration modules are permitted to include utility classes for protocol-specific operations when such operations are necessary for complex data transformations and API interactions.

## Policies

1. Integration modules MAY include utility classes for protocol-specific operations (e.g., Services/Utils/Dav) when needed for complex transformations

## Rationale
- Encapsulates protocol-specific complexity within integration boundaries
- Prevents domain logic contamination with API-specific concerns
- Allows reusable utility functions for common transformation patterns
- Maintains clear separation of concerns while enabling practical implementation

## Consequences

### Positive
- Domain modules remain free of external API dependencies
- Integration logic is centralized and easier to maintain
- Protocol-specific utilities are discoverable and reusable
- Clear module boundaries facilitate testing and evolution

### Negative
- Integration modules may grow in complexity
- Requires discipline to prevent utility classes from becoming dumping grounds
- Additional abstraction layer adds some overhead

## Implementation Guidelines

- Utility classes should be cohesive and focused on a single protocol or transformation concern
- Utilities must not contain business logic; they handle only technical transformations
- Integration modules should have clear, documented boundaries
- Regular review of utility classes to prevent scope creep
