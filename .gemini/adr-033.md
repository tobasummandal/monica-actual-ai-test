# Adopt Mock-Based Unit Testing for External Service Dependencies in CI/CD Pipeline: Unit Tests Services

## Status
Proposed

## Context
Unit tests that depend on real external services create brittle, slow, and unreliable test suites. Network calls introduce flakiness, increase test execution time, and create coupling between the test environment and external systems. This undermines the purpose of unit testing and complicates CI/CD pipeline reliability.

## Decision
We adopt mock-based unit testing for all service dependencies that interact with external APIs or network resources. Unit tests MUST use mocks, stubs, or fakes instead of real connections.

## Policies

1. Unit tests for services that interact with external APIs or network resources MUST use mocks, stubs, or fakes instead of real connections

## Rationale
- **Isolation**: Tests remain independent of external system availability and state
- **Speed**: Mocked responses eliminate network latency
- **Reliability**: Tests produce consistent, deterministic results
- **Cost**: Reduces unnecessary API calls and associated costs
- **CI/CD Stability**: Pipeline execution is not blocked by external service outages

## Consequences
- Developers must maintain mock implementations alongside service integrations
- Integration tests (separate from unit tests) should verify real service interactions
- Mock behavior must be kept synchronized with actual API contracts
- Requires discipline to ensure mocks accurately reflect external service behavior

## Implementation Guidelines
- Use established mocking libraries appropriate to the technology stack
- Document mock behavior and assumptions
- Maintain separate integration test suites for real service validation
- Review mocks during code review to ensure accuracy
