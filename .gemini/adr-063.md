# Adopt Domain-Driven Module Boundaries with External API Integration Layers: External Integrations Organized

## Status
Proposed

## Context
As the application grows, external API integrations are scattered across the codebase, making it difficult to maintain, test, and reason about dependencies. Without clear organizational boundaries, integrations become tightly coupled to business logic, hindering modularity and domain isolation.

## Decision
We adopt domain-driven module boundaries for external API integrations, organizing them within domain-specific modules using a consistent integration layer pattern.

## Policies

1. External API integrations MUST be organized within domain-specific modules following the pattern: app/Domains/{DomainName}/{IntegrationName}/

## Rationale
- **Domain Cohesion**: Integrations stay close to the domain logic they serve, improving discoverability and maintainability.
- **Clear Boundaries**: Explicit module structure prevents integration logic from leaking into business logic.
- **Testability**: Isolated integration layers can be mocked and tested independently.
- **Scalability**: New integrations follow a predictable structure, reducing onboarding friction.
- **Dependency Management**: Domain modules own their external dependencies, clarifying responsibility.

## Consequences

### Positive
- Improved code organization and navigation
- Easier to identify and manage external dependencies per domain
- Simplified testing through clear integration boundaries
- Reduced coupling between domains

### Negative
- Requires refactoring of existing scattered integrations
- May result in some code duplication if integrations serve multiple domains
- Team must maintain discipline in following the pattern

## Implementation

### Directory Structure Example
```
app/Domains/
├── Payment/
│   ├── StripeIntegration/
│   │   ├── StripeClient.ts
│   │   ├── StripeWebhookHandler.ts
│   │   └── index.ts
│   └── PaymentService.ts
├── Notification/
│   ├── SendgridIntegration/
│   │   ├── SendgridClient.ts
│   │   └── index.ts
│   └── NotificationService.ts
```

### Guidelines
- Each integration lives in its own subdirectory within the domain module
- Integration modules export a clean public API through `index.ts`
- Configuration and credentials are injected, not hardcoded
- Integration logic does not directly modify domain entities; it returns data for the domain service to process
