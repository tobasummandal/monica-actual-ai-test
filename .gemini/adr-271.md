# Adopt Domain-Driven Controller Organization for Journal Management: Each Distinct Entity

## Status
Proposed

## Context
Journal management encompasses multiple distinct domains: journals themselves, individual posts, photo collections, metrics and analytics, and slices of life narratives. A monolithic or poorly organized controller structure creates tight coupling, reduces testability, and makes it difficult to reason about domain boundaries.

## Decision
We will organize controllers using domain-driven design principles, with each distinct entity or concern within journal management receiving a dedicated controller class.

## Policies

1. Each distinct entity or concern within journal management (journals, posts, photos, metrics, slices of life) MUST have a dedicated controller class

## Consequences

### Positive
- Clear separation of concerns aligned with domain boundaries
- Improved testability through isolated controller responsibilities
- Easier to locate and modify functionality for specific entities
- Reduced cognitive load when reasoning about the codebase
- Facilitates independent scaling and deployment of domain services

### Negative
- Increased number of controller classes to maintain
- Potential for code duplication if cross-cutting concerns are not properly abstracted
- Requires discipline to maintain domain boundaries over time

## Implementation Notes
- Use base controller classes or mixins for shared HTTP handling patterns
- Establish clear naming conventions (e.g., `JournalsController`, `PostsController`, `PhotosController`)
- Document domain boundaries in architecture decision records
- Consider API versioning strategy per domain if evolution rates differ
