# Adopt Inertia.js with SSR for Frontend-Backend Integration: Middleware Handling Stateful

## Status
Proposed

## Context
When integrating Inertia.js with server-side rendering (SSR) in a full-stack application, middleware must handle stateful requests consistently. Inertia provides a HandleInertiaRequests middleware that manages the request/response lifecycle, but custom middleware for authentication, authorization, and state management must coordinate with it to avoid conflicts and maintain predictable behavior.

## Decision
We adopt Inertia.js with SSR and establish that all middleware handling stateful requests MUST extend or integrate with Inertia's HandleInertiaRequests middleware to maintain consistent request/response patterns.

## Policies

1. Middleware handling stateful requests SHOULD extend or integrate with Inertia's HandleInertiaRequests middleware to maintain consistent request/response patterns

## Rationale
- Ensures a single source of truth for request/response handling across the application
- Prevents middleware conflicts that could corrupt Inertia props or component state
- Simplifies debugging and tracing of state mutations through the middleware stack
- Enables SSR to reliably serialize and hydrate application state

## Consequences
- All custom middleware must be aware of Inertia's lifecycle and conventions
- Developers must understand Inertia's middleware architecture before adding custom logic
- Potential performance overhead if middleware is not optimized for SSR contexts
- Easier to maintain consistent behavior across Inertia and non-Inertia routes

## Alternatives Considered
- Separate middleware stacks for Inertia and non-Inertia routes (rejected: increases complexity)
- Wrapping Inertia middleware instead of extending it (rejected: less flexible)
