# Adopt Domain-Driven Resource Modeling for Data Access Layer: Resource Classes External

## Status
Proposed

## Context
The data access layer requires clear separation between core domain models and external protocol representations. Resource classes that handle external formats (VCard, VCalendar, etc.) introduce protocol-specific concerns that can pollute domain logic and complicate maintenance.

## Decision
Adopt domain-driven resource modeling that strictly separates external protocol integration resource classes from core domain models. External resource classes serve as adapters and translators between domain entities and external protocol formats.

## Policies

1. Resource classes for external protocol integration (e.g., VCard, VCalendar) MUST be separated from core domain models

## Rationale
- Maintains domain model purity by isolating protocol-specific concerns
- Enables independent evolution of domain logic and external integrations
- Simplifies testing by allowing protocol adapters to be tested separately
- Reduces coupling between domain and external dependencies
- Facilitates addition of new external protocols without domain model changes

## Consequences
- Requires additional adapter/translator classes
- Clear separation improves maintainability and testability
- Domain models remain focused on business logic
- External protocol changes are isolated to resource classes
