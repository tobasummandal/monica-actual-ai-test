<rule_activation id="483f72cf-e356-4c53-9e93-b5a072a73c3b" title="Adopt Domain-Driven Service Layer Architecture for Business Operations: Domain Services Reused" applies_to="app/Domains/**/*">
These rules are ALWAYS ACTIVE for all files under `app/Domains/`.

This architecture separates business logic into domain-specific service classes, with web controllers delegating to these services. Business operations are organized by domain and feature within a structured directory hierarchy.
</rule_activation>

### Rules

- **R-DDS-001** MAY: Domain services MAY be reused across multiple controllers or other services when appropriate.

- **R-DDS-002** MUST: Service classes MUST be placed in `app/Domains/{Domain}/{Feature}/Services/` directories.

- **R-DDS-003** MUST: Controllers MUST be placed in `app/Domains/{Domain}/{Feature}/Web/Controllers/` directories.

- **R-DDS-004** MUST: Business logic MUST be implemented in service classes, not in controllers. Controllers should only handle request validation, service invocation, and response formatting.

- **R-DDS-005** SHOULD: Use dependency injection to provide services to controllers, avoiding direct instantiation.

- **R-DDS-006** SHOULD: Name service classes after the business operation they perform (e.g., CreateAccount, AcceptInvitation, CancelAccount).

- **R-DDS-007** SHOULD: Keep controllers thin by limiting them to request validation, service invocation, and response formatting.

### Verify

```bash
# Verify service classes exist in correct domain structure
find app/Domains -type f -name '*.php' -path '*/Services/*' | wc -l

# Verify service namespaces follow domain pattern
grep -r 'namespace.*Domains.*Services' app/Domains --include='*.php' | wc -l

# Verify controllers exist in correct domain structure
find app/Domains -type f -name '*Controller.php' -path '*/Web/Controllers/*' | wc -l
```

**Accept when:**
- Service classes exist in `app/Domains/{Domain}/{Feature}/Services/` directories
- Controllers exist in `app/Domains/{Domain}/{Feature}/Web/Controllers/` directories
- At least 3 domain service classes follow the established pattern (matching detected evidence)
- Controllers delegate to services rather than containing business logic
- Service class names reflect the business operation they perform

<enforcement>
Claude Code MUST NOT skip or defer verification.

- Automated static analysis MUST check namespace and directory structure compliance
- Code review MUST verify business logic is in service classes, not controllers
- CI pipeline MUST check for proper file organization using the verify commands above
- CI build MUST fail if controllers contain business logic exceeding complexity thresholds
- Pull requests MUST be blocked if service classes are not placed in correct domain directories
- Architecture review REQUIRED for new domains or significant deviations from pattern

**Exception process:**
- Document exception rationale in ADR amendment or inline code comments
- Obtain approval from tech lead or architecture review board
- Add technical debt ticket if exception is temporary workaround
</enforcement>

### Scope

**In scope:**
- All business logic for account management operations
- User invitation and acceptance workflows
- Domain-specific service classes handling core business rules
- Web controllers that serve as entry points for HTTP requests

**Out of scope:**
- Infrastructure-level services (database, caching, queuing)
- Third-party API integrations that don't represent core business logic
- Utility classes and helpers that provide cross-cutting concerns
- Framework-level middleware and request handling
