<rule_activation id="94696166-6c7f-45cf-9104-f07b8c194662" title="Adopt Internationalization (i18n) Language Files for Multi-Language Support: Each Locale Provide" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching `**/*`. Each locale MUST provide translation files for core categories to ensure consistent, maintainable internationalization across the codebase.
</rule_activation>

### Rules

- **R-I18N-001** MUST: Each locale MUST provide translation files for core categories: auth, validation, passwords, actions, pagination, http-statuses, and format.
- **R-I18N-002** MUST: All user-facing text strings in web interfaces, APIs, and command-line tools MUST be externalized to language files, not hardcoded in application code.
- **R-I18N-003** MUST: Error messages, validation feedback, and system notifications MUST be managed through translation files.
- **R-I18N-004** MUST: HTTP status messages and standard framework responses MUST be provided through language files.
- **R-I18N-005** MUST: Authentication and authorization messages MUST be externalized to translation files.
- **R-I18N-006** MUST: Pagination controls and navigation elements MUST use translation keys from language files.
- **R-I18N-007** SHOULD: Use a localization framework (e.g., Laravel's localization, Symfony Translation) that provides helper functions for translation key lookup and parameter substitution.
- **R-I18N-008** SHOULD: Establish naming conventions for translation keys that reflect their context (e.g., auth.failed, validation.required, pagination.next).
- **R-I18N-009** SHOULD: Create a base English locale as the source of truth and use it as the fallback when translations are missing in other locales.
- **R-I18N-010** SHOULD: Implement automated tooling to extract translatable strings from code and generate skeleton translation files for new locales.
- **R-I18N-011** MAY: Internal logging messages not visible to end users MAY remain outside translation files.
- **R-I18N-012** MAY: Developer documentation and code comments MAY remain in English without translation.
- **R-I18N-013** MAY: Configuration file keys and technical identifiers MAY remain untranslated.

### Exceptions

- **EXC-001**: Emergency hotfixes where translation infrastructure is unavailable may proceed without full translation coverage, with follow-up remediation required.
- **EXC-002**: Prototype or proof-of-concept code not intended for production may defer full i18n implementation.

### Verify

```bash
# Count language files in lang/ directory
find lang/ -type f -name '*.php' | wc -l | grep -E '[0-9]+'

# Check for hardcoded user-facing strings outside language files
grep -r "echo\|print" app/ | grep -v "trans(\|__('\|@lang" || echo 'No hardcoded strings found'

# Verify translation completeness and missing keys
php artisan lang:check --missing || composer run check-translations
```

**Accept when:**
- Language directory structure exists with at least one locale containing all required translation categories (auth, validation, passwords, actions, pagination, http-statuses, format)
- No hardcoded user-facing strings are found in application code outside of language files
- Translation loading mechanism is implemented and functional with fallback to default locale for missing keys
- Automated CI pipeline checks confirm no missing translation keys across supported locales
- Code review process verifies new user-facing strings are added to language files
