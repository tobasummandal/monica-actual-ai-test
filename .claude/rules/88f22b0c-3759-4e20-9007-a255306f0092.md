<rule_activation id="88f22b0c-3759-4e20-9007-a255306f0092" title="Use Laravel Hash Facade for Password Credential Storage: Hash Facade Configuration" applies_to="**/*.php">
These rules are ALWAYS ACTIVE for Laravel PHP files handling user authentication and password management, including account creation, password resets, password updates, user invitations, and any authentication action that stores or verifies passwords.

**In scope:**
- All user account creation workflows
- Password reset and recovery flows
- Password update and change operations
- User invitation acceptance with password setting
- Any authentication action that stores or verifies passwords

**Out of scope:**
- API token generation and storage (uses different hashing strategy)
- OAuth provider tokens (managed by external providers)
- Session identifiers (use different security mechanisms)
- Remember me tokens (may use different hashing approach)
- Password reset tokens (temporary, different security model)
</rule_activation>

### Rules

- **R-HASH-001** MUST: Always use `Hash::make($password)` when storing passwords, typically in service classes like CreateAccount, AcceptInvitation, ResetUserPassword, or UpdateUserPassword.
- **R-HASH-002** MUST: Use `Hash::check($plaintext, $hashedValue)` for password verification during authentication.
- **R-HASH-003** MUST NOT: Use direct `password_hash()` or `password_verify()` calls in application code. The Laravel Hash facade must be used instead.
- **R-HASH-004** MUST NOT: Store plain-text passwords or assign password values without hashing through `Hash::make()`.
- **R-HASH-005** SHOULD: Use `Hash::fake()` in tests to avoid expensive hashing operations and speed up test execution.
- **R-HASH-006** SHOULD: Configure `config/hashing.php` to use bcrypt or argon2id algorithms with framework-recommended work factors.
- **R-HASH-007** SHOULD: Consider implementing password rehashing on successful login to automatically upgrade legacy hashes when algorithm configuration changes.

### Verify

```bash
# Check that Hash::make is used for password storage
grep -r "Hash::make" app/ --include="*.php" | wc -l

# Verify no direct password_hash usage in application code
grep -r "password_hash" app/ --include="*.php" || echo "No direct password_hash usage found (good)"

# Check for plain-text password assignments
grep -r "'password'.*=>.*\$" app/ --include="*.php" | grep -v "Hash::make" | grep -v "bcrypt" || echo "No plain-text password assignments found (good)"

# Verify Hash facade configuration
php artisan tinker --execute="echo config('hashing.driver');"
```

**Accept when:**
- All password storage operations use `Hash::make()` as verified by grep showing consistent usage across authentication files
- No direct `password_hash()` calls found in application code (framework usage only)
- Hash facade configuration is properly set in `config/hashing.php` with bcrypt or argon2id driver
- Test suite includes verification that passwords are hashed before database storage
- No plain-text password assignments detected in code review

<enforcement>
Claude Code MUST NOT skip or defer verification of password hashing practices. All password-related code changes require verification that Hash facade is used correctly. CI pipeline MUST fail if plain-text password storage patterns are detected or if Hash facade usage is bypassed. Security team notification is mandatory for violations in production code.

**Violation handling:**
- CI pipeline fails if plain-text password storage patterns are detected
- Pull requests blocked until Hash facade usage is corrected
- Security team notification for violations in production code
- Mandatory security review for any code bypassing Hash facade

**Exception process:**
- Developer submits exception request with technical justification to security team

- Exceptions reviewed quarterly and removed when no longer needed
