<rule_activation id="13fd5be8-42d3-4f06-8178-14c4a177ddd6" title="Adopt HTTP Client Libraries for External API Integration: Http Client Configurations" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files integrating with external APIs, OAuth providers, WebDAV/CalDAV servers, and third-party services.
</rule_activation>

### Rules

- **R-HTTP-001** SHOULD: HTTP client configurations SHOULD be externalized to configuration files or environment variables for different environments.

### Scope

In scope:
- All outbound HTTP/HTTPS requests to external APIs and services
- OAuth provider integrations (Google, Facebook, GitHub, etc.)
- WebDAV, CalDAV, and CardDAV protocol communications
- Third-party REST API consumption (Wikipedia, documentation services, etc.)
- vCard and vCalendar data import/export operations

Out of scope:
- Internal service-to-service communication within the same application
- Database connections and queries
- File system operations
- Message queue or event bus communications
- WebSocket connections (unless using HTTP upgrade mechanism)

### Verify

```bash
# Verify Socialite library usage in OAuth flows
grep -r "use.*Socialite" app/ --include="*.php" | wc -l

# Verify Sabre DAV/VObject libraries for DAV and vCard/vCalendar operations
grep -r "use.*Sabre" app/ --include="*.php" | wc -l

# Verify no raw cURL or socket implementations in external API code
grep -r "curl_exec\|fsockopen" app/ --include="*.php" | wc -l
```

**Accept when:**
- Socialite library usage is detected in OAuth authentication flows
- Sabre DAV/VObject libraries are used for DAV protocol and vCard/vCalendar operations
- No raw cURL or socket implementations are found in new external API integration code
- Service classes encapsulate HTTP client library usage with clear domain interfaces
- HTTP clients are configured with appropriate timeouts, retry policies, and error handling strategies
- Dependency injection is used to provide HTTP client instances for testability
- External API integrations are wrapped in service classes (e.g., WikipediaHelper, DavClient)

### Implementation Guidance

- Wrap HTTP client library usage in service classes to encapsulate external API logic and provide domain-specific interfaces
- Configure HTTP clients with appropriate timeouts, retry policies, and error handling strategies based on each external service's reliability requirements
- Use dependency injection to provide HTTP client instances, enabling easy mocking in unit tests and configuration flexibility across environments
- Document authentication patterns for each integration type (OAuth, Basic Auth, API keys) with examples in the codebase
- Implement logging and monitoring for external API calls to track performance, errors, and usage patterns

### Exceptions

- **EXC-001**: Legacy code maintenance where refactoring risk exceeds benefit
- **EXC-002**: Performance-critical scenarios where library overhead is demonstrably prohibitive (requires benchmarking)

Exception process:
- Developer submits exception request with performance benchmarks or technical justification to Technical Lead
- Technical Lead reviews request and approves/rejects with documented rationale
- Approved exceptions are documented in code comments with issue tracking reference and future migration plan
- Exception registry is maintained and reviewed quarterly to identify patterns requiring policy updates

<enforcement>
Claude Code MUST verify HTTP client library usage patterns and MUST NOT approve external API integrations using raw cURL or socket implementations without documented exceptions. Verification is mandatory before accepting code changes in scope.
</enforcement>
