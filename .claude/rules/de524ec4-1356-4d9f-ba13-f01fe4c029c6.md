<rule_activation id="de524ec4-1356-4d9f-ba13-f01fe4c029c6" title="Adopt Laravel Migrations as Standard Database Schema Management: Migration Files Follow" applies_to="database/migrations/**/*.php">
These rules are ALWAYS ACTIVE for all database schema changes. All schema modifications MUST be implemented through Laravel migration files.
</rule_activation>

### Rules

> **Note**: The source ADR did not contain explicit R-PREFIX-### rule identifiers. The following rules are derived from the ADR's Decision and Policy Block sections.

- **R-LM-001** MUST: Migration files MUST follow Laravel's naming convention: `YYYY_MM_DD_HHMMSS_descriptive_name.php` with timestamps ensuring chronological execution order.

- **R-LM-002** MUST: Each migration file MUST contain both `up()` and `down()` methods using Schema Builder API.

- **R-LM-003** MUST: All table creation, modification, and deletion operations MUST be implemented through migrations.

- **R-LM-004** MUST: All column additions, modifications, and removals MUST be implemented through migrations.

- **R-LM-005** MUST: All index creation and removal MUST be implemented through migrations.

- **R-LM-006** MUST: All foreign key constraint definitions MUST be implemented through migrations.

- **R-LM-007** MUST: Use `php artisan make:migration` command to generate new migration files with proper timestamp and structure.

- **R-LM-008** SHOULD: Test migrations locally with both `migrate` and `migrate:rollback` commands before committing to ensure down() method works correctly.

- **R-LM-009** SHOULD: Use Laravel's migration methods like `foreignId()`, `timestamps()`, `softDeletes()` for consistency with framework conventions.

**In Scope:**
- All table creation, modification, and deletion operations
- Column additions, modifications, and removals
- Index creation and removal
- Foreign key constraint definitions
- Database-level configuration changes that affect schema structure

**Out of Scope:**
- Application data seeding for testing purposes (use database/seeders instead)
- Data migration or transformation scripts that don't modify schema structure
- Database performance tuning that doesn't affect schema (query optimization, connection pooling)
- Backup and restore operations

**Exceptions:**
- **EXC-001**: Emergency production hotfix requiring immediate schema change to resolve critical outage
- **EXC-002**: Database-specific optimizations requiring raw SQL that cannot be expressed through Schema Builder

### Verify

```bash
# Check migration files exist and count them
find database/migrations -name '*.php' -type f | wc -l | grep -E '^[0-9]+$'

# Verify Schema Builder usage
grep -r 'Schema::create\|Schema::table\|Schema::drop' database/migrations/ | wc -l

# Check migration status
php artisan migrate:status 2>&1 | grep -E 'Ran|Pending'

# Verify up() and down() methods exist
ls database/migrations/*.php 2>/dev/null | head -5 | xargs grep -l 'function up()' | xargs grep -l 'function down()'
```

**Accept when:**
- All migration files exist in `database/migrations` directory and follow Laravel naming convention with timestamps
- Each migration file contains both `up()` and `down()` methods using Schema Builder API
- Migration status command executes successfully showing tracked migrations
- No direct SQL schema modifications are found in application code outside migration files

<enforcement>
Claude Code MUST NOT skip or defer verification. All schema changes MUST be reviewed to ensure they are implemented through Laravel migrations. Pull requests containing direct SQL schema changes outside of migrations MUST be flagged.
</enforcement>
