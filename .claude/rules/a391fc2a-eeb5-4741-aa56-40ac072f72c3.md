<rule_activation id="a391fc2a-eeb5-4741-aa56-40ac072f72c3" title="Adopt Internationalization (i18n) Language Files for Multi-Language Support: Language Files Organized" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching `**/*`. Language files MUST be organized by locale code following ISO 639-1 standards, and all user-facing text strings MUST be externalized to language files rather than hardcoded in application code.
</rule_activation>

### Rules

- **R-I18N-001** MUST: Language files MUST be organized by locale code (e.g., lang/en/, lang/hi/, lang/he/, lang/ja/, lang/it/) following ISO 639-1 standards.
- **R-I18N-002** MUST: All user-facing text strings in web interfaces, APIs, and command-line tools MUST be externalized to language files.
- **R-I18N-003** MUST: Error messages, validation feedback, and system notifications MUST be managed through language files.
- **R-I18N-004** MUST: HTTP status messages and standard framework responses MUST be managed through language files.
- **R-I18N-005** MUST: Authentication and authorization messages MUST be managed through language files.
- **R-I18N-006** MUST: Pagination controls and navigation elements MUST be managed through language files.
- **R-I18N-007** SHOULD: Use a localization framework (e.g., Laravel's localization, Symfony Translation) that provides helper functions for translation key lookup and parameter substitution.
- **R-I18N-008** SHOULD: Establish naming conventions for translation keys that reflect their context (e.g., auth.failed, validation.required, pagination.next).
- **R-I18N-009** SHOULD: Create a base English locale as the source of truth and use it as the fallback when translations are missing in other locales.
- **R-I18N-010** SHOULD: Implement automated tooling to extract translatable strings from code and generate skeleton translation files for new locales.
- **R-I18N-011** MAY: Internal logging messages not visible to end users MAY remain outside language files.
- **R-I18N-012** MAY: Developer documentation and code comments MAY remain outside language files.
- **R-I18N-013** MAY: Configuration file keys and technical identifiers MAY remain outside language files.
- **R-I18N-014** MAY: Database schema names and internal system identifiers MAY remain outside language files.
- **R-I18N-015** MAY: Third-party library messages that cannot be intercepted MAY remain outside language files.

### Verify

```bash
# Count language files in lang/ directory
find lang/ -type f -name '*.php' | wc -l | grep -E '[0-9]+'

# Check for hardcoded user-facing strings in application code
grep -r "echo\|print" app/ | grep -v "trans(\|__('\|@lang" || echo 'No hardcoded strings found'

# Run translation checks (Laravel example)
php artisan lang:check --missing || composer run check-translations
```

**Accept when:**
- Language directory structure exists with at least one locale containing all required translation categories (auth, validation, passwords, actions, pagination, http-statuses, format)
- No hardcoded user-facing strings are found in application code outside of language files
- Translation loading mechanism is implemented and functional with fallback to default locale for missing keys
- Automated CI pipeline checks for missing translation keys across supported locales pass
- Code review process verifies new user-facing strings are added to language files
- Static analysis tools confirm no hardcoded strings in application code
- Translation completeness audits show key counts are consistent across locales
