<rule_activation id="a391fc2a-eeb5-4741-aa56-40ac072f72c3" title="Adopt Internationalization (i18n) Language Files for Multi-Language Support: Language Files Organized" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files. This ADR establishes internationalization (i18n) requirements for multi-language support through organized language files.
</rule_activation>

### Rules

- **R-I18N-001** MUST: Language files MUST be organized by locale code (e.g., lang/en/, lang/hi/, lang/he/, lang/ja/, lang/it/) following ISO 639-1 standards.

- **R-I18N-002** MUST: All user-facing text strings in web interfaces, APIs, and command-line tools MUST use translation keys from language files.

- **R-I18N-003** MUST: Error messages, validation feedback, and system notifications MUST be internationalized through language files.

- **R-I18N-004** MUST: HTTP status messages, authentication and authorization messages, pagination controls, and navigation elements MUST use translation keys.

- **R-I18N-005** MUST NOT: Hardcoded user-facing strings MUST NOT appear in application code outside of language files.

- **R-I18N-006** SHOULD: Use a localization framework (e.g., Laravel's localization, Symfony Translation) that provides helper functions for translation key lookup and parameter substitution.

- **R-I18N-007** SHOULD: Establish naming conventions for translation keys that reflect their context (e.g., auth.failed, validation.required, pagination.next).

- **R-I18N-008** SHOULD: Create a base English locale as the source of truth and use it as the fallback when translations are missing in other locales.

- **R-I18N-009** SHOULD: Implement automated tooling to extract translatable strings from code and generate skeleton translation files for new locales.

**Out of scope:**
- Internal logging messages not visible to end users
- Developer documentation and code comments
- Configuration file keys and technical identifiers
- Database schema names and internal system identifiers
- Third-party library messages that cannot be intercepted

**Exceptions:**
- EXC-001: Emergency hotfixes where translation infrastructure is unavailable
- EXC-002: Prototype or proof-of-concept code not intended for production

### Verify

```bash
# Verify language files exist
find lang/ -type f -name '*.php' | wc -l | grep -E '[0-9]+'

# Check for hardcoded strings in application code
grep -r "echo\|print" app/ | grep -v "trans(\|__('\|@lang" || echo 'No hardcoded strings found'

# Check for missing translations across locales
php artisan lang:check --missing || composer run check-translations
```

**Accept when:**
- Language directory structure exists with at least one locale containing all required translation categories (auth, validation, passwords, actions, pagination, http-statuses, format)
- No hardcoded user-facing strings are found in application code outside of language files
- Translation loading mechanism is implemented and functional with fallback to default locale for missing keys

<enforcement>
Claude Code MUST NOT skip or defer verification. All changes introducing user-facing strings must add corresponding translation keys to language files. CI pipeline checks for missing translation keys and hardcoded strings are mandatory. Code reviews must verify compliance before merge.
</enforcement>
