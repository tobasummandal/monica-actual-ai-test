## Context

The application integrates with multiple external services including OAuth providers (Socialite), Wikipedia API, DAV/CalDAV servers, and vCard/vCalendar standards. External API communication requires robust HTTP client capabilities with support for authentication, headers, error handling, and various content types.

## Rules

- **R-HTTP-001** SHOULD: External API integrations SHOULD be wrapped in service classes that encapsulate the HTTP client library usage (e.g., WikipediaHelper, DavClient) to provide domain-specific interfaces.

- **R-HTTP-002** SHOULD: Use specialized libraries (Socialite for OAuth, Sabre DAV for WebDAV/CalDAV/vCard/vCalendar) for complex protocol implementations rather than raw HTTP clients.

- **R-HTTP-003** SHOULD: Configure HTTP clients with appropriate timeouts, retry policies, and error handling strategies based on the reliability requirements of each external service.

- **R-HTTP-004** SHOULD: Use dependency injection to provide HTTP client instances, enabling easy mocking in unit tests and configuration flexibility across environments.

- **R-HTTP-005** MUST NOT: Use raw HTTP implementations (curl_exec, fsockopen) in new external API integration code without documented exceptions following the exception process.

- **R-HTTP-006** SHOULD: Document authentication patterns for each integration type (OAuth, Basic Auth, API keys) with examples in the codebase.

- **R-HTTP-007** SHOULD: Implement logging and monitoring for external API calls to track performance, errors, and usage patterns.

## Rationale

- Using specialized libraries (Socialite, Sabre DAV) reduces implementation complexity and ensures protocol compliance
- HTTP client libraries provide built-in features for authentication, error handling, retry logic, and testing
- Standardizing on established libraries improves code maintainability, reduces security vulnerabilities, and enables easier testing through mocking capabilities
