<rule_activation id="144cf925-c259-4c53-856f-0854e7269130" title="Adopt Domain-Driven Module Boundaries with External API Integration Layers: Resource Handler Classes" applies_to="**/*">
These rules are ALWAYS ACTIVE for all external API integration implementations and domain boundary definitions within the codebase.

**In scope:**
- All external API integrations including REST, SOAP, WebDAV, CardDAV, and other protocol-based communications
- Third-party service integrations that require protocol-specific client implementations
- Data import/export operations involving external standards or formats
- Public API endpoints that expose domain functionality to external consumers

**Out of scope:**
- Internal service-to-service communication within the same application boundary
- Database access layers and repository patterns
- Framework-level HTTP routing and middleware
- Authentication and authorization mechanisms (unless specific to external API integration)

**Exceptions:**
- EXC-001: Legacy integrations predating this ADR that require significant refactoring effort
- EXC-002: Proof-of-concept or experimental integrations in non-production environments
</rule_activation>

### Rules

- **R-DDM-001** SHOULD: Resource handler classes (e.g., ImportResource, ImportVCardResource) SHOULD be used to manage external data import/export operations with clear single responsibilities.
- **R-DDM-002** SHOULD: External API integration modules SHOULD follow domain-based directory structure with dedicated Services and Utils/Model subdirectories.
- **R-DDM-003** SHOULD: Backend interfaces SHOULD exist for all external protocol implementations and be used via dependency injection.
- **R-DDM-004** MUST: Core domain entity and business logic classes MUST NOT contain direct external protocol library usage.
- **R-DDM-005** SHOULD: All data exchange with external APIs SHOULD use dedicated DTO classes rather than direct domain entity serialization.
- **R-DDM-006** SHOULD: ViewHelper classes SHOULD provide presentation layer abstractions that maintain domain boundaries while exposing functionality to external consumers.
- **R-DDM-007** SHOULD: External protocol concerns SHOULD be isolated into dedicated client service layers and utility models.

### Verify

```bash
# Count backend interfaces and implementations
find app/Domains -type f -name '*Client*' -o -name '*Backend*' | xargs grep -l 'interface\|implements' | wc -l

# Count DTO classes in domain modules
find app/Domains -path '*/Services/Utils/Model/*Dto.php' | wc -l

# Check for direct external protocol usage in domain classes (should return 0)
grep -r 'use.*\\Dav\\' app/Domains --include='*.php' | grep -v 'DavClient\|Dav/' | wc -l
```

**Accept when:**
- All external API integration modules follow the domain-based directory structure with dedicated Services and Utils/Model subdirectories
- Backend interfaces exist for all external protocol implementations and are used via dependency injection
- No direct external protocol library usage is found in core domain entity or business logic classes (grep verification returns 0 violations)
- All data exchange with external APIs uses dedicated DTO classes rather than direct domain entity serialization
- Resource handler classes demonstrate clear single responsibilities for import/export operations

<enforcement>
Claude Code MUST NOT skip or defer verification. Verification is mandatory via:
- Automated CI pipeline checks using grep and find commands to detect pattern violations
- Code review checklist items specifically covering external API integration structure
- Architecture decision review for new external integrations before implementation begins

**Violation handling:**
- CI pipeline fails if direct external protocol usage is detected in core domain classes
- Code review blocks merge requests that don't follow the established module structure for new integrations
- Existing violations are logged as technical debt items with prioritized remediation plans

**Exception process:**
- Developer submits exception request to architecture review board with justification and impact analysis
- Review board evaluates request within 2 business days
- Approved exceptions are documented in ADR exceptions log with review date and conditions
- All exceptions require follow-up review after 6 months
</enforcement>
