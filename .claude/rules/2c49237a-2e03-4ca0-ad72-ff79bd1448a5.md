<rule_activation id="2c49237a-2e03-4ca0-ad72-ff79bd1448a5" title="Adopt Internationalization (i18n) Language Files for Multi-Language Support: Translation Files Use" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in the codebase to ensure consistent internationalization practices across user-facing strings, error messages, and locale-specific content.
</rule_activation>

### Rules

- **R-I18N-001** SHOULD: Translation files SHOULD use PHP array return structures for framework compatibility and easy key-value access.

### Verify

```bash
# Verify language files exist and follow PHP array structure
find lang/ -type f -name '*.php' | wc -l | grep -E '[0-9]+'

# Check for hardcoded user-facing strings outside language files
grep -r "echo\|print" app/ | grep -v "trans(\|__('\|@lang" || echo 'No hardcoded strings found'

# Run translation checks
php artisan lang:check --missing || composer run check-translations
```

**Accept when:**
- Language directory structure exists with at least one locale containing all required translation categories (auth, validation, passwords, actions, pagination, http-statuses, format)
- No hardcoded user-facing strings are found in application code outside of language files
- Translation loading mechanism is implemented and functional with fallback to default locale for missing keys

<enforcement>
Claude Code MUST NOT skip or defer verification. Automated CI pipeline checks for missing translation keys across supported locales are mandatory. Code review process must verify new user-facing strings are added to language files. Static analysis tools must scan for hardcoded strings in application code. Violation handling includes CI pipeline failure, code review blocks, and warning notifications when translation drift exceeds 5%.
</enforcement>
