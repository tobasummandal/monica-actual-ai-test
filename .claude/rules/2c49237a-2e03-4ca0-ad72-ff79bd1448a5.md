<rule_activation id="2c49237a-2e03-4ca0-ad72-ff79bd1448a5" title="Adopt Internationalization (i18n) Language Files for Multi-Language Support: Translation Files Use" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files. They govern how internationalization (i18n) should be implemented using language files for multi-language support in the codebase.
</rule_activation>

### Rules

- **R-I18N-001** SHOULD: Translation files SHOULD use PHP array return structures for framework compatibility and easy key-value access

- **R-I18N-002** MUST: All user-facing text strings in web interfaces, APIs, command-line tools, error messages, validation feedback, system notifications, HTTP status messages, authentication/authorization messages, and pagination controls MUST be stored in language files

- **R-I18N-003** MUST NOT: Internal logging messages not visible to end users, developer documentation, code comments, configuration file keys, technical identifiers, database schema names, and internal system identifiers MUST NOT be placed in translation files

- **R-I18N-004** SHOULD: Create a base English locale as the source of truth and use it as the fallback when translations are missing in other locales

- **R-I18N-005** SHOULD: Translation keys SHOULD follow naming conventions that reflect their context (e.g., auth.failed, validation.required, pagination.next)

- **R-I18N-006** SHOULD: Use a localization framework (e.g., Laravel's localization, Symfony Translation) that provides helper functions for translation key lookup and parameter substitution

- **R-I18N-007** SHOULD: Language files SHOULD be organized in a consistent directory structure across all supported locales with standard translation categories (auth, validation, passwords, actions, pagination, http-statuses, format)

- **R-I18N-008** MAY: Emergency hotfixes where translation infrastructure is unavailable (EXC-001) or prototype/proof-of-concept code not intended for production (EXC-002) MAY bypass these translation requirements

### Verify

```bash
# Check that language files exist
find lang/ -type f -name '*.php' | wc -l | grep -E '[0-9]+'

# Verify no hardcoded user-facing strings in application code
grep -r "echo\|print" app/ | grep -v "trans(\|__('\|@lang" || echo 'No hardcoded strings found'

# Check for missing translations across locales
php artisan lang:check --missing || composer run check-translations
```

**Accept when:**
- Language directory structure exists with at least one locale containing all required translation categories (auth, validation, passwords, actions, pagination, http-statuses, format)
- No hardcoded user-facing strings are found in application code outside of language files
- Translation loading mechanism is implemented and functional with fallback to default locale for missing keys
- Translation keys follow consistent naming conventions reflecting their context
- All locales share the same structural pattern and translation key organization

<enforcement>
Claude Code MUST NOT skip or defer verification. Automated CI pipeline checks MUST verify translation completeness across supported locales. Code review MUST verify new user-facing strings are added to language files. Static analysis tools MUST scan for hardcoded strings in application code. CI pipeline MUST fail if hardcoded user-facing strings are detected in pull requests.
</enforcement>
