<rule_activation id="cb1b3330-310b-40bb-8674-347ca401622b" title="Standardize External API Integration with DAV Protocol and DTO Pattern: Resource Import Operations" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in the codebase, particularly external API integrations including DAV, CardDAV, and CalDAV protocols.

**In scope:**
- All external API integrations including DAV, CardDAV, and CalDAV protocols
- Data transfer between external systems and internal domain models
- Resource import and export operations for contacts, calendars, and related entities
- Permission validation and error handling for public-facing API endpoints
- Backend interface implementations for protocol-specific operations

**Out of scope:**
- Internal service-to-service communication within the application
- Database access patterns and repository implementations
- Frontend API endpoints that do not interact with external systems
- Authentication mechanisms (covered by separate security ADRs)
- GraphQL or REST API design for the application's own public API

**Exceptions:**
- EX-001: Legacy integrations that predate this ADR and are scheduled for deprecation within 6 months
- EX-002: Proof-of-concept or experimental integrations in feature branches not intended for production
</rule_activation>

### Rules

- **R-API-001** MUST: Resource import operations from external APIs MUST implement dedicated resource classes (e.g., ImportResource, ImportVCardResource) that handle protocol-specific data transformation.

- **R-API-002** MUST: External API integrations MUST use DTO classes (e.g., ContactDto, ContactDeleteDto) for data transfer with at least one DTO per external entity type to provide clear boundaries between external data formats (e.g., vCard) and internal domain models.

- **R-API-003** MUST: Protocol-specific operations MUST be abstracted behind interface contracts (e.g., IDAVBackend) to enable dependency injection, facilitate unit testing with mocks, and allow for multiple backend implementations without changing client code.

- **R-API-004** MUST: Domain-specific exception types MUST be created for common API failure scenarios (e.g., NotEnoughPermissionException, MaximumNumberOfUsersInVaultException, DavServerNotCompliantException) and properly caught in controllers to provide actionable error messages.

- **R-API-005** SHOULD: ViewHelper classes SHOULD be used in the Web layer to prepare data for API responses, keeping controllers thin and focused on HTTP concerns.

- **R-API-006** SHOULD: When creating new external API integrations, start by defining the DTO classes that represent the external data format, then create mappers to internal domain models.

- **R-API-007** SHOULD: Define backend interfaces before implementing concrete classes; use dependency injection to provide implementations to consumers.

- **R-API-008** SHOULD: Add the Loggable trait to API client classes to ensure consistent logging of external API interactions for debugging and monitoring.

### Verify

```bash
# Check for DTO classes in DavClient services
grep -r "class.*Dto" app/Domains/*/DavClient/Services/Utils/Model/ | wc -l

# Check for Backend interface abstractions
grep -r "interface.*Backend" app/Domains/*/Dav/Web/Backend/ | wc -l

# Check for domain-specific exception types
grep -r "class.*Exception extends" app/Domains/ | grep -E "(Permission|Compliant|Maximum)" | wc -l

# Check for ViewHelper classes
find app/Domains -name "*ViewHelper.php" -type f | wc -l
```

**Accept when:**
- All external API integrations use DTO classes for data transfer with at least one DTO per external entity type
- Protocol-specific operations are abstracted behind interface contracts with at least one concrete implementation
- Domain-specific exception types exist for common API failure scenarios (permission, compliance, limits) and are properly caught in controllers
- ViewHelper classes are present for domains that expose external APIs and are used in controller response preparation

<enforcement>
Claude Code MUST NOT skip or defer verification of external API integration patterns.

**Automated verification:**
- Code review checks for new API integration code to verify presence of DTOs, interfaces, and exception types
- Architecture review sessions for new external API integrations to validate pattern compliance
- Static analysis tools configured to detect direct external API usage without DTO abstraction

**Violation handling:**
- Pull requests that introduce external API integrations without proper DTO/interface patterns are blocked until refactored
- Existing violations in legacy code are tracked in technical debt backlog with priority based on integration stability and maintenance frequency
- Critical violations (missing permission checks, generic exceptions) require immediate remediation before deployment

**Exception process:**
1. Developer submits exception request to Technical Lead with justification and impact analysis
2. Technical Lead reviews request and either approves with conditions or requests pattern compliance
3. Approved exceptions are documented in code with TODO comments linking to migration tickets
4. Exception review occurs quarterly to assess whether exceptions can be resolved
</enforcement>
