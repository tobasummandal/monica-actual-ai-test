<rule_activation id="cb1b3330-310b-40bb-8674-347ca401622b" title="Standardize External API Integration with DAV Protocol and DTO Pattern: Resource Import Operations" applies_to="**/*">
These rules are ALWAYS ACTIVE for all external API integrations including DAV, CardDAV, and CalDAV protocols, data transfer between external systems and internal domain models, resource import and export operations, and permission validation for public-facing API endpoints.
</rule_activation>

### Rules

- **R-DAV-001** MUST: Resource import operations from external APIs MUST implement dedicated resource classes (e.g., ImportResource, ImportVCardResource) that handle protocol-specific data transformation.
- **R-DAV-002** MUST: All external API integrations MUST use DTO classes (e.g., ContactDto, ContactDeleteDto) for data transfer with at least one DTO per external entity type.
- **R-DAV-003** MUST: Protocol-specific operations MUST be abstracted behind interface contracts (e.g., IDAVBackend) with at least one concrete implementation.
- **R-DAV-004** MUST: Domain-specific exception types (NotEnoughPermissionException, MaximumNumberOfUsersInVaultException, DavServerNotCompliantException) MUST exist for common API failure scenarios and be properly caught in controllers.
- **R-DAV-005** MUST: ViewHelper classes MUST be present for domains that expose external APIs and MUST be used in controller response preparation to separate presentation concerns from business logic.
- **R-DAV-006** MUST: Permission validation and error handling MUST be implemented for all public-facing API endpoints that interact with external systems.
- **R-DAV-007** SHOULD: When creating new external API integrations, start by defining DTO classes that represent the external data format, then create mappers to internal domain models.
- **R-DAV-008** SHOULD: Define backend interfaces before implementing concrete classes and use dependency injection to provide implementations to consumers.
- **R-DAV-009** SHOULD: Create domain-specific exception types in the appropriate domain namespace (e.g., app/Domains/Contact/DavClient/Services/Utils/Dav/) with descriptive names and error messages.
- **R-DAV-010** SHOULD: Add the Loggable trait to API client classes to ensure consistent logging of external API interactions for debugging and monitoring.

### Verify

```bash
# Count DTO classes in external API integration paths
grep -r "class.*Dto" app/Domains/*/DavClient/Services/Utils/Model/ | wc -l

# Count backend interface definitions
grep -r "interface.*Backend" app/Domains/*/Dav/Web/Backend/ | wc -l

# Count domain-specific exception types for common failure scenarios
grep -r "class.*Exception extends" app/Domains/ | grep -E "(Permission|Compliant|Maximum)" | wc -l

# Count ViewHelper classes in domains with external APIs
find app/Domains -name "*ViewHelper.php" -type f | wc -l
```

**Accept when:**
- All external API integrations use DTO classes for data transfer with at least one DTO per external entity type
- Protocol-specific operations are abstracted behind interface contracts with at least one concrete implementation
- Domain-specific exception types exist for common API failure scenarios (permission, compliance, limits) and are properly caught in controllers
- ViewHelper classes are present for domains that expose external APIs and are used in controller response preparation
- All external API client classes include the Loggable trait for consistent logging
- No direct external API usage exists without DTO abstraction in new code

Claude Code MUST NOT skip or defer verification. All external API integrations MUST comply with these rules before deployment. Pull requests introducing external API integrations without proper DTO/interface patterns MUST be blocked until refactored. Critical violations (missing permission checks, generic exceptions) require immediate remediation before deployment.
</enforcement>
