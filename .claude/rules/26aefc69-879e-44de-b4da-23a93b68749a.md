<rule_activation id="26aefc69-879e-44de-b4da-23a93b68749a" title="Adopt Laravel Migrations as Standard Database Schema Management: Direct Sql Schema" applies_to="**/*">
These rules are ALWAYS ACTIVE for all database schema changes across the application. All schema modifications MUST be implemented through Laravel migration files.
</rule_activation>

### Rules

- **R-LMIG-001** MUST_NOT: Direct SQL schema modifications MUST NOT be performed on production databases outside of the migration system.
- **R-LMIG-002** MUST: All table creation, modification, and deletion operations MUST be implemented through Laravel migrations.
- **R-LMIG-003** MUST: Column additions, modifications, and removals MUST be implemented through Laravel migrations.
- **R-LMIG-004** MUST: Index creation and removal MUST be implemented through Laravel migrations.
- **R-LMIG-005** MUST: Foreign key constraint definitions MUST be implemented through Laravel migrations.
- **R-LMIG-006** MUST: Database-level configuration changes affecting schema structure MUST be implemented through Laravel migrations.
- **R-LMIG-007** MUST: Use 'php artisan make:migration' command to generate new migration files with proper timestamp and structure.
- **R-LMIG-008** MUST: Each migration file MUST contain both up() and down() methods using Schema Builder API.
- **R-LMIG-009** MUST: Test migrations locally with both 'migrate' and 'migrate:rollback' commands before committing to ensure down() method works correctly.
- **R-LMIG-010** SHOULD: Use Laravel's migration methods like 'foreignId()', 'timestamps()', 'softDeletes()' for consistency with framework conventions.
- **R-LMIG-011** SHOULD: For complex data transformations, separate schema changes from data migrations into distinct migration files for clarity.
- **R-LMIG-012** SHOULD: Document any database-specific SQL used in migrations with comments explaining compatibility implications.
- **R-LMIG-013** MAY: Emergency production hotfixes requiring immediate schema change to resolve critical outage may bypass this process (EXC-001), with post-incident review required.
- **R-LMIG-014** MAY: Database-specific optimizations requiring raw SQL that cannot be expressed through Schema Builder may be considered (EXC-002) with architecture review board approval.

### Verify

```bash
# Count migration files
find database/migrations -name '*.php' -type f | wc -l | grep -E '^[0-9]+$'

# Verify Schema Builder usage
grep -r 'Schema::create\|Schema::table\|Schema::drop' database/migrations/ | wc -l

# Check migration status
php artisan migrate:status 2>&1 | grep -E 'Ran|Pending'

# Verify up() and down() methods exist
ls database/migrations/*.php 2>/dev/null | head -5 | xargs grep -l 'function up()' | xargs grep -l 'function down()'
```

**Accept when:**
- All migration files exist in database/migrations directory and follow Laravel naming convention with timestamps (YYYY_MM_DD_HHMMSS_description.php)
- Each migration file contains both up() and down() methods using Schema Builder API
- Migration status command executes successfully showing tracked migrations
- No direct SQL schema modifications are found in application code outside migration files
- Migration files follow chronological ordering and prevent conflicts through timestamp-based naming
- All schema changes (table creation/modification/deletion, column operations, indexes, foreign keys) are implemented through migrations

<enforcement>
Claude Code MUST verify all database schema changes comply with Laravel migration requirements. Code review MUST flag any direct SQL schema modifications outside the migration system. Pre-deployment checks MUST run 'php artisan migrate:status' to verify migration state. Violations MUST be rejected and require creation of corresponding migration file.
</enforcement>
