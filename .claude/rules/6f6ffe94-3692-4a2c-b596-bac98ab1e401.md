<rule_activation id="6f6ffe94-3692-4a2c-b596-bac98ab1e401" title="Adopt Domain-Driven Module Boundaries with External API Integration Layers: Each External Integration" applies_to="**/*">
These rules are ALWAYS ACTIVE for all external API integration implementations and domain boundary definitions within the codebase.

**In scope:**
- All external API integrations including REST, SOAP, WebDAV, CardDAV, and other protocol-based communications
- Third-party service integrations that require protocol-specific client implementations
- Data import/export operations involving external standards or formats
- Public API endpoints that expose domain functionality to external consumers

**Out of scope:**
- Internal service-to-service communication within the same application boundary
- Database access layers and repository patterns
- Framework-level HTTP routing and middleware
- Authentication and authorization mechanisms (unless specific to external API integration)

**Exceptions:**
- EXC-001: Legacy integrations predating this ADR that require significant refactoring effort
- EXC-002: Proof-of-concept or experimental integrations in non-production environments
</rule_activation>

### Rules

- **R-DDMB-001** MUST: Each external API integration MUST provide a dedicated client service layer (e.g., DavClient/Services) that encapsulates all protocol-specific communication logic.

- **R-DDMB-002** MUST: External API integration modules MUST follow the domain-based directory structure with dedicated Services and Utils/Model subdirectories (e.g., `{Domain}/{IntegrationName}/Services`, `/Utils/Model`, `/Web/Backend`).

- **R-DDMB-003** MUST: Backend interfaces MUST exist for all external protocol implementations and be used via dependency injection to enable testability and implementation substitution.

- **R-DDMB-004** MUST: Core domain entity and business logic classes MUST NOT contain direct external protocol library usage. Protocol-specific code must be isolated to integration layers.

- **R-DDMB-005** MUST: All data exchange with external APIs MUST use dedicated DTO (Data Transfer Object) classes rather than direct domain entity serialization.

- **R-DDMB-006** SHOULD: Define the backend interface contract before implementing concrete clients to ensure testability from the start.

- **R-DDMB-007** SHOULD: Create DTOs that match external API schemas closely, then use separate mapper classes to transform between DTOs and domain entities.

- **R-DDMB-008** SHOULD: Document the external API version and protocol specifications in the integration module README for future maintainers.

### Verify

```bash
# Count client and backend implementations using interfaces
find app/Domains -type f -name '*Client*' -o -name '*Backend*' | xargs grep -l 'interface\|implements' | wc -l

# Count DTO classes in integration modules
find app/Domains -path '*/Services/Utils/Model/*Dto.php' | wc -l

# Detect direct protocol library usage in core domain classes (should return 0)
grep -r 'use.*\\Dav\\' app/Domains --include='*.php' | grep -v 'DavClient\|Dav/' | wc -l
```

**Accept when:**
- All external API integration modules follow the domain-based directory structure with dedicated Services and Utils/Model subdirectories
- Backend interfaces exist for all external protocol implementations and are used via dependency injection
- No direct external protocol library usage is found in core domain entity or business logic classes (grep verification returns 0 violations)
- All data exchange with external APIs uses dedicated DTO classes rather than direct domain entity serialization

<enforcement>
Claude Code MUST verify compliance with these rules when creating or modifying external API integrations. Verification commands MUST be executed to detect violations. Code review and architectural approval are required for all exceptions.
</enforcement>
