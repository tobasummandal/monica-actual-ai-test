<rule_activation id="38f686a5-cf99-4fd1-b4b8-a709af962732" title="Standardize Public API Contract Design with Interface-Based DTOs and Exception Handling: External Service Integrations" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in the codebase, with particular focus on REST API endpoints, WebDAV/CardDAV integration interfaces, data transfer objects, custom exception classes, ViewHelper classes, and service layer interfaces.

**In scope:**
- All REST API endpoints exposed to external consumers
- WebDAV/CardDAV integration interfaces and backends
- Data transfer objects used in API request/response payloads
- Custom exception classes thrown by public API methods
- ViewHelper classes that prepare data for API responses
- Service layer interfaces that define public contracts

**Out of scope:**
- Internal domain models and entities not exposed via APIs
- Private service methods used only within domain boundaries
- Database repositories and data access layers
- Internal event handlers and message queue consumers
- Administrative CLI commands and internal tools

**Exceptions:**
- EXC-001: Legacy API endpoints that predate this ADR and have established external consumers
- EXC-002: Prototype or experimental APIs explicitly marked as unstable/alpha
</rule_activation>

### Rules

- **R-API-001** SHOULD: External service integrations SHOULD implement service-specific exception types (e.g., DavServerNotCompliantException) to distinguish integration failures from application errors.

- **R-API-002** SHOULD: All public API endpoints SHOULD have corresponding interface definitions with explicit method signatures to provide clear contract boundaries.

- **R-API-003** SHOULD: All API request/response payloads SHOULD use dedicated DTO classes rather than exposing domain models directly to decouple internal representations from external contracts.

- **R-API-004** SHOULD: All public API error conditions SHOULD throw domain-specific exceptions with clear messages rather than generic exception types.

- **R-API-005** SHOULD: DTOs SHOULD be suffixed with 'Dto' (e.g., ContactDto, ContactDeleteDto) following established naming conventions.

- **R-API-006** SHOULD: Interfaces SHOULD be prefixed with 'I' (e.g., IDAVBackend) following established naming conventions.

- **R-API-007** SHOULD: Custom exceptions SHOULD be suffixed with 'Exception' (e.g., NotEnoughPermissionException, MaximumNumberOfUsersInVaultException) following established naming conventions.

- **R-API-008** SHOULD: All interface methods SHOULD use PHP type hints and return type declarations to enforce contract compliance at runtime.

- **R-API-009** SHOULD: All public interfaces and DTOs SHOULD be documented with PHPDoc annotations including @api tag to clearly mark public contracts.

### Verify

```bash
# Count DTO classes in domain layer
grep -r "class.*Dto" app/Domains --include="*.php" | wc -l

# Count interface definitions with 'I' prefix
grep -r "interface I[A-Z]" app/Domains --include="*.php" | wc -l

# Count custom exception classes
grep -r "class.*Exception extends" app/Exceptions --include="*.php" | wc -l

# Count ViewHelper classes
find app/Domains -name "*ViewHelper.php" -type f | wc -l
```

**Accept when:**
- All public API endpoints have corresponding interface definitions with explicit method signatures
- All API request/response payloads use dedicated DTO classes rather than exposing domain models
- All public API error conditions throw domain-specific exceptions with clear messages
- Grep commands show consistent presence of DTOs, interfaces, custom exceptions, and ViewHelpers across API-related code
- Naming conventions are followed: DTOs suffixed with 'Dto', interfaces prefixed with 'I', exceptions suffixed with 'Exception'
- Interface methods include PHP type hints and return type declarations
- Public interfaces and DTOs include PHPDoc annotations with @api tags

<enforcement>
Claude Code MUST verify compliance with these rules when:
- Creating or modifying public API endpoints
- Adding or updating data transfer objects
- Implementing external service integrations
- Defining new exception types for API error handling
- Creating interface definitions for service contracts

Verification MUST include:
- Automated static analysis checking for direct domain model exposure in API controllers
- Code review validation that interface definitions exist for all new public API endpoints
- CI pipeline tests validating DTO serialization/deserialization contracts
- Confirmation that naming conventions are followed for DTOs, interfaces, and exceptions

Claude Code MUST NOT skip or defer verification of these architectural contracts.
</enforcement>
