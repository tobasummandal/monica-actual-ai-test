<rule_activation id="6b0fe053-7ede-4625-82e3-a79dd3a91ea5" title="Adopt Domain-Driven Service Layer Pattern for Journal Management: Service Classes Follow" applies_to="app/Domains/Vault/ManageJournals/**/*.php">
These rules are ALWAYS ACTIVE for all files matching `app/Domains/Vault/ManageJournals/**/*.php`.

This ADR establishes a domain-driven service layer pattern for journal management operations, ensuring clean separation between HTTP handling and business logic.

**In scope:**
- All journal management operations including posts, metrics, photos, tags, slices of life, and contacts
- Business logic that requires database transactions or multiple model interactions
- Operations that enforce domain-specific business rules and validation
- Functionality within the Vault domain's ManageJournals subdomain

**Out of scope:**
- Simple CRUD operations that only involve single-model persistence without business logic
- HTTP request/response handling and view rendering (belongs in controllers)
- Cross-domain operations that span multiple bounded contexts
- Infrastructure concerns like caching, logging, and external API integration
</rule_activation>

### Rules

- **R-SVC-001** MUST: Service classes MUST follow single-responsibility principle with one primary operation per class (e.g., CreatePostMetric, DestroySliceOfLife, UpdateJournalMetric).
- **R-SVC-002** MUST: Controllers MUST remain thin and delegate business logic to service classes - controllers should only validate input, call services, and return responses.
- **R-SVC-003** MUST: Service classes MUST exist in dedicated Services directories within domain boundaries (e.g., app/Domains/Vault/ManageJournals/Services).
- **R-SVC-004** SHOULD: Service class names SHOULD follow verb-noun convention to clearly communicate intent (e.g., CreatePost, UpdateMetric, RemoveTag).
- **R-SVC-005** SHOULD: Services SHOULD accept primitive types or DTOs as parameters rather than HTTP request objects to maintain independence from web layer.
- **R-SVC-006** SHOULD: Use dependency injection for service dependencies to improve testability and enable mocking.
- **R-SVC-007** MAY: Group related services in subdirectories if a domain grows large (e.g., ManageJournals/Services/Posts, ManageJournals/Services/Metrics).

### Verify

```bash
# Check that service classes exist in Services directories
find app/Domains/*/Services -type f -name '*.php' | wc -l

# Count controllers in journal management
grep -r 'class.*Controller' app/Domains/Vault/ManageJournals/Web/Controllers | wc -l

# Verify Services namespace usage
grep -r 'namespace.*Services' app/Domains/Vault/ManageJournals/Services | head -5
```

**Accept when:**
- Service classes exist in dedicated Services directories within domain boundaries
- Controllers delegate to services rather than implementing business logic directly
- Service class names follow verb-noun convention and implement single-responsibility operations

<enforcement>
Claude Code MUST verify adherence to service layer patterns during code review. Violations MUST be flagged with specific guidance:
- Business logic in controllers → refactor to service classes
- Service classes with multiple responsibilities → split into single-responsibility services
- Services without clear verb-noun naming → rename to communicate intent

Exception process:
1. Document rationale for exception in code comments or ADR
2. Obtain approval from tech lead or architect for significant deviations
3. Review exceptions quarterly to determine if pattern needs adjustment

Automated verification:
- Code review process checking for business logic in controllers
- Static analysis tools detecting controller method complexity
- Architecture decision review for new domains and subdomains
</enforcement>
