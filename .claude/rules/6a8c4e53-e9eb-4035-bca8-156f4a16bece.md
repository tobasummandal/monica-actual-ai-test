<rule_activation id="6a8c4e53-e9eb-4035-bca8-156f4a16bece" title="Standardize Logging with Laravel Log Facade in DAV and Job Components: Components Use Dedicated" applies_to="**/*">
These rules apply to DAV backend implementations, background jobs in Contact/Dav and Contact/DavClient domains, DavClient service utilities, and console commands for address book setup.

**In scope:**
- DAV backend implementations (CalDAV/CardDAV)
- Background jobs in Contact/Dav and Contact/DavClient domains
- DavClient service utilities and synchronization services
- Console commands for address book and application setup
- Any component performing external DAV server communication

**Out of scope:**
- Frontend JavaScript logging
- Database query logging (handled by Laravel's query log)
- HTTP middleware logging (handled by web server/framework)
- Third-party package internal logging
- Unit test execution logging

**Exceptions:**
- EXC-001: Performance-critical hot paths where logging overhead is measured and documented as unacceptable
- EXC-002: Temporary debugging code using dd(), dump(), or var_dump() during active development
</rule_activation>

### Rules

- **R-LLOG-001** MUST: Use Laravel's Log facade (`Illuminate\Support\Facades\Log`) for logging in DAV backend implementations, background jobs in Contact/Dav and Contact/DavClient domains, DavClient service utilities, and console commands for address book setup.
- **R-LLOG-002** MAY: Components MAY use dedicated log channels for DAV operations to enable separate log routing and retention policies (e.g., `Log::channel('dav')->info('Sync started')`).
- **R-LLOG-003** SHOULD: Import the Log facade at the top of each class using `use Illuminate\Support\Facades\Log;`.
- **R-LLOG-004** SHOULD: Use appropriate log levels based on event significance:
  - `Log::debug()` for detailed tracing
  - `Log::info()` for significant events
  - `Log::warning()` for recoverable issues
  - `Log::error()` for failures requiring attention
- **R-LLOG-005** SHOULD: Include structured context as second parameter to log methods (e.g., `Log::info('VCard synchronized', ['contact_id' => $id, 'addressbook_id' => $addressbookId])`).
- **R-LLOG-006** SHOULD: In job classes, log at the beginning and end of handle() method with job-specific context to enable job execution tracking.
- **R-LLOG-007** SHOULD: Avoid logging in tight loops - consider sampling or aggregating log messages for bulk operations.
- **R-LLOG-008** MUST: Avoid logging sensitive data (authentication tokens, personal contact information) to prevent security and privacy compliance violations.

### Verify

```bash
# Check for Log facade imports in target directories
grep -r "use Illuminate\\\\Support\\\\Facades\\\\Log" app/Domains/Contact/Dav* app/Console/Commands/ | wc -l

# Check for Log method calls with appropriate levels
grep -r "Log::" app/Domains/Contact/Dav* app/Console/Commands/ | grep -E "(debug|info|warning|error)" | wc -l

# Verify Log facade is available and properly configured
php artisan tinker --execute="echo class_exists('Illuminate\\\\Support\\\\Facades\\\\Log') ? 'PASS' : 'FAIL';"
```

**Accept when:**
- Log facade import statements are present in all DAV backend classes, DavClient services, and relevant console commands
- Log method calls (debug/info/warning/error) are present in job handle() methods and synchronization service methods
- Laravel's Log facade class is available and properly configured in the application

<enforcement>
Claude Code MUST NOT skip or defer verification. Violations are handled through:
- Code review checklist requiring Log facade usage in DAV and job components
- Static analysis with custom PHPStan/Psalm rules detecting missing logging in job handle() methods
- Automated grep-based verification in CI pipeline checking for Log facade imports in target directories
- PR comments requesting addition of appropriate logging statements with context
- Failed CI checks for missing Log facade imports in new DAV/job files
- Architecture review escalation for systematic violations or proposed alternatives

Exception process:
- Developer documents performance impact with profiling data and proposes alternative observability approach
- Tech lead reviews exception request and approves/rejects with written justification
- Approved exceptions are documented in code comments with ADR reference and expiration date for review
</enforcement>
