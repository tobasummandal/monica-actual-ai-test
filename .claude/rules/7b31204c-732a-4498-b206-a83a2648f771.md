<rule_activation id="7b31204c-732a-4498-b206-a83a2648f771" title="Standardize Exception and Logging Formatting for External API Responses: Exception Classes Include" applies_to="**/*">
These rules are ALWAYS ACTIVE for all external API endpoints and exception handling components. All new exception classes and logging utilities MUST comply with the formatting standards defined herein.
</rule_activation>

### Rules

- **R-API-001** MAY: Exception classes MAY include additional domain-specific fields in the formatted response if they enhance client-side error handling.
- **R-API-002** MUST: All custom exception classes that can be thrown from external API endpoints implement a Formattable interface or equivalent formatter trait.
- **R-API-003** MUST: Logging utilities and traits used within API request/response lifecycle follow the same formatting methods as exception classes.
- **R-API-004** MUST: Error response middleware and exception handlers for public APIs produce structurally consistent output.
- **R-API-005** MUST: All exception classes implement methods like toArray(), toJson(), and getHttpStatusCode().
- **R-API-006** MUST: Error responses follow a standard schema: {error: {code, message, status, timestamp, context}}.
- **R-API-007** SHOULD: New exception classes be generated using scaffold commands that automatically include formatter implementation.

### Verify

```bash
# Verify all exception classes implement Formattable interface
grep -r "class.*Exception" app/ | xargs -I {} sh -c 'grep -l "Formattable\|toArray\|toJson" {}'

# Run exception formatter tests
php artisan test --filter ExceptionFormatterTest

# Verify Loggable trait uses consistent formatting
grep -r "use.*Loggable" app/ | xargs -I {} sh -c 'grep -l "format\|toArray" {}'
```

**Accept when:**
- All exception classes in app/Exceptions/ that are thrown from API routes implement the Formattable interface or equivalent formatter trait
- Automated tests verify that exception responses match the documented JSON schema with required fields (code, message, status, timestamp)
- The Loggable trait and all exception formatters produce structurally consistent output as verified by integration tests
- CI pipeline validates exception response formats against JSON schema
- Static analysis tools (PHPStan/Psalm) confirm Formattable interface requirement on exception classes
- API contract tests validate error response structures

<enforcement>
Claude Code MUST NOT skip or defer verification. All exception classes and logging utilities MUST be verified against the Formattable interface requirement and JSON schema validation before code is committed. Violations block CI pipeline execution and code review approval.
</enforcement>
