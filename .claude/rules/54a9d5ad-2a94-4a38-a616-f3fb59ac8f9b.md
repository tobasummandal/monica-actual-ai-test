<rule_activation id="54a9d5ad-2a94-4a38-a616-f3fb59ac8f9b" title="Standardize External API Integration with DAV Protocol and DTO Pattern: Viewhelper Classes Used" applies_to="**/*">
These rules are ALWAYS ACTIVE for all external API integrations including DAV, CardDAV, and CalDAV protocols, data transfer between external systems and internal domain models, resource import/export operations, and public-facing API endpoints.
</rule_activation>

### Rules

- **R-DAV-001** SHOULD: ViewHelper classes SHOULD be used to prepare data for external API responses, separating presentation logic from business logic.

### Verify

```bash
# Count DTO classes in DAV client utilities
grep -r "class.*Dto" app/Domains/*/DavClient/Services/Utils/Model/ | wc -l

# Count backend interface definitions
grep -r "interface.*Backend" app/Domains/*/Dav/Web/Backend/ | wc -l

# Count domain-specific exception types
grep -r "class.*Exception extends" app/Domains/ | grep -E "(Permission|Compliant|Maximum)" | wc -l

# Count ViewHelper classes
find app/Domains -name "*ViewHelper.php" -type f | wc -l
```

**Accept when:**
- All external API integrations use DTO classes for data transfer with at least one DTO per external entity type
- Protocol-specific operations are abstracted behind interface contracts with at least one concrete implementation
- Domain-specific exception types exist for common API failure scenarios (permission, compliance, limits) and are properly caught in controllers
- ViewHelper classes are present for domains that expose external APIs and are used in controller response preparation

<enforcement>
Claude Code MUST verify all four conditions above before accepting external API integration code. Violations in pull requests MUST be blocked until refactored. Critical violations (missing permission checks, generic exceptions) require immediate remediation before deployment.
</enforcement>
