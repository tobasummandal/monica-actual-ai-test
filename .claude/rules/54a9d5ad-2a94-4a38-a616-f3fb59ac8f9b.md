These rules are ALWAYS ACTIVE for external API integrations, particularly DAV protocol implementations in app/Domains/*/DavClient/ and related directories.
</rule_activation>

### Rules

- **R-DAV-001** SHOULD: Use DTO classes for external API data transfer between external data formats (e.g., vCard) and internal domain models, with at least one DTO per external entity type.
- **R-DAV-002** SHOULD: Abstract protocol-specific operations behind interface contracts (e.g., IDAVBackend) with dependency injection to enable testability and multiple implementations.
- **R-DAV-003** SHOULD: Create domain-specific exception types in the appropriate domain namespace (e.g., NotEnoughPermissionException, DavServerNotCompliantException, MaximumNumberOfUsersInVaultException) for common API failure scenarios, ensuring they are properly caught in controllers.
- **R-DAV-004** SHOULD: Use ViewHelper classes in the Web layer to prepare data for external API responses, separating presentation logic from business logic and keeping controllers thin.
- **R-DAV-005** SHOULD: When creating new external API integrations, define DTOs first, then create mappers to internal domain models, followed by backend interfaces before concrete implementations.

### Scope

**In scope:**
- All external API integrations including DAV, CardDAV, and CalDAV protocols
- Data transfer between external systems and internal domain models
- Resource import and export operations for contacts, calendars, and related entities
- Permission validation and error handling for public-facing API endpoints
- Backend interface implementations for protocol-specific operations

**Out of scope:**
- Internal service-to-service communication within the application
- Database access patterns and repository implementations
- Frontend API endpoints that do not interact with external systems
- Authentication mechanisms (covered by separate security ADRs)
- GraphQL or REST API design for the application's own public API

**Exceptions:**
- EX-001: Legacy integrations that predate this ADR and are scheduled for deprecation within 6 months
- EX-002: Proof-of-concept or experimental integrations in feature branches not intended for production

### Verify

```bash
# Check for DTO classes in DavClient integrations
grep -r "class.*Dto" app/Domains/*/DavClient/Services/Utils/Model/ | wc -l

# Check for Backend interface abstractions
grep -r "interface.*Backend" app/Domains/*/Dav/Web/Backend/ | wc -l

# Check for domain-specific exception types
grep -r "class.*Exception extends" app/Domains/ | grep -E "(Permission|Compliant|Maximum)" | wc -l

# Check for ViewHelper classes
find app/Domains -name "*ViewHelper.php" -type f | wc -l
```

**Accept when:**
- All external API integrations use DTO classes for data transfer with at least one DTO per external entity type
- Protocol-specific operations are abstracted behind interface contracts with at least one concrete implementation
- Domain-specific exception types exist for common API failure scenarios (permission, compliance, limits) and are properly caught in controllers
- ViewHelper classes are present for domains that expose external APIs and are used in controller response preparation

<enforcement>
Claude Code MUST verify compliance with these patterns when implementing or modifying external API integrations. Automated code review checks should verify presence of DTOs, interfaces, and exception types. Pull requests that introduce external API integrations without proper DTO/interface patterns should be blocked until refactored.
</enforcement>

### Implementation Guidance

- Start by defining DTO classes that represent the external data format
- Create mappers from DTOs to internal domain models with proper validation
- Define backend interfaces before implementing concrete classes
- Use dependency injection to provide implementations to consumers
- Create domain-specific exception types with descriptive names and error messages
- Add the Loggable trait to API client classes for consistent logging
- Use ViewHelper classes in the Web layer for API response preparation, keeping controllers focused on HTTP concerns
