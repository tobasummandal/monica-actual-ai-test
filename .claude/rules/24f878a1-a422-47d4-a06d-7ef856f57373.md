<rule_activation id="24f878a1-a422-47d4-a06d-7ef856f57373" title="Adopt Domain-Driven DAV/CardDAV Integration Pattern for External Contact Synchronization: Import Export Operations" applies_to="**/*">
These rules are ACTIVE for all external API integrations involving contact synchronization via DAV/CardDAV protocols within domain-bounded contexts.

**In scope:**
- All DAV/CardDAV protocol integrations for contact synchronization
- External API integrations requiring domain boundary enforcement
- VCard import/export operations across system boundaries
- Contact data synchronization with third-party DAV servers

**Out of scope:**
- Internal domain-to-domain communication within the application
- REST API endpoints for web/mobile clients
- Database-level data access patterns
- Non-contact related external integrations

**Exception:** EXC-001: Legacy DAV server integration requires direct database access for performance optimization
</rule_activation>

### Rules

- **R-DAV-001** SHOULD: Import and export operations SHOULD be separated into distinct resource classes (ImportResource, ImportVCardResource) following single responsibility principle.

- **R-DAV-002** MUST: Domain boundaries MUST be enforced through dedicated DTO objects (ContactDto, ContactDeleteDto) and service boundaries to prevent tight coupling between external systems and internal domain models.

- **R-DAV-003** MUST: External DAV integrations MUST use interface-based backend implementations (IDAVBackend) to enable testability and maintainability.

- **R-DAV-004** MUST: Explicit exception handling MUST be implemented for non-compliant DAV servers using specific exception types (DavServerNotCompliantException) with detailed error messages.

- **R-DAV-005** SHOULD: ViewHelper pattern SHOULD be used to separate presentation concerns from domain logic when preparing data for presentation layers.

- **R-DAV-006** MUST: VCard format MUST be used as the standard interchange format for contact data in DAV/CardDAV ecosystems.

- **R-DAV-007** MUST: DTO classes MUST include explicit validation rules and transformation methods to/from domain entities.

### Verify

```bash
# Check for DTO classes in Contact domain DavClient services
grep -r "class.*Dto" app/Domains/Contact/DavClient/Services/Utils/Model/ | wc -l

# Verify IDAVBackend interface exists
grep -r "interface.*Backend" app/Domains/Contact/Dav/Web/Backend/ | grep -c "IDAVBackend"

# Check for non-compliant server exception handling
grep -r "DavServerNotCompliantException" app/Domains/Contact/DavClient/Services/Utils/Dav/ | wc -l

# Count separate resource classes for import operations
find app/Domains/Contact/Dav -name "*Resource.php" -type f | wc -l
```

**Accept when:**
- At least 2 DTO classes exist in Contact domain DavClient services for data transfer
- IDAVBackend interface is defined and implemented by at least one concrete backend class
- DavServerNotCompliantException exists and is used in DAV client error handling
- Separate resource classes exist for import operations (ImportResource, ImportVCardResource)
