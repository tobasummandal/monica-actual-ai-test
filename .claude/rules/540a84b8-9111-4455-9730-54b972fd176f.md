<rule_activation id="540a84b8-9111-4455-9730-54b972fd176f" title="Adopt Eloquent ORM Models as Standard Data Access Layer: Models Define Custom" applies_to="**/*.php">
These rules are ALWAYS ACTIVE for all PHP files.

Use Eloquent ORM models as the standard data access layer. Models should be placed in app/Models namespace and extend Illuminate\Database\Eloquent\Model.

**In scope:**
- All database-backed domain entities requiring CRUD operations
- Entities with relationships to other database tables
- Data structures requiring validation, casting, or transformation
- Objects requiring query builder functionality and collection operations

**Out of scope:**
- Value objects without database persistence
- Data Transfer Objects (DTOs) used for API communication
- Temporary data structures for in-memory processing
- External service integrations not backed by application database

**Exceptions:**
- EXC-001: Legacy database schemas require raw SQL queries that cannot be efficiently expressed through Eloquent
- EXC-002: Read-only reporting queries spanning multiple complex joins benefit from query builder or raw SQL
</rule_activation>

### Rules

- **R-ELOQUENT-001** MUST: All model files in app/Models must extend Illuminate\Database\Eloquent\Model.
- **R-ELOQUENT-002** MUST: Models must define either $fillable or $guarded properties for mass assignment protection.
- **R-ELOQUENT-003** MUST: Direct database queries outside models (using DB::table or DB::select) must be documented with exception justifications referencing EXC-001 or EXC-002.
- **R-ELOQUENT-004** MAY: Models may define custom query scopes, accessors, and mutators for domain-specific data manipulation.
- **R-ELOQUENT-005** SHOULD: Use php artisan make:model command to generate new models with consistent structure and optional migration/factory scaffolding.
- **R-ELOQUENT-006** SHOULD: Define relationships using type-hinted return types (e.g., public function posts(): HasMany) for better IDE support and static analysis.
- **R-ELOQUENT-007** SHOULD: Document complex query scopes and custom accessors with PHPDoc blocks explaining their purpose and usage.
- **R-ELOQUENT-008** SHOULD: Consider using model observers for cross-cutting concerns like logging, caching, or event dispatching rather than cluttering model methods.

### Verify

```bash
# Count models extending Model class
grep -r "extends Model" app/Models/ | wc -l

# Find models missing proper namespace
find app/Models -name '*.php' -exec grep -L 'namespace App\\Models' {} \;

# Count total model classes (requires Laravel)
php artisan model:show --all 2>&1 | grep -c 'class'

# Find direct database queries outside models (excluding documented exceptions)
grep -r "DB::table\|DB::select" app/Http app/Services | grep -v "// Exception" | wc -l
```

**Accept when:**
- All model files in app/Models extend Illuminate\Database\Eloquent\Model
- At least 7 model classes exist matching the detected pattern (File, PostTemplateSection, ContactInformationType, GiftOccasion, CallReasonType, Account, QuickFact)
- Models define either $fillable or $guarded properties for mass assignment protection
- Direct database queries outside models are documented with exception justifications (EXC-001 or EXC-002)
- No models are created outside app/Models namespace
- Verification commands show expected baseline: grep count ≥ 7, namespace check returns empty, direct query count with exceptions = 0

<enforcement>
Claude Code MUST verify these rules when:
- Creating new model classes
- Modifying existing models in app/Models
- Adding database queries in controllers, services, or other non-model layers
- Code review of changes affecting data access patterns

Verification MUST NOT be skipped or deferred. CI pipeline should fail if:
- Models are created outside app/Models namespace
- Models lack mass assignment protection ($fillable or $guarded)
- Direct database queries lack exception documentation

Exception process:
- Developer documents exception rationale in code comments with EXC-ID reference (EXC-001 or EXC-002)
- Technical lead reviews and approves exception via pull request comment
- Exceptions are reviewed quarterly to determine if they should become permanent patterns or be refactored
</enforcement>
