<rule_activation id="c9e7bfd4-6df4-4c64-8def-83ce061810ea" title="Standardize External API Integration with DAV Protocol and DTO Pattern: External Integrations Use" applies_to="**/*">
These rules are ALWAYS ACTIVE for all external API integrations, particularly those involving DAV, CardDAV, and CalDAV protocols, as well as resource import/export operations and public-facing API endpoints that interact with external systems.
</rule_activation>

### Rules

- **R-DAV-001** MUST: External API integrations MUST use Data Transfer Objects (DTOs) to represent external data structures and maintain clear boundaries between external formats and internal domain models.

### Verify

```bash
# Count DTO classes in external API integration paths
grep -r "class.*Dto" app/Domains/*/DavClient/Services/Utils/Model/ | wc -l

# Count backend interface definitions
grep -r "interface.*Backend" app/Domains/*/Dav/Web/Backend/ | wc -l

# Count domain-specific exception types for API failures
grep -r "class.*Exception extends" app/Domains/ | grep -E "(Permission|Compliant|Maximum)" | wc -l

# Count ViewHelper classes for API response preparation
find app/Domains -name "*ViewHelper.php" -type f | wc -l
```

**Accept when:**
- All external API integrations use DTO classes for data transfer with at least one DTO per external entity type
- Protocol-specific operations are abstracted behind interface contracts with at least one concrete implementation
- Domain-specific exception types exist for common API failure scenarios (permission, compliance, limits) and are properly caught in controllers
- ViewHelper classes are present for domains that expose external APIs and are used in controller response preparation

<enforcement>
Claude Code MUST NOT skip or defer verification of external API integration patterns. All new integrations with DAV, CardDAV, CalDAV, or similar external protocols MUST comply with DTO abstraction, interface-based design, and domain-specific exception handling before approval.
</enforcement>
