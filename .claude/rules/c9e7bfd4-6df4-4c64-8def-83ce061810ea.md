<rule_activation id="c9e7bfd4-6df4-4c64-8def-83ce061810ea" title="Standardize External API Integration with DAV Protocol and DTO Pattern: External Integrations Use" applies_to="**/*">
These rules apply to all external API integrations including DAV, CardDAV, and CalDAV protocols. Rules are ACTIVE for:
- Data transfer between external systems and internal domain models
- Resource import and export operations for contacts, calendars, and related entities
- Permission validation and error handling for public-facing API endpoints
- Backend interface implementations for protocol-specific operations

**In scope:**
- All external API integrations including DAV, CardDAV, and CalDAV protocols
- Data transfer between external systems and internal domain models
- Resource import and export operations for contacts, calendars, and related entities
- Permission validation and error handling for public-facing API endpoints
- Backend interface implementations for protocol-specific operations

**Out of scope:**
- Internal service-to-service communication within the application
- Database access patterns and repository implementations
- Frontend API endpoints that do not interact with external systems
- Authentication mechanisms (covered by separate security ADRs)
- GraphQL or REST API design for the application's own public API

**Exceptions:**
- EX-001: Legacy integrations that predate this ADR and are scheduled for deprecation within 6 months
- EX-002: Proof-of-concept or experimental integrations in feature branches not intended for production
</rule_activation>

### Rules

- **R-EXT-001** MUST: External API integrations MUST use Data Transfer Objects (DTOs) to represent external data structures and maintain clear boundaries between external formats and internal domain models. Each external entity type requires at least one corresponding DTO class.

- **R-EXT-002** MUST: Protocol-specific operations MUST be abstracted behind interface contracts (e.g., IDAVBackend) with at least one concrete implementation. Define backend interfaces before implementing concrete classes and use dependency injection to provide implementations to consumers.

- **R-EXT-003** MUST: Domain-specific exception types MUST be created for common API failure scenarios (permission, compliance, limits) in the appropriate domain namespace (e.g., app/Domains/Contact/DavClient/Services/Utils/Dav/) with descriptive names and error messages. These exceptions MUST be properly caught in controllers.

- **R-EXT-004** MUST: ViewHelper classes MUST be present in the Web layer for domains that expose external APIs and MUST be used in controller response preparation to separate presentation concerns from business logic.

- **R-EXT-005** SHOULD: API client classes SHOULD add the Loggable trait to ensure consistent logging of external API interactions for debugging and monitoring.

### Implementation Notes

- When creating new external API integrations, start by defining the DTO classes that represent the external data format, then create mappers to internal domain models
- Create domain-specific exception types with descriptive names and error messages
- Keep controllers thin and focused on HTTP concerns by using ViewHelper classes for API response preparation
- Implement automated mapping libraries (e.g., AutoMapper patterns) to reduce maintenance burden as external APIs evolve
- Review interface design during architecture review sessions when adding new integrations

### Verify

```bash
# Count DTO classes in DavClient implementations
grep -r "class.*Dto" app/Domains/*/DavClient/Services/Utils/Model/ | wc -l

# Count backend interface abstractions
grep -r "interface.*Backend" app/Domains/*/Dav/Web/Backend/ | wc -l

# Count domain-specific exception types for API failures
grep -r "class.*Exception extends" app/Domains/ | grep -E "(Permission|Compliant|Maximum)" | wc -l

# Count ViewHelper classes for API response preparation
find app/Domains -name "*ViewHelper.php" -type f | wc -l
```

**Accept when:**
- All external API integrations use DTO classes for data transfer with at least one DTO per external entity type
- Protocol-specific operations are abstracted behind interface contracts with at least one concrete implementation
- Domain-specific exception types exist for common API failure scenarios (permission, compliance, limits) and are properly caught in controllers
- ViewHelper classes are present for domains that expose external APIs and are used in controller response preparation

<enforcement>
Claude Code MUST NOT skip or defer verification. Pull requests that introduce external API integrations without proper DTO/interface patterns are blocked until refactored. Critical violations (missing permission checks, generic exceptions) require immediate remediation before deployment.

**Verification process:**
- Automated code review checks for new API integration code to verify presence of DTOs, interfaces, and exception types
- Architecture review sessions for new external API integrations to validate pattern compliance
- Static analysis tools configured to detect direct external API usage without DTO abstraction

**Exception process:**
- Developer submits exception request to Technical Lead with justification and impact analysis
- Technical Lead reviews request and either approves with conditions or requests pattern compliance
- Approved exceptions are documented in code with TODO comments linking to migration tickets
- Exception review occurs quarterly to assess whether exceptions can be resolved
</enforcement>
