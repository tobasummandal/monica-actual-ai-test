<rule_activation id="bed99b1b-21df-41f4-9ae1-2847b9d3750d" title="Adopt Domain-Driven Resource Modeling for Data Access Layer: Data Models Follow" applies_to="**/*">
These rules are ALWAYS ACTIVE for all data model and resource classes in the codebase.

**Context:** The application requires a consistent approach to modeling domain entities and their persistence layer representations. Multiple domain contexts (Contact, File management) need standardized data access patterns that align with domain boundaries.

**In Scope:**
- All Eloquent models representing persistent domain entities
- Resource classes for DAV protocol integration (VCard, VCalendar)
- Data transfer objects used for external API communication
- Domain-specific model classes within bounded contexts

**Out of Scope:**
- View models or presentation layer DTOs
- Temporary data structures used only within single methods
- Third-party library models or external package entities
- Database migration files and schema definitions
</rule_activation>

### Rules

- **R-DDM-001** MUST: Data models MUST follow a consistent naming convention that reflects their domain purpose (e.g., File.php for file entities, VCardResource.php for vCard protocol resources)
- **R-DDM-002** SHOULD: Place core domain models in `app/Models/` directory with clear, singular naming (e.g., File.php, User.php)
- **R-DDM-003** SHOULD: Organize domain-specific models and resources within `app/Domains/{DomainName}/` subdirectories to maintain bounded contexts
- **R-DDM-004** SHOULD: Create dedicated resource classes (e.g., VCardResource, VCalendarResource) for external protocol transformations in appropriate domain subdirectories
- **R-DDM-005** SHOULD: Use consistent method naming for resource transformations (e.g., toVCard(), fromVCard()) to establish predictable APIs
- **R-DDM-006** MUST: Separate domain models from protocol-specific resources to maintain single responsibility principle
- **R-DDM-007** MUST: Maintain clear separation between domain logic and data persistence concerns through dedicated resource and model classes

### Verify

```bash
# Count domain models in app/Models directory
find app/Models -name '*.php' -type f | wc -l

# Count resource classes in domain directories
grep -r 'class.*Resource' app/Domains/ --include='*.php' | wc -l

# Check for domain organization with DAV subdirectories
find app/Domains -type d -name 'Dav' | wc -l
```

**Accept when:**
- All domain entities have corresponding model classes in `app/Models/` or domain-specific directories
- External protocol integrations use dedicated resource classes separate from core models
- Domain organization follows consistent directory structure with clear bounded contexts
- Model naming consistently reflects domain purpose (singular, descriptive names)
- Resource classes are properly separated from domain models with clear transformation methods

<enforcement>
Claude Code MUST NOT skip or defer verification of domain model organization.

**Verified by:**
- Code review process checking for proper model organization and naming conventions
- Static analysis tools verifying model class locations match domain structure
- CI pipeline checks ensuring resource classes are properly separated from domain models

**Violation handling:**
- Pull requests with improperly organized models are flagged during code review
- Automated linting failures block merge until models are reorganized according to pattern
- Architecture review required for new domain contexts to ensure consistent application of pattern

**Exception process:**
- Exceptions must be documented in ADR amendments with clear justification
- Technical lead approval required for deviations from standard model organization
- Exception cases are tracked and reviewed quarterly to identify pattern improvements
</enforcement>

### Rationale

- Separation of domain models from protocol-specific resources demonstrates adherence to single responsibility principle
- Domain-driven organization suggests intentional bounded context implementation
- Pattern enables maintainability by providing clear locations for data-related logic
- Well-defined model boundaries facilitate testing through clear interfaces

### Risks and Mitigation

- **Risk:** Inconsistent application across different domains leading to architectural drift
  - *Mitigation:* Establish code review guidelines and automated linting rules
- **Risk:** Over-engineering simple entities with unnecessary abstraction layers
  - *Mitigation:* Document clear criteria for when to create separate resource classes
- **Risk:** Tight coupling between domain models and ORM framework (Eloquent)
  - *Mitigation:* Consider repository interfaces if framework independence becomes required
