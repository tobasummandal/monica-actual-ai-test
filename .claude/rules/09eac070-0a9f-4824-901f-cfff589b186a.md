<rule_activation id="09eac070-0a9f-4824-901f-cfff589b186a" title="Adopt Laravel Fortify for Authentication Action Standardization: Feature Tests Authentication" applies_to="app/Actions/Fortify/**/*.php,app/Domains/*/Services/*.php,tests/Feature/**/*.php">
These rules are ALWAYS ACTIVE for all authentication-related files including Fortify actions, domain services, and feature tests.

**Context:** Laravel Fortify provides headless authentication backend enabling consistent behavior across web and API interfaces. Authentication operations span multiple bounded contexts requiring unified approach to password validation and user state management.

**In Scope:**
- All password management operations (reset, update, validation)
- User account lifecycle operations (creation, cancellation, invitation acceptance)
- Authentication action classes in app/Actions/Fortify
- Domain service classes handling user management in app/Domains/Settings
- Feature tests validating authentication behavior

**Out of Scope:**
- Frontend authentication UI components
- Session management and cookie handling
- OAuth and social authentication providers
- Authorization and permission logic
- API token generation and management
</rule_activation>

### Rules

- **R-FORTIFY-001** SHOULD: Feature tests for authentication operations SHOULD verify behavior independently of presentation layer to ensure deployment target flexibility.

- **R-FORTIFY-002** MUST: Authentication action classes in app/Actions/Fortify MUST extend appropriate Fortify contracts and be registered in FortifyServiceProvider.

- **R-FORTIFY-003** SHOULD: Domain-specific user management services SHOULD be placed in app/Domains/{DomainName}/Services and follow single-responsibility principle, handling one user lifecycle operation per service.

- **R-FORTIFY-004** MUST: Password operations MUST use Laravel's Hash facade consistently across all authentication touchpoints (never hash passwords directly).

- **R-FORTIFY-005** MUST: Password validation MUST use Laravel's validation rules (min:8, confirmed, etc.) consistently across all authentication actions.

- **R-FORTIFY-006** MUST: Feature tests MUST use Laravel's authentication testing helpers (actingAs, assertAuthenticated) and test both success and failure scenarios.

- **R-FORTIFY-007** SHOULD: Clear separation SHOULD be maintained between Fortify actions (framework-level authentication) and domain services (business-specific user management).

### Verify

```bash
# Count Fortify action classes that properly extend Fortify contracts
grep -r "extends.*Fortify" app/Actions/Fortify/ | wc -l

# Count domain service classes in proper location
find app/Domains -name "*Service.php" -path "*/Services/*" | wc -l

# Verify consistent use of Hash facade
grep -r "use Illuminate\\Support\\Facades\\Hash" app/Actions/Fortify app/Domains/Settings | wc -l

# Run authentication feature tests
php artisan test --filter=Auth --filter=Password --filter=Account
```

**Accept when:**
- All authentication actions in app/Actions/Fortify extend appropriate Fortify contracts and are registered in FortifyServiceProvider
- Domain-specific user management services exist in app/Domains/*/Services and delegate to Fortify actions for password operations
- Feature tests for authentication operations pass and cover both web and API scenarios without presentation layer dependencies
- Password validation uses Laravel Hash facade consistently across all authentication touchpoints

### Implementation Guidelines

**Creating Fortify Action Classes:**
- Extend appropriate Fortify contracts (ResetUserPassword, UpdateUserPassword)
- Register actions in FortifyServiceProvider
- Use Laravel's validation rules for password requirements

**Domain Services Pattern:**
- Place services in app/Domains/{DomainName}/Services
- Follow single-responsibility principle
- Delegate password operations to Fortify actions

**Testing Approach:**
- Test authentication behavior independent of deployment target
- Use Laravel's authentication testing helpers
- Cover both success and failure scenarios
- Test web and API scenarios without presentation layer dependencies

**Consequences:**
- ✅ Authentication logic can be deployed to multiple targets (web, API, mobile) without modification
- ✅ Clear separation enables independent evolution of frontend and backend
- ✅ Standardized password handling ensures consistent security posture
- ⚠️ Additional abstraction layer increases initial complexity
- ⚠️ Requires clear documentation about when to use Fortify actions vs domain services
