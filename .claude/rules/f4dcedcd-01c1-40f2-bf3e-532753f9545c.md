### Context

The application implements a domain-driven architecture for journal management with:
- ManageJournals subdomain containing 25+ files following consistent patterns
- Controllers delegating to Services for business operations
- Support for complex operations: posts, metrics, photos, tags, slices of life, contact associations
- Clear namespace boundaries: Web, Services, and other concerns

**In scope:**
- All journal management operations (posts, metrics, photos, tags, slices of life, contacts)
- Business logic requiring database transactions or multiple model interactions
- Operations enforcing domain-specific business rules and validation
- Functionality within the Vault domain's ManageJournals subdomain

**Out of scope:**
- Simple CRUD operations involving only single-model persistence without business logic
- HTTP request/response handling and view rendering (belongs in controllers)
- Cross-domain operations spanning multiple bounded contexts
- Infrastructure concerns (caching, logging, external API integration)

### Rules

- **R-DDSL-001** MUST: Domain operations MUST be organized by subdomain (ManageJournals) with clear namespace boundaries separating Web, Services, and other concerns
- **R-DDSL-002** MUST: Controllers MUST delegate to services rather than implementing business logic directly. Controllers should only validate input, call services, and return responses
- **R-DDSL-003** MUST: Service classes MUST implement single-responsibility operations focused on specific business capabilities
- **R-DDSL-004** SHOULD: Use verb-noun naming for service classes (e.g., CreatePost, UpdateMetric, RemoveTag) to clearly communicate intent
- **R-DDSL-005** SHOULD: Services should accept primitive types or DTOs as parameters rather than HTTP request objects to maintain independence from web layer
- **R-DDSL-006** SHOULD: Use dependency injection for service dependencies to improve testability and enable mocking
- **R-DDSL-007** MAY: Group related services in subdirectories when a domain grows large (e.g., ManageJournals/Services/Posts, ManageJournals/Services/Metrics)

### Verify

```bash
# Count service files in domain structure
find app/Domains/*/Services -type f -name '*.php' | wc -l

# Verify controllers exist in proper location
grep -r 'class.*Controller' app/Domains/Vault/ManageJournals/Web/Controllers | wc -l

# Check service namespace organization
grep -r 'namespace.*Services' app/Domains/Vault/ManageJournals/Services | head -5
```

**Accept when:**
- Service classes exist in dedicated Services directories within domain boundaries
- Controllers delegate to services rather than implementing business logic directly
- Service class names follow verb-noun convention and implement single-responsibility operations
- Clear namespace separation exists between Web (controllers) and Services (business logic)

### Risks & Mitigation

**Risk:** Service layer becomes anemic with simple pass-through to models
- **Mitigation:** Ensure services encapsulate meaningful business logic, validation, or orchestration
- **Owner:** Engineering team and architecture reviewers

**Risk:** Inconsistent application across different domains
- **Mitigation:** Document pattern in architecture guidelines, provide examples and templates
- **Owner:** Architecture team

**Risk:** Performance overhead from additional abstraction layers
- **Mitigation:** Profile critical paths, optimize service composition, consider caching at boundaries
- **Owner:** Engineering team and performance engineers
