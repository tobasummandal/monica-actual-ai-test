<rule_activation id="e91301f7-fcbc-4ffc-8527-1ad9bb6d6235" title="Adopt Laravel Migrations as Standard Database Schema Management: Migration Files Use" applies_to="**/*">
These rules are ALWAYS ACTIVE for all database schema changes across the application. All schema modifications MUST be implemented through Laravel migration files.
</rule_activation>

### Rules

- **R-LM-001** MUST: Migration files MUST use Laravel's Schema Builder API (Schema::create, Schema::table, etc.) rather than raw SQL for database-agnostic operations.
- **R-LM-002** MUST: All table creation, modification, and deletion operations MUST be implemented through Laravel migration files.
- **R-LM-003** MUST: Column additions, modifications, and removals MUST be performed using Schema Builder methods in migration files.
- **R-LM-004** MUST: Index creation and removal MUST be defined in Laravel migration files.
- **R-LM-005** MUST: Foreign key constraint definitions MUST be implemented through Laravel migration files.
- **R-LM-006** MUST: Migration files MUST follow Laravel's timestamp-based naming convention (YYYY_MM_DD_HHMMSS_description.php).
- **R-LM-007** MUST: Each migration file MUST contain both up() and down() methods to support rollback capability.
- **R-LM-008** MUST: Use 'php artisan make:migration' command to generate new migration files with proper timestamp and structure.
- **R-LM-009** SHOULD: Use Laravel's migration methods like 'foreignId()', 'timestamps()', 'softDeletes()' for consistency with framework conventions.
- **R-LM-010** SHOULD: For complex data transformations, consider separating schema changes from data migrations into distinct migration files.

**In scope:**
- All table creation, modification, and deletion operations
- Column additions, modifications, and removals
- Index creation and removal
- Foreign key constraint definitions
- Database-level configuration changes that affect schema structure

**Out of scope:**
- Application data seeding for testing purposes (use database/seeders instead)
- Data migration or transformation scripts that don't modify schema structure
- Database performance tuning that doesn't affect schema (query optimization, connection pooling)
- Backup and restore operations

**Exceptions:**
- EXC-001: Emergency production hotfix requiring immediate schema change to resolve critical outage
- EXC-002: Database-specific optimizations requiring raw SQL that cannot be expressed through Schema Builder

### Verify

```bash
# Check migration files exist and count them
find database/migrations -name '*.php' -type f | wc -l | grep -E '^[0-9]+$'

# Verify Schema Builder API usage
grep -r 'Schema::create\|Schema::table\|Schema::drop' database/migrations/ | wc -l

# Check migration status
php artisan migrate:status 2>&1 | grep -E 'Ran|Pending'

# Verify migration files have both up() and down() methods
ls database/migrations/*.php 2>/dev/null | head -5 | xargs grep -l 'function up()' | xargs grep -l 'function down()'
```

**Accept when:**
- All migration files exist in database/migrations directory and follow Laravel naming convention with timestamps
- Each migration file contains both up() and down() methods using Schema Builder API
- Migration status command executes successfully showing tracked migrations
- No direct SQL schema modifications are found in application code outside migration files
