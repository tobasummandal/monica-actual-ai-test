<rule_activation id="21e15460-7aab-480f-a25d-1574be832927" title="Adopt Domain-Driven Resource Modeling for Data Access Layer: Models Implement Additional" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching domain models, resources, and data access layer implementations.
</rule_activation>

### Rules

- **R-DDD-001** MAY: Models MAY implement additional interfaces or traits to support cross-cutting concerns like auditing, soft deletes, or timestamps

### Verify

```bash
# Count Eloquent models in app/Models directory
find app/Models -name '*.php' -type f | wc -l

# Count resource classes in domain-specific directories
grep -r 'class.*Resource' app/Domains/ --include='*.php' | wc -l

# Count DAV domain subdirectories
find app/Domains -type d -name 'Dav' | wc -l
```

**Accept when:**
- All domain entities have corresponding model classes in `app/Models/` or domain-specific directories
- External protocol integrations use dedicated resource classes separate from core models
- Domain organization follows consistent directory structure with clear bounded contexts
- Models are placed in `app/Models/` with clear, singular naming (e.g., `File.php`, `User.php`)
- Domain-specific models and resources are organized within `app/Domains/{DomainName}/` subdirectories
- Resource classes for external protocols (e.g., `VCardResource`, `VCalendarResource`) are in appropriate domain subdirectories
- Resource transformation methods use consistent naming (e.g., `toVCard()`, `fromVCard()`)

<enforcement>
Claude Code MUST verify model organization and resource class separation during code review. Violations flagged during static analysis or CI pipeline checks MUST be resolved before merge. Architecture review is required for new domain contexts to ensure consistent application of this pattern.
</enforcement>
