<rule_activation id="e8db1dff-0699-4788-9314-f5b96fea88a7" title="Adopt Modular Architecture with Factory-Based Component Generation: Domain Modules Organized" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in the codebase. They enforce a modular architecture with factory-based component generation and domain-driven organization.
</rule_activation>

### Rules

- **R-DDD-001** MUST: All domain modules MUST be organized under a clear namespace hierarchy following the pattern `app/Domains/{Domain}/{Subdomain}/{Layer}`.
- **R-DDD-002** MUST: All factory classes in `database/factories` MUST extend the framework's base Factory class.
- **R-DDD-003** MUST: All setup commands in `app/Console/Commands` MUST extend the framework's Command class and follow `Setup*.php` naming conventions.
- **R-DDD-004** SHOULD: Domain names should be singular nouns (Contact, not Contacts), subdomain names should describe the capability (ManageContact), layer names should be standard (Web, Console, Database).
- **R-DDD-005** SHOULD: Use code generation tools or IDE templates to scaffold new modules with correct directory structure, namespace, and boilerplate factory/command classes.
- **R-DDD-006** SHOULD: Document module dependencies in a central registry or dependency graph to prevent circular dependencies and clarify initialization order.

### In Scope

- All application modules and domain components
- Database factories for test data generation and seeding
- Console commands for setup, initialization, and maintenance
- View helpers and presentation layer components
- Scheduled task definitions and cron job management

### Out of Scope

- Third-party vendor packages and external libraries
- Framework core files and base classes
- Configuration files and environment-specific settings
- Static assets and frontend build artifacts

### Exceptions

- **EX-001**: Legacy modules predating this ADR that require significant refactoring effort
- **EX-002**: Rapid prototyping or proof-of-concept code in designated experimental branches

### Verify

```bash
# Verify all PHP files in app/Domains use correct namespace hierarchy
find app/Domains -type f -name '*.php' | xargs grep -L 'namespace App\\Domains' | wc -l | grep -q '^0$'

# Verify all factory classes extend the base Factory class
find database/factories -type f -name '*Factory.php' | xargs grep -c 'extends Factory' | grep -v ':0'

# Verify all setup commands extend the Command class
find app/Console/Commands -type f -name 'Setup*.php' | xargs grep -c 'extends Command' | grep -v ':0'
```

**Accept when:**
- All PHP files in `app/Domains` directory use the correct `App\Domains` namespace hierarchy
- All factory classes in `database/factories` extend the framework's base Factory class
- All setup commands in `app/Console/Commands` extend the framework's Command class and follow naming conventions

<enforcement>
Claude Code MUST NOT skip or defer verification. All changes affecting domain modules, factories, or setup commands MUST be verified against these rules before completion.

**Violation handling:**
- CI pipeline fails if namespace conventions are violated, blocking merge
- Code review approval withheld until module structure compliance is achieved
- Technical debt tickets created for legacy code violations with prioritized remediation plan

**Exception process:**
- Developer submits exception request to Technical Lead with justification and impact analysis
- Technical Lead reviews with Architecture Review Board if exception affects multiple modules
- Approved exceptions documented in ADR exceptions log with expiration date and migration plan
</enforcement>
