<rule_activation id="c55d7160-bcb3-4435-b28e-dc312f0cccc8" title="Use Laravel Hash Facade for Password Credential Storage: Applications Implement Automatic" applies_to="**/*.php">
These rules are ALWAYS ACTIVE for all PHP files handling password credential storage, including account creation, user invitations, password resets, and authentication flows.
</rule_activation>

### Rules

- **R-LHASH-001** MUST: Use `Hash::make($password)` when storing passwords, typically in service classes like CreateAccount, AcceptInvitation, ResetUserPassword, or UpdateUserPassword.
- **R-LHASH-002** MUST: Use `Hash::check($plaintext, $hashedValue)` for password verification during authentication.
- **R-LHASH-003** MUST NOT: Use PHP's native `password_hash()` or `password_verify()` functions directly in application code.
- **R-LHASH-004** MUST NOT: Store or assign passwords in plain text (e.g., `'password' => $password` without hashing).
- **R-LHASH-005** SHOULD: Use `Hash::fake()` in tests to avoid expensive hashing operations and speed up test execution.
- **R-LHASH-006** SHOULD: Configure `config/hashing.php` with appropriate algorithm (bcrypt or argon2id) and work factor.
- **R-LHASH-007** MAY: Applications MAY implement automatic password rehashing on login if the configured algorithm or work factor changes.

### In Scope

- All user account creation workflows
- Password reset and recovery flows
- Password update and change operations
- User invitation acceptance with password setting
- Any authentication action that stores or verifies passwords

### Out of Scope

- API token generation and storage (uses different hashing strategy)
- OAuth provider tokens (managed by external providers)
- Session identifiers (use different security mechanisms)
- Remember me tokens (may use different hashing approach)
- Password reset tokens (temporary, different security model)

### Exceptions

- **EXC-001**: Testing environments require deterministic password hashes for fixture data
- **EXC-002**: Migration from legacy system requires temporary dual-hash verification

### Verify

```bash
# Count Hash::make usage in application code
grep -r "Hash::make" app/ --include="*.php" | wc -l

# Check for direct password_hash usage (should be none)
grep -r "password_hash" app/ --include="*.php" || echo "No direct password_hash usage found (good)"

# Check for plain-text password assignments (should be none)
grep -r "'password'.*=>.*\$" app/ --include="*.php" | grep -v "Hash::make" | grep -v "bcrypt" || echo "No plain-text password assignments found (good)"

# Verify hashing driver configuration
php artisan tinker --execute="echo config('hashing.driver');"
```

**Accept when:**

- All password storage operations use `Hash::make()` as verified by grep showing consistent usage across authentication files
- No direct `password_hash()` calls found in application code (framework usage only)
- Hash facade configuration is properly set in `config/hashing.php` with bcrypt or argon2id driver
- Test suite includes verification that passwords are hashed before database storage
- No plain-text password assignments detected in codebase
