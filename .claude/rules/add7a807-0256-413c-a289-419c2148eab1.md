<rule_activation id="add7a807-0256-413c-a289-419c2148eab1" title="Standardize Exception and Logging Formatting for External API Responses: Exception Formatters Include" applies_to="**/*">
These rules are ALWAYS ACTIVE for all external API endpoints and exception handling components. All new exception classes and logging utilities MUST comply with the formatting standards defined herein.

In scope:
- All custom exception classes that can be thrown from external API endpoints
- Logging utilities and traits used within API request/response lifecycle
- Error response middleware and exception handlers for public APIs
- API documentation and OpenAPI specifications describing error formats

Out of scope:
- Internal service-to-service communication errors (may use different formats)
- CLI command error output formatting
- Background job failure handling (unless exposed via API)
- Development/debug mode error pages (may include additional details)

Exceptions:
- EXC-001: Legacy API versions (v1, v2) that have established error formats with existing client dependencies
- EXC-002: Third-party library exceptions that cannot be wrapped without significant performance impact
</rule_activation>

### Rules

- **R-EFI-001** MUST: All new exception classes and logging utilities MUST comply with the formatting standards defined in this ADR.
- **R-EFI-002** MUST: All API exceptions MUST implement a base Formattable interface or trait defining methods like toArray(), toJson(), and getHttpStatusCode().
- **R-EFI-003** MUST: All exception classes in app/Exceptions/ that are thrown from API routes MUST implement the Formattable interface or equivalent formatter trait.
- **R-EFI-004** MUST: Exception responses MUST match the documented JSON schema with required fields (code, message, status, timestamp).
- **R-EFI-005** MUST: Establish a standard error response schema (e.g., {error: {code, message, status, timestamp, context}}) and document it in OpenAPI specifications.
- **R-EFI-006** SHOULD: Exception formatters SHOULD include contextual metadata (e.g., resource IDs, user context) when available without exposing sensitive information.
- **R-EFI-007** MUST: The Loggable trait MUST use the same formatting methods as exceptions, ensuring logs and API responses are structurally consistent.
- **R-EFI-008** MUST: Formatter implementations MUST undergo security review to ensure no sensitive information is inadvertently exposed.

### Verify

```bash
# Verify exception classes implement formatter interface
grep -r "class.*Exception" app/ | xargs -I {} sh -c 'grep -l "Formattable\|toArray\|toJson" {}'

# Run exception formatter tests
php artisan test --filter ExceptionFormatterTest

# Verify Loggable trait usage includes formatter methods
grep -r "use.*Loggable" app/ | xargs -I {} sh -c 'grep -l "format\|toArray" {}'
```

**Accept when:**
- All exception classes in app/Exceptions/ that are thrown from API routes implement the Formattable interface or equivalent formatter trait
- Automated tests verify that exception responses match the documented JSON schema with required fields (code, message, status, timestamp)
- The Loggable trait and all exception formatters produce structurally consistent output as verified by integration tests
- Static analysis tools (PHPStan/Psalm) are configured to require Formattable interface on exception classes and pass validation
- API contract tests validate error response structures against documented schema

<enforcement>
Claude Code MUST NOT skip or defer verification. All exception classes and logging utilities MUST be validated against formatter requirements before considering the implementation complete.

Verification is performed by:
- Automated CI pipeline tests that validate exception response formats against JSON schema
- Static analysis tools (PHPStan/Psalm) configured to require Formattable interface on exception classes
- Code review checklist requiring verification of formatter implementation for new exceptions
- API contract tests that validate error response structures

Violation handling:
- CI pipeline fails if exception classes lack required formatter interface
- Code review blocks merge if new exceptions don't follow formatting standards
- Runtime monitoring alerts on non-standard error responses in production
- Quarterly audits identify and remediate non-compliant exception classes
</enforcement>
