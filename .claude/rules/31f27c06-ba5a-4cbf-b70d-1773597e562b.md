These rules are ALWAYS ACTIVE for authentication-related files including Fortify actions, domain services, and authentication feature tests.
</rule_activation>

## Context

Laravel Fortify provides a headless authentication backend that separates authentication logic from presentation concerns. This ADR establishes patterns for implementing authentication operations across multiple domains while maintaining deployment flexibility for web, API, and mobile interfaces.

**In scope:**
- All password management operations (reset, update, validation)
- User account lifecycle operations (creation, cancellation, invitation acceptance)
- Authentication action classes in app/Actions/Fortify
- Domain service classes handling user management in app/Domains/Settings
- Feature tests validating authentication behavior

**Out of scope:**
- Frontend authentication UI components
- Session management and cookie handling
- OAuth and social authentication providers
- Authorization and permission logic
- API token generation and management

### Rules

- **R-AUTH-001** MUST: All authentication actions (password reset, password update, user creation) MUST be implemented as Laravel Fortify action classes in the app/Actions/Fortify namespace.

- **R-AUTH-002** MUST: Fortify action classes MUST extend the appropriate Fortify contracts (ResetUserPassword, UpdateUserPassword) and be registered in FortifyServiceProvider.

- **R-AUTH-003** MUST: Domain-specific user management services MUST be placed in app/Domains/{DomainName}/Services and follow single-responsibility principle, handling one user lifecycle operation per service.

- **R-AUTH-004** MUST: Password validation MUST use Laravel Hash facade consistently across all authentication touchpoints.

- **R-AUTH-005** MUST: Password requirements MUST use Laravel's validation rules (min:8, confirmed, etc.) consistently across all authentication actions.

- **R-AUTH-006** SHOULD: Domain services SHOULD delegate to Fortify actions for password operations rather than implementing password logic directly.

- **R-AUTH-007** MUST: Feature tests for authentication operations MUST use Laravel's authentication testing helpers (actingAs, assertAuthenticated) and test both success and failure scenarios.

- **R-AUTH-008** MUST: Feature tests MUST cover both web and API scenarios without presentation layer dependencies.

### Verify

```bash
# Count Fortify action classes extending Fortify contracts
grep -r "extends.*Fortify" app/Actions/Fortify/ | wc -l

# Count domain service classes in proper location
find app/Domains -name "*Service.php" -path "*/Services/*" | wc -l

# Verify consistent use of Hash facade
grep -r "use Illuminate\\Support\\Facades\\Hash" app/Actions/Fortify app/Domains/Settings | wc -l

# Run authentication-related tests
php artisan test --filter=Auth --filter=Password --filter=Account
```

**Accept when:**
- All authentication actions in app/Actions/Fortify extend appropriate Fortify contracts and are registered in FortifyServiceProvider
- Domain-specific user management services exist in app/Domains/*/Services and delegate to Fortify actions for password operations
- Feature tests for authentication operations pass and cover both web and API scenarios without presentation layer dependencies
- Password validation uses Laravel Hash facade consistently across all authentication touchpoints

<enforcement>
Verification is mandatory. Claude Code MUST:
- Run verification commands before marking authentication work as complete
- Ensure all authentication actions follow the Fortify pattern
- Validate that domain services properly delegate to Fortify actions
- Confirm feature tests cover both success and failure scenarios
- Flag any direct password hashing without Hash facade

Violations require:
- CI pipeline approval override for emergency deployments
- Architecture team review for new authentication features
- Documented exception with time-limited approval (6-12 months)
- Quarterly audit review and migration plan for non-compliant code
</enforcement>

## Implementation Notes

- Document the decision boundary between Fortify actions (framework-level authentication) and domain services (business-specific user management) in team guidelines
- Clear separation between authentication mechanics and presentation layer enables independent evolution of frontend and backend components
- Standardized password handling through Laravel's Hash facade ensures consistent security posture across all deployment environments

## Risks and Mitigations

- **Risk**: Inconsistent application of the pattern across teams
  - **Mitigation**: Establish clear architectural guidelines, provide code examples and templates, implement automated linting
  
- **Risk**: Fortify framework updates may introduce breaking changes
  - **Mitigation**: Pin Fortify version in composer.json, establish comprehensive test coverage, review changelogs before upgrading
  
- **Risk**: Performance overhead from additional abstraction layers
  - **Mitigation**: Implement caching strategies for user lookups, monitor authentication endpoint performance, optimize database queries
