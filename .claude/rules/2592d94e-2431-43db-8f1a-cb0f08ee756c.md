<rule_activation id="2592d94e-2431-43db-8f1a-cb0f08ee756c" title="Use Laravel Hash Facade for Password Credential Storage: Password Hashing Operations" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching `**/*`.

This ADR establishes Laravel's Hash facade as the standard for password credential storage across all authentication workflows including account creation, user invitations, password resets, and password updates.

**In scope:**
- All user account creation workflows
- Password reset and recovery flows
- Password update and change operations
- User invitation acceptance with password setting
- Any authentication action that stores or verifies passwords

**Out of scope:**
- API token generation and storage (uses different hashing strategy)
- OAuth provider tokens (managed by external providers)
- Session identifiers (use different security mechanisms)
- Remember me tokens (may use different hashing approach)
- Password reset tokens (temporary, different security model)

**Exceptions:**
- EXC-001: Testing environments require deterministic password hashes for fixture data
- EXC-002: Migration from legacy system requires temporary dual-hash verification
</rule_activation>

### Rules

- **R-HASH-001** SHOULD: Password hashing operations SHOULD be performed immediately before database persistence to minimize plain-text exposure in memory
- **R-HASH-002** MUST: Always use `Hash::make($password)` when storing passwords, typically in service classes like CreateAccount or AcceptInvitation
- **R-HASH-003** MUST: Use `Hash::check($plaintext, $hashedValue)` for password verification during authentication
- **R-HASH-004** SHOULD: In tests, use `Hash::fake()` to avoid expensive hashing operations and speed up test execution
- **R-HASH-005** MUST: Do not use PHP's native `password_hash()` or `password_verify()` functions directly; use Laravel's Hash facade instead
- **R-HASH-006** MUST: Do not bypass the Hash facade with custom password hashing implementations
- **R-HASH-007** MUST: Do not log or expose hashed passwords in application logs or error messages

### Verify

```bash
# Count Hash::make usage in application code
grep -r "Hash::make" app/ --include="*.php" | wc -l

# Verify no direct password_hash usage (should find none in app code)
grep -r "password_hash" app/ --include="*.php" || echo "No direct password_hash usage found (good)"

# Check for plain-text password assignments (should find none)
grep -r "'password'.*=>.*\$" app/ --include="*.php" | grep -v "Hash::make" | grep -v "bcrypt" || echo "No plain-text password assignments found (good)"

# Verify hashing driver configuration
php artisan tinker --execute="echo config('hashing.driver');"
```

**Accept when:**
- All password storage operations use `Hash::make()` as verified by grep showing consistent usage across authentication files
- No direct `password_hash()` calls found in application code (framework usage only)
- Hash facade configuration is properly set in `config/hashing.php` with bcrypt or argon2id driver
- Test suite includes verification that passwords are hashed before database storage

<enforcement>
Claude Code MUST verify Hash facade usage when modifying authentication code. CI pipeline MUST fail if plain-text password storage patterns are detected. Pull requests MUST be blocked until Hash facade usage is corrected. Security team notification is REQUIRED for violations in production code.

Exception process: Developer submits exception request with technical justification to security team. Security team reviews and approves/rejects within 2 business days. Approved exceptions documented in ADR exceptions section with sunset date. Exceptions reviewed quarterly.
</enforcement>
