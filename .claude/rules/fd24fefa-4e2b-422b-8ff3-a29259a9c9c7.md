<rule_activation id="fd24fefa-4e2b-422b-8ff3-a29259a9c9c7" title="Adopt Domain-Driven Resource Modeling for Data Access Layer: Resource Transformation Logic" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files. This ADR establishes domain-driven resource modeling patterns for data access layers, requiring separation between domain models and external protocol representations.

**In scope:**
- All Eloquent models representing persistent domain entities
- Resource classes for DAV protocol integration (VCard, VCalendar)
- Data transfer objects used for external API communication
- Domain-specific model classes within bounded contexts

**Out of scope:**
- View models or presentation layer DTOs
- Temporary data structures used only within single methods
- Third-party library models or external package entities
- Database migration files and schema definitions
</rule_activation>

### Rules

- **R-DRM-001** SHOULD: Resource transformation logic (converting between domain models and external formats) SHOULD be encapsulated within dedicated resource classes.
- **R-DRM-002** SHOULD: Core domain models SHOULD be placed in `app/Models/` directory with clear, singular naming (e.g., `File.php`, `User.php`).
- **R-DRM-003** SHOULD: Domain-specific models and resources SHOULD be organized within `app/Domains/{DomainName}/` subdirectories to maintain bounded contexts.
- **R-DRM-004** SHOULD: Dedicated resource classes (e.g., `VCardResource`, `VCalendarResource`) for external protocol transformations SHOULD be created in appropriate domain subdirectories.
- **R-DRM-005** SHOULD: Resource transformation methods SHOULD use consistent naming conventions (e.g., `toVCard()`, `fromVCard()`) to establish predictable APIs.

### Verify

```bash
# Count domain models in app/Models
find app/Models -name '*.php' -type f | wc -l

# Count resource classes in domains
grep -r 'class.*Resource' app/Domains/ --include='*.php' | wc -l

# Count domain directories with DAV integration
find app/Domains -type d -name 'Dav' | wc -l
```

**Accept when:**
- All domain entities have corresponding model classes in `app/Models/` or domain-specific directories
- External protocol integrations use dedicated resource classes separate from core models
- Domain organization follows consistent directory structure with clear bounded contexts

<enforcement>
Verification is MANDATORY. Code review and static analysis MUST enforce proper model organization and resource class separation according to these rules. Pull requests with improperly organized models MUST be flagged, and automated linting failures MUST block merge until models are reorganized.
</enforcement>
