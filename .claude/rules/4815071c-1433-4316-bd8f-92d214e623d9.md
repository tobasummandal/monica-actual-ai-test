<rule_activation id="4815071c-1433-4316-bd8f-92d214e623d9" title="Adopt Domain-Driven Module Boundaries with External API Integration Layers: Viewhelper Classes Providing" applies_to="**/*">
These rules are ALWAYS ACTIVE for all external API integration implementations and domain boundary definitions within the codebase.
</rule_activation>

### Rules

- **R-DDD-001** MUST: ViewHelper classes providing external API functionality MUST reside in Web/ViewHelpers directories within their respective domain modules.

### Verify

```bash
# Verify backend interfaces exist for external protocol implementations
find app/Domains -type f -name '*Client*' -o -name '*Backend*' | xargs grep -l 'interface\|implements' | wc -l

# Verify DTO classes exist in Utils/Model subdirectories
find app/Domains -path '*/Services/Utils/Model/*Dto.php' | wc -l

# Verify no direct external protocol library usage in core domain logic
grep -r 'use.*\\Dav\\' app/Domains --include='*.php' | grep -v 'DavClient\|Dav/' | wc -l
```

**Accept when:**
- All external API integration modules follow the domain-based directory structure with dedicated Services and Utils/Model subdirectories
- Backend interfaces exist for all external protocol implementations and are used via dependency injection
- No direct external protocol library usage is found in core domain entity or business logic classes (grep verification returns 0 violations)
- All data exchange with external APIs uses dedicated DTO classes rather than direct domain entity serialization
- ViewHelper classes are located in Web/ViewHelpers directories within their respective domain modules

<enforcement>
Claude Code MUST NOT skip or defer verification. Violations detected by automated CI pipeline checks using grep and find commands MUST block merge requests. Code review MUST enforce the established module structure for all new external API integrations.
</enforcement>
