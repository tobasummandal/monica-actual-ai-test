<rule_activation id="4815071c-1433-4316-bd8f-92d214e623d9" title="Adopt Domain-Driven Module Boundaries with External API Integration Layers: Viewhelper Classes Providing" applies_to="**/*">
These rules are ALWAYS ACTIVE for all external API integration implementations and domain boundary definitions within the codebase.
</rule_activation>

### Rules

- **R-API-001** MUST: ViewHelper classes providing external API functionality MUST reside in Web/ViewHelpers directories within their respective domain modules
- **R-API-002** MUST: External API integration modules MUST follow domain-based directory structure with dedicated Services and Utils/Model subdirectories
- **R-API-003** MUST: Backend interfaces MUST exist for all external protocol implementations and be used via dependency injection
- **R-API-004** MUST: Core domain entity or business logic classes MUST NOT contain direct external protocol library usage
- **R-API-005** MUST: All data exchange with external APIs MUST use dedicated DTO classes rather than direct domain entity serialization
- **R-API-006** SHOULD: Define backend interface contracts before implementing concrete clients to ensure testability
- **R-API-007** SHOULD: Create DTOs that match external API schemas closely, using separate mapper classes to transform between DTOs and domain entities
- **R-API-008** SHOULD: Document external API version and protocol specifications in the integration module README

**In scope:**
- All external API integrations including REST, SOAP, WebDAV, CardDAV, and other protocol-based communications
- Third-party service integrations that require protocol-specific client implementations
- Data import/export operations involving external standards or formats
- Public API endpoints that expose domain functionality to external consumers

**Out of scope:**
- Internal service-to-service communication within the same application boundary
- Database access layers and repository patterns
- Framework-level HTTP routing and middleware
- Authentication and authorization mechanisms (unless specific to external API integration)

**Exceptions:**
- EXC-001: Legacy integrations predating this ADR that require significant refactoring effort
- EXC-002: Proof-of-concept or experimental integrations in non-production environments

### Verify

```bash
# Verify backend interfaces and implementations exist
find app/Domains -type f -name '*Client*' -o -name '*Backend*' | xargs grep -l 'interface\|implements' | wc -l

# Verify DTO classes exist in proper structure
find app/Domains -path '*/Services/Utils/Model/*Dto.php' | wc -l

# Verify no direct external protocol usage in core domain classes (should return 0)
grep -r 'use.*\\Dav\\' app/Domains --include='*.php' | grep -v 'DavClient\|Dav/' | wc -l
```

**Accept when:**
- All external API integration modules follow the domain-based directory structure with dedicated Services and Utils/Model subdirectories
- Backend interfaces exist for all external protocol implementations and are used via dependency injection
- No direct external protocol library usage is found in core domain entity or business logic classes (grep verification returns 0 violations)
- All data exchange with external APIs uses dedicated DTO classes rather than direct domain entity serialization
- ViewHelper classes providing external API functionality reside in Web/ViewHelpers directories within their respective domain modules

<enforcement>
Claude Code MUST verify compliance with these rules when creating or modifying external API integrations. Verification commands MUST be executed to ensure no direct protocol coupling exists in core domain classes. Exception requests must be submitted to architecture review board with justification.
</enforcement>
