<rule_activation id="fc7035be-3bfa-4709-9784-577246ebc142" title="Adopt Domain-Driven Service Layer Pattern for Journal Management: Web Controllers Managejournals" applies_to="app/Domains/Vault/ManageJournals/**/*">
These rules are ALWAYS ACTIVE for all files in the ManageJournals domain.

**Context:** The application implements a domain-driven architecture with clear separation between web controllers and business logic services. Journal management functionality is organized into dedicated service classes that encapsulate single-responsibility operations.

**In scope:**
- All journal management operations including posts, metrics, photos, tags, slices of life, and contacts
- Business logic that requires database transactions or multiple model interactions
- Operations that enforce domain-specific business rules and validation
- Functionality within the Vault domain's ManageJournals subdomain

**Out of scope:**
- Simple CRUD operations that only involve single-model persistence without business logic
- HTTP request/response handling and view rendering (belongs in controllers)
- Cross-domain operations that span multiple bounded contexts
- Infrastructure concerns like caching, logging, and external API integration
</rule_activation>

### Rules

- **R-DSL-001** MUST: Web controllers in the ManageJournals/Web/Controllers directory MUST delegate business logic to service classes rather than implementing logic directly.
- **R-DSL-002** SHOULD: Use verb-noun naming for service classes (e.g., CreatePost, UpdateMetric, RemoveTag) to clearly communicate intent.
- **R-DSL-003** MUST: Keep controllers thin - they should validate input, call services, and return responses without implementing business logic.
- **R-DSL-004** SHOULD: Services should accept primitive types or DTOs as parameters rather than HTTP request objects to maintain independence from web layer.
- **R-DSL-005** SHOULD: Consider using dependency injection for service dependencies to improve testability and enable mocking.
- **R-DSL-006** SHOULD: Group related services in subdirectories if a domain grows large (e.g., ManageJournals/Services/Posts, ManageJournals/Services/Metrics).
- **R-DSL-007** MUST: Ensure services encapsulate meaningful business logic, validation, or orchestration rather than acting as simple pass-through to models.

**Accept when:**
- Service classes exist in dedicated Services directories within domain boundaries
- Controllers delegate to services rather than implementing business logic directly
- Service class names follow verb-noun convention and implement single-responsibility operations
- Controllers remain focused on HTTP concerns (validation, response handling) without complex business logic
- Services provide clear transaction boundaries and can be tested in isolation

### Implementation Notes

**Rationale:**
- Service layer pattern provides clear separation between HTTP concerns and business logic
- Single-responsibility services enable fine-grained reusability and composition
- Domain-driven organization creates clear boundaries aligned with business capabilities
- Centralized business logic improves testability and maintainability

**Risks & Mitigation:**
- Risk: Service layer becomes anemic with pass-through methods
  - Mitigation: Ensure services provide value through orchestration, validation, or business logic
- Risk: Inconsistent pattern application across domains
  - Mitigation: Document pattern in architecture guidelines, conduct architecture reviews
- Risk: Performance overhead from abstraction layers
  - Mitigation: Profile critical paths, optimize service composition, cache at service boundaries

**Alternatives Considered:**
- Fat Controllers: Rejected - violates single responsibility, makes testing difficult
- Active Record Pattern: Rejected - creates bloated models with mixed concerns
- Command Bus Pattern: Deferred - may be considered for cross-cutting concerns at higher complexity
