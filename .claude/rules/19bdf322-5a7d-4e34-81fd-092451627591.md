<rule_activation id="19bdf322-5a7d-4e34-81fd-092451627591" title="Standardize External API Integration with DAV Protocol and DTO Pattern: Permission Validation External" applies_to="**/*">
These rules apply to all external API integrations including DAV, CardDAV, and CalDAV protocols; data transfer between external systems and internal domain models; resource import and export operations; permission validation and error handling for public-facing API endpoints; and backend interface implementations for protocol-specific operations.

**In scope:**
- All external API integrations including DAV, CardDAV, and CalDAV protocols
- Data transfer between external systems and internal domain models
- Resource import and export operations for contacts, calendars, and related entities
- Permission validation and error handling for public-facing API endpoints
- Backend interface implementations for protocol-specific operations

**Out of scope:**
- Internal service-to-service communication within the application
- Database access patterns and repository implementations
- Frontend API endpoints that do not interact with external systems
- Authentication mechanisms (covered by separate security ADRs)
- GraphQL or REST API design for the application's own public API
</rule_activation>

### Rules

- **R-EAPI-001** MUST: Permission validation for external API operations MUST throw specific permission exceptions (NotEnoughPermissionException) rather than generic authorization errors

### Implementation Guidance

When implementing external API integrations, follow these patterns:

- **DTO Pattern**: Define DTO classes that represent the external data format, then create mappers to internal domain models
- **Interface Abstraction**: Define backend interfaces before implementing concrete classes; use dependency injection to provide implementations to consumers
- **Domain-Specific Exceptions**: Create domain-specific exception types in the appropriate domain namespace with descriptive names and error messages
- **ViewHelper Pattern**: Use ViewHelper classes in the Web layer to prepare data for API responses, keeping controllers thin and focused on HTTP concerns
- **Logging**: Add the Loggable trait to API client classes to ensure consistent logging of external API interactions

### Verify

```bash
# Check for DTO classes in external API integrations
grep -r "class.*Dto" app/Domains/*/DavClient/Services/Utils/Model/ | wc -l

# Check for backend interface abstractions
grep -r "interface.*Backend" app/Domains/*/Dav/Web/Backend/ | wc -l

# Check for domain-specific exception types
grep -r "class.*Exception extends" app/Domains/ | grep -E "(Permission|Compliant|Maximum)" | wc -l

# Check for ViewHelper classes
find app/Domains -name "*ViewHelper.php" -type f | wc -l
```

**Accept when:**
- All external API integrations use DTO classes for data transfer with at least one DTO per external entity type
- Protocol-specific operations are abstracted behind interface contracts with at least one concrete implementation
- Domain-specific exception types exist for common API failure scenarios (permission, compliance, limits) and are properly caught in controllers
- ViewHelper classes are present for domains that expose external APIs and are used in controller response preparation

<enforcement>
Claude Code MUST verify compliance with these rules for all external API integration code. Pull requests that introduce external API integrations without proper DTO/interface patterns must be flagged. Critical violations (missing permission checks, generic exceptions) require immediate remediation.

**Exceptions:**
- EX-001: Legacy integrations that predate this ADR and are scheduled for deprecation within 6 months
- EX-002: Proof-of-concept or experimental integrations in feature branches not intended for production

Exception requests must be submitted to Technical Lead with justification and impact analysis.
</enforcement>
