<rule_activation id="3b5d15bb-fbad-4257-ba58-11456d441ad3" title="Standardize External API Integration with DAV Protocol and DTO Pattern: External Integrations Implement" applies_to="app/Domains/**/*.php">
These rules are ALWAYS ACTIVE for all files matching `app/Domains/**/*.php` that implement external API integrations (DAV, CardDAV, CalDAV protocols).
</rule_activation>

### Rules

- **R-EAI-001** SHOULD: External API integrations SHOULD implement logging capabilities using traits (e.g., Loggable) for consistent observability across API interactions.

- **R-EAI-002** MUST: External API integrations MUST use DTO classes for data transfer with at least one DTO per external entity type.

- **R-EAI-003** MUST: Protocol-specific operations MUST be abstracted behind interface contracts (e.g., IDAVBackend) with at least one concrete implementation.

- **R-EAI-004** MUST: Domain-specific exception types MUST exist for common API failure scenarios (NotEnoughPermissionException, MaximumNumberOfUsersInVaultException, DavServerNotCompliantException) and MUST be properly caught in controllers.

- **R-EAI-005** MUST: ViewHelper classes MUST be present for domains that expose external APIs and MUST be used in controller response preparation.

### Scope

**In scope:**
- All external API integrations including DAV, CardDAV, and CalDAV protocols
- Data transfer between external systems and internal domain models
- Resource import and export operations for contacts, calendars, and related entities
- Permission validation and error handling for public-facing API endpoints
- Backend interface implementations for protocol-specific operations

**Out of scope:**
- Internal service-to-service communication within the application
- Database access patterns and repository implementations
- Frontend API endpoints that do not interact with external systems
- Authentication mechanisms (covered by separate security ADRs)

**Exceptions:**
- EX-001: Legacy integrations scheduled for deprecation within 6 months
- EX-002: Proof-of-concept or experimental integrations in feature branches not intended for production

### Verify

```bash
# Check for DTO classes in external API integration directories
grep -r "class.*Dto" app/Domains/*/DavClient/Services/Utils/Model/ | wc -l

# Check for backend interface abstractions
grep -r "interface.*Backend" app/Domains/*/Dav/Web/Backend/ | wc -l

# Check for domain-specific exception types
grep -r "class.*Exception extends" app/Domains/ | grep -E "(Permission|Compliant|Maximum)" | wc -l

# Check for ViewHelper classes
find app/Domains -name "*ViewHelper.php" -type f | wc -l
```

**Accept when:**
- All external API integrations use DTO classes for data transfer with at least one DTO per external entity type
- Protocol-specific operations are abstracted behind interface contracts with at least one concrete implementation
- Domain-specific exception types exist for common API failure scenarios (permission, compliance, limits) and are properly caught in controllers
- ViewHelper classes are present for domains that expose external APIs and are used in controller response preparation

### Implementation Guidance

When creating new external API integrations:

1. **Start with DTOs**: Define DTO classes that represent the external data format (e.g., ContactDto, ContactDeleteDto), then create mappers to internal domain models

2. **Define interfaces first**: Define backend interfaces (e.g., IDAVBackend) before implementing concrete classes; use dependency injection to provide implementations to consumers

3. **Create domain-specific exceptions**: Create exception types in the appropriate domain namespace (e.g., `app/Domains/Contact/DavClient/Services/Utils/Dav/`) with descriptive names and error messages

4. **Use ViewHelper pattern**: Use ViewHelper classes in the Web layer to prepare data for API responses, keeping controllers thin and focused on HTTP concerns

5. **Add logging**: Add the Loggable trait to API client classes to ensure consistent logging of external API interactions for debugging and monitoring

<enforcement>
Claude Code MUST verify compliance with these rules when creating or modifying external API integrations. Verification MUST NOT be skipped or deferred. Pull requests that introduce external API integrations without proper DTO/interface patterns are blocked until refactored.
</enforcement>
