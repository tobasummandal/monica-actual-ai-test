<rule_activation id="a1e04203-ee4a-4c53-9459-0d2bebd4b0b7" title="Adopt Laravel Fortify for Authentication Action Standardization: Domain Specific User" applies_to="app/Actions/Fortify/**/*.php,app/Domains/**/Services/**/*.php">
These rules are ALWAYS ACTIVE for authentication action classes in `app/Actions/Fortify` and domain service classes in `app/Domains/**/Services`.
</rule_activation>

### Rules

- **R-FORT-001** MUST: Domain-specific user management services (CreateAccount, AcceptInvitation, CancelAccount) MUST be implemented as dedicated service classes within their respective domain boundaries.
- **R-FORT-002** MUST: Fortify action classes MUST extend appropriate Fortify contracts (ResetUserPassword, UpdateUserPassword) and be registered in FortifyServiceProvider.
- **R-FORT-003** MUST: Password validation MUST use Laravel's Hash facade consistently across all authentication touchpoints.
- **R-FORT-004** SHOULD: Domain services SHOULD be placed in app/Domains/{DomainName}/Services and follow single-responsibility principle.
- **R-FORT-005** SHOULD: Authentication logic SHOULD be separated from presentation layer to enable deployment across multiple targets (web, API, mobile).
- **R-FORT-006** MUST: Feature tests for authentication operations MUST cover both success and failure scenarios using Laravel's authentication testing helpers.

### In Scope

- All password management operations (reset, update, validation)
- User account lifecycle operations (creation, cancellation, invitation acceptance)
- Authentication action classes in app/Actions/Fortify
- Domain service classes handling user management in app/Domains/Settings
- Feature tests validating authentication behavior

### Out of Scope

- Frontend authentication UI components
- Session management and cookie handling
- OAuth and social authentication providers
- Authorization and permission logic
- API token generation and management

### Verify

```bash
# Check Fortify action classes extend Fortify contracts
grep -r "extends.*Fortify" app/Actions/Fortify/ | wc -l

# Check domain service classes exist in proper location
find app/Domains -name "*Service.php" -path "*/Services/*" | wc -l

# Check Hash facade usage in authentication code
grep -r "use Illuminate\\Support\\Facades\\Hash" app/Actions/Fortify app/Domains/Settings | wc -l

# Run authentication feature tests
php artisan test --filter=Auth --filter=Password --filter=Account
```

**Accept when:**

- All authentication actions in app/Actions/Fortify extend appropriate Fortify contracts and are registered in FortifyServiceProvider
- Domain-specific user management services exist in app/Domains/*/Services and delegate to Fortify actions for password operations
- Feature tests for authentication operations pass and cover both web and API scenarios without presentation layer dependencies
- Password validation uses Laravel Hash facade consistently across all authentication touchpoints

<enforcement>
Claude Code MUST NOT skip or defer verification. All authentication changes require:
- Automated CI pipeline checks for presence of Fortify action classes and domain services
- Code review checklist verification of authentication pattern compliance
- Static analysis tools (PHPStan, Psalm) configured to detect direct password hashing without Hash facade
- Architecture decision record review during sprint planning for new authentication features

Violation handling:
- CI pipeline fails if authentication logic is detected in controllers without corresponding Fortify action or domain service
- Pull requests containing authentication changes require architecture team approval
- Quarterly architecture audits identify and flag non-compliant authentication implementations for refactoring
- New authentication features must include ADR compliance documentation

Exception process:
- Submit exception request to architecture review board with justification for deviation
- Document exception rationale in code comments with reference to approval ticket
- Exceptions are time-limited (6-12 months) and require re-approval or migration to standard pattern
- All exceptions tracked in architecture decision log and reviewed quarterly
</enforcement>
