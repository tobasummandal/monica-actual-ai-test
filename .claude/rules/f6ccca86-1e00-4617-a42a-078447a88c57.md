<rule_activation id="f6ccca86-1e00-4617-a42a-078447a88c57" title="Adopt Domain-Driven Service Layer Pattern for Journal Management: Services Composed Together" applies_to="app/Domains/**/*.php">
These rules are ALWAYS ACTIVE for all PHP files in the Domains directory matching `app/Domains/**/*.php`.
</rule_activation>

### Rules

#### Service Composition
- **R-DDS-001** MAY: Services MAY be composed together to implement complex workflows, but each service should remain independently testable.

#### Naming and Structure
- **R-DDS-002** SHOULD: Use verb-noun naming for service classes (e.g., CreatePost, UpdateMetric, RemoveTag) to clearly communicate intent.
- **R-DDS-003** SHOULD: Keep controllers thin - they should validate input, call services, and return responses without implementing business logic.
- **R-DDS-004** SHOULD: Services should accept primitive types or DTOs as parameters rather than HTTP request objects to maintain independence from web layer.
- **R-DDS-005** SHOULD: Consider using dependency injection for service dependencies to improve testability and enable mocking.
- **R-DDS-006** MAY: Group related services in subdirectories if a domain grows large (e.g., ManageJournals/Services/Posts, ManageJournals/Services/Metrics).

#### Scope - Where Pattern Applies
- **R-DDS-007** MUST: Apply this pattern to all journal management operations including posts, metrics, photos, tags, slices of life, and contacts.
- **R-DDS-008** MUST: Apply to business logic that requires database transactions or multiple model interactions.
- **R-DDS-009** MUST: Apply to operations that enforce domain-specific business rules and validation.
- **R-DDS-010** MUST: Apply to functionality within the Vault domain's ManageJournals subdomain.

#### Scope - Where Pattern Does NOT Apply
- **R-DDS-011** MUST NOT: Apply to simple CRUD operations that only involve single-model persistence without business logic.
- **R-DDS-012** MUST NOT: Place HTTP request/response handling and view rendering in services (belongs in controllers).
- **R-DDS-013** MUST NOT: Apply to cross-domain operations that span multiple bounded contexts.
- **R-DDS-014** MUST NOT: Apply to infrastructure concerns like caching, logging, and external API integration.

### Verify

```bash
# Check that service classes exist in dedicated Services directories
find app/Domains/*/Services -type f -name '*.php' | wc -l

# Verify controllers exist in proper locations
grep -r 'class.*Controller' app/Domains/Vault/ManageJournals/Web/Controllers | wc -l

# Verify service namespaces are properly structured
grep -r 'namespace.*Services' app/Domains/Vault/ManageJournals/Services | head -5
```

**Accept when:**
- Service classes exist in dedicated Services directories within domain boundaries
- Controllers delegate to services rather than implementing business logic directly
- Service class names follow verb-noun convention and implement single-responsibility operations
- Business logic is encapsulated in services, not scattered across controllers or models
- Each service maintains single-responsibility and is independently testable

### Context

**Rationale:**
- Service layer pattern provides clear separation between HTTP concerns (controllers) and business logic (services)
- Single-responsibility services enable fine-grained reusability and composition for complex workflows
- Domain-driven organization creates clear boundaries that align with business capabilities
- Improves testability, maintainability, and code reusability

**Key Risks:**
- Service layer becomes anemic with services acting as simple pass-through to models without adding value
- Inconsistent application of pattern across different domains leading to architectural fragmentation
- Performance overhead from additional abstraction layers in high-throughput scenarios
