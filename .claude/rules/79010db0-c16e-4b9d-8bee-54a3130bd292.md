<rule_activation id="79010db0-c16e-4b9d-8bee-54a3130bd292" title="Organize Domain Logic Using Domain-Driven Design Bounded Contexts: Each Domain Separate" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in the application codebase. Domain-driven design organization is a foundational architectural pattern that applies to all new business logic, service classes, web controllers, and domain models.
</rule_activation>

### Rules

- **R-DDD-001** MUST: Each domain MUST separate concerns into distinct subdirectories: Services for business logic, Web/Controllers for HTTP handling, and Models for data structures.

### Verify

```bash
# Verify all controllers are in Web/Controllers subdirectories
find app/Domains -type f -name '*Controller.php' | xargs grep -L 'namespace.*\\Web\\Controllers' | wc -l | grep -q '^0$'

# Count service classes in Services subdirectories
find app/Domains -type f -name '*Service.php' -path '*/Services/*' | wc -l

# Verify no controllers exist outside Web/Controllers namespaces
grep -r 'class.*Controller' app/Domains --include='*.php' | grep -v 'namespace.*\\Web\\Controllers' | wc -l | grep -q '^0$'
```

**Accept when:**
- All controllers are located in Web/Controllers subdirectories within their respective domains
- Service classes are located in Services subdirectories and contain business logic separate from HTTP concerns
- New features added to the codebase follow the domain structure pattern with at least 95% compliance
- Code review checklist includes verification of proper domain organization
- Domain boundaries align with actual business domains and functional areas
- Cross-domain communication uses dependency inversion or domain events rather than direct service calls

<enforcement>
Claude Code MUST verify domain organization compliance before approving code changes. Violations must be resolved through refactoring or documented exceptions before merge. Automated CI pipeline checks are mandatory.
</enforcement>
