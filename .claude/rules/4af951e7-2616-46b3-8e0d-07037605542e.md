<rule_activation id="4af951e7-2616-46b3-8e0d-07037605542e" title="Adopt Domain-Driven Resource Modeling for Data Access Layer: Resource Classes External" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching the application codebase, particularly app/Models/, app/Domains/, and resource class definitions.
</rule_activation>

### Rules

- **R-DDD-001** MUST: Resource classes for external protocol integration (e.g., VCard, VCalendar) MUST be separated from core domain models.
- **R-DDD-002** MUST: Place core domain models in app/Models/ directory with clear, singular naming (e.g., File.php, User.php).
- **R-DDD-003** MUST: Organize domain-specific models and resources within app/Domains/{DomainName}/ subdirectories to maintain bounded contexts.
- **R-DDD-004** MUST: Create dedicated resource classes (e.g., VCardResource, VCalendarResource) for external protocol transformations in appropriate domain subdirectories.
- **R-DDD-005** SHOULD: Use consistent method naming for resource transformations (e.g., toVCard(), fromVCard()) to establish predictable APIs.

### Verify

```bash
# Count core domain models
find app/Models -name '*.php' -type f | wc -l

# Count resource classes in domain directories
grep -r 'class.*Resource' app/Domains/ --include='*.php' | wc -l

# Verify domain-specific organization (DAV example)
find app/Domains -type d -name 'Dav' | wc -l
```

**Accept when:**
- All domain entities have corresponding model classes in app/Models/ or domain-specific directories
- External protocol integrations use dedicated resource classes separate from core models
- Domain organization follows consistent directory structure with clear bounded contexts
- Resource classes use consistent transformation method naming patterns (toVCard, fromVCard, etc.)
- No protocol-specific logic (VCard, VCalendar) is mixed into core domain model classes
