<rule_activation id="773ccd70-a291-4972-afc1-1ddc8186edfe" title="Adopt CardDAV/WebDAV Protocol for External Contact Synchronization: Non Compliant Dav" applies_to="app/Domains/Contact/**/*">
These rules are ALWAYS ACTIVE for all external contact synchronization integrations and DAV protocol implementations within the Contact domain.

**In scope:**
- All contact synchronization with external CardDAV/WebDAV servers
- vCard import and export operations for contact data
- DAV backend interface implementations
- Contact DTO models for external API communication
- Error handling for non-compliant DAV servers

**Out of scope:**
- Internal contact storage and database operations
- REST API endpoints for web/mobile clients
- GraphQL APIs for internal services
- Non-DAV third-party integrations (OAuth-based APIs, webhooks)
- Real-time synchronization protocols (WebSocket, Server-Sent Events)

**Exceptions:**
- EX-001: Legacy contact import from proprietary formats (CSV, Excel) that cannot be converted to vCard
- EX-002: Emergency fallback to direct database operations when DAV server is persistently unavailable
</rule_activation>

### Rules

- **R-DAV-001** MUST: Non-compliant DAV servers MUST be handled with specific exceptions (DavServerNotCompliantException) to provide clear error diagnostics.
- **R-DAV-002** MUST: All DAV backend implementations MUST implement the IDAVBackend interface.
- **R-DAV-003** MUST: Contact DTO models (ContactDto and ContactDeleteDto) MUST be used consistently across all DavClient services for type safety and testability.
- **R-DAV-004** SHOULD: Create separate resource handlers (ImportResource, ImportVCardResource) to handle different import scenarios and maintain single responsibility principle.
- **R-DAV-005** SHOULD: Implement comprehensive error handling that distinguishes between network errors, authentication failures, and protocol compliance issues.

### Verify

```bash
# Check IDAVBackend interface implementation
grep -r "IDAVBackend" app/Domains/Contact/Dav/ --include="*.php" | wc -l

# Check ContactDto usage
grep -r "ContactDto\|ContactDeleteDto" app/Domains/Contact/DavClient/ --include="*.php" | wc -l

# Check DavServerNotCompliantException usage
grep -r "DavServerNotCompliantException" app/Domains/Contact/ --include="*.php" | wc -l

# Check import resource handlers
find app/Domains/Contact/Dav* -name "*Import*Resource.php" -o -name "*VCard*.php" | wc -l
```

**Accept when:**
- All DAV backend implementations implement the IDAVBackend interface (verify command returns > 0)
- Contact DTO models are consistently used across DavClient services (verify command returns >= 2 for both DTOs)
- DavServerNotCompliantException is present and used for error handling (verify command returns > 0)
- Import resource handlers exist for DAV and vCard operations (verify command returns >= 2)

<enforcement>
Claude Code MUST NOT skip or defer verification. All changes to contact synchronization code must:

- Be verified by automated static analysis checks for IDAVBackend interface implementation in all DAV backend classes
- Undergo code review requiring verification of DTO usage in all external API communication
- Pass integration test suite validating CardDAV protocol compliance with reference implementations
- Comply with architecture fitness functions checking namespace organization (DavClient separation from domain logic)

**Violation handling:**
- CI pipeline fails if DAV backend classes do not implement IDAVBackend interface
- Pull requests are blocked if external API calls bypass DTO models and use raw arrays or stdClass objects
- Architecture review is triggered if new contact synchronization code is added outside the DavClient namespace
- Warning notifications are generated if DavServerNotCompliantException is not caught in DAV client service methods

**Exception process:**
1. Developer submits exception request with justification to Technical Lead via architecture decision log
2. Technical Lead reviews the request against policy exceptions (EX-001, EX-002) and architectural principles
3. If approved, exception is documented in ADR amendments with time-bound review date (max 6 months)
4. All exceptions are reviewed quarterly to determine if they should become permanent alternatives or be refactored to comply
</enforcement>
