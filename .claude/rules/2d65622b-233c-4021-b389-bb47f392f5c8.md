<rule_activation id="2d65622b-233c-4021-b389-bb47f392f5c8" title="Adopt Eloquent ORM Models as Standard Data Access Layer: Each Model Correspond" applies_to="app/Models/**/*.php">
These rules are ALWAYS ACTIVE for all Laravel Eloquent model files in `app/Models/`.

**Context**: The application uses Laravel's Eloquent ORM as the standard data access layer. Models represent database entities with built-in support for relationships, query building, and lifecycle events.

**In scope**:
- All database-backed domain entities requiring CRUD operations
- Entities with relationships to other database tables
- Data structures requiring validation, casting, or transformation
- Objects requiring query builder functionality and collection operations

**Out of scope**:
- Value objects without database persistence
- Data Transfer Objects (DTOs) for API communication
- Temporary data structures for in-memory processing
- External service integrations not backed by application database

**Exceptions**:
- **EXC-001**: Legacy database schemas require raw SQL queries that cannot be efficiently expressed through Eloquent
- **EXC-002**: Read-only reporting queries spanning multiple complex joins benefit from query builder or raw SQL
</rule_activation>

### Rules

- **R-ELO-001** MUST: Each model MUST correspond to a single database table with explicit or conventional table name mapping.
- **R-ELO-002** MUST: All model files MUST extend `Illuminate\Database\Eloquent\Model`.
- **R-ELO-003** MUST: Models MUST define either `$fillable` or `$guarded` properties for mass assignment protection.
- **R-ELO-004** MUST: Direct database queries outside models (using `DB::table` or `DB::select`) MUST be documented with exception justifications referencing EXC-001 or EXC-002.
- **R-ELO-005** SHOULD: Define relationships using type-hinted return types (e.g., `public function posts(): HasMany`) for better IDE support and static analysis.
- **R-ELO-006** SHOULD: Use `php artisan make:model` command to generate new models with consistent structure.
- **R-ELO-007** SHOULD: Leverage model factories for testing to ensure consistent test data generation.
- **R-ELO-008** SHOULD: Use eager loading to prevent N+1 query problems.
- **R-ELO-009** SHOULD: Keep models focused on data access; move complex business logic to service layer classes.
- **R-ELO-010** SHOULD: Document complex query scopes and custom accessors with PHPDoc blocks.
- **R-ELO-011** SHOULD: Consider using model observers for cross-cutting concerns like logging, caching, or event dispatching.

### Verify

```bash
# Count models extending Eloquent Model
grep -r "extends Model" app/Models/ | wc -l

# Find models missing proper namespace
find app/Models -name '*.php' -exec grep -L 'namespace App\\Models' {} \;

# Count total model classes (requires Laravel)
php artisan model:show --all 2>&1 | grep -c 'class'

# Find direct database queries outside models (excluding documented exceptions)
grep -r "DB::table\|DB::select" app/Http app/Services | grep -v "// Exception" | wc -l
```

**Accept when:**
- All model files in `app/Models` extend `Illuminate\Database\Eloquent\Model`
- At least 7 model classes exist matching the detected pattern (File, PostTemplateSection, ContactInformationType, GiftOccasion, CallReasonType, Account, QuickFact)
- Models define either `$fillable` or `$guarded` properties for mass assignment protection
- Direct database queries outside models are documented with exception justifications (EXC-001 or EXC-002)
- Models are placed in the `app/Models` namespace
- Mass assignment protection is explicitly configured (not relying on defaults)

### Implementation Notes

- Use `php artisan make:model` command to generate new models with consistent structure and optional migration/factory scaffolding
- Define relationships using type-hinted return types for better IDE support and static analysis
- Leverage model factories for testing to ensure consistent test data generation
- Document complex query scopes and custom accessors with PHPDoc blocks
- Consider using model observers for cross-cutting concerns rather than cluttering model methods

### Risk Mitigations

- **N+1 query problems**: Implement query monitoring, enforce eager loading in code reviews, use Laravel Debugbar in development, add automated tests for query counts
- **Fat models**: Establish service layer pattern for complex business logic, enforce single responsibility in code reviews, refactor models exceeding 300 lines
- **Mass assignment vulnerabilities**: Require explicit `$fillable` or `$guarded` definitions, add static analysis checks, include mass assignment testing in security audits
