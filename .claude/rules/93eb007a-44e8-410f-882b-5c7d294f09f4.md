<rule_activation id="93eb007a-44e8-410f-882b-5c7d294f09f4" title="Standardize Password Hashing for Authentication Operations: Password Hashing Logic" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching authentication operations, domain services, and Fortify action handlers that deal with password creation, updates, and resets.
</rule_activation>

### Rules

- **R-AUTH-001** SHOULD: Password hashing logic SHOULD be centralized in dedicated service methods or use framework-provided mechanisms rather than inline implementations.

### Verify

```bash
# Detect unhashed password assignments in authentication code
grep -r "'password'\s*=>\s*\$" app/ --include='*.php' | grep -v 'Hash::make' | grep -v 'bcrypt(' | grep -v '// ' || echo 'No unhashed password assignments found'

# Count Hash::make and bcrypt usage in Fortify and Settings domains
grep -r "Hash::make\|bcrypt(" app/Actions/Fortify/ app/Domains/Settings/ --include='*.php' | wc -l

# Verify password-related feature tests exist and pass
php artisan test --filter=Password --coverage-text | grep -E '(UpdatePasswordTest|ResetPasswordTest)'
```

**Accept when:**
- All password assignment operations in authentication code paths use `Hash::make()` or `bcrypt()` helper
- Feature tests verify that stored passwords are hashed (`Hash::check()` returns true for original password)
- Code review checklist includes verification of password hashing for any authentication-related changes
- No unhashed password assignments detected in grep verification
- Password hashing is applied in all in-scope workflows: account creation, password reset, password update, and invitation acceptance

<enforcement>
Claude Code MUST NOT skip or defer verification of password hashing patterns. All authentication code paths MUST use centralized hashing mechanisms. Violations in production authentication code are non-negotiable security failures and MUST block deployment.
</enforcement>
