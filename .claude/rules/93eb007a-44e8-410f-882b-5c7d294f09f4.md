<rule_activation id="93eb007a-44e8-410f-882b-5c7d294f09f4" title="Standardize Password Hashing for Authentication Operations: Password Hashing Logic" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching `**/*`.

**Context:** The application handles sensitive user authentication data including password creation, updates, and resets across multiple domains (Settings, Fortify actions). Password security operations are distributed across account creation, invitation acceptance, password updates, and password reset workflows.

**Scope:**
- Account creation workflows (new user registration)
- Password reset operations (forgotten password flows)
- Password update operations (authenticated user password changes)
- Invitation acceptance flows that set initial passwords
- All Fortify action handlers dealing with password operations
- Domain service classes that create or modify user credentials

**Out of scope:**
- API token generation and management
- OAuth or third-party authentication flows that don't store passwords
- Session management and cookie handling
- Two-factor authentication token handling
- Password reset token generation (tokens themselves, not the new password)
</rule_activation>

### Rules

- **R-PH-001** SHOULD: Password hashing logic SHOULD be centralized in dedicated service methods or use framework-provided mechanisms rather than inline implementations.

- **R-PH-002** MUST: Use `Hash::make($password)` for all password hashing operations; configure cost factor in `config/hashing.php`.

- **R-PH-003** MUST: In Fortify action classes (`ResetUserPassword`, `UpdateUserPassword`), ensure password hashing occurs before calling `$user->forceFill(['password' => ...])->save()`.

- **R-PH-004** MUST: In domain service classes (`CreateAccount`, `AcceptInvitation`), apply hashing before user model creation or password updates.

- **R-PH-005** MUST: Feature tests should use `Hash::check($plainPassword, $user->password)` to verify hashing occurred correctly.

- **R-PH-006** SHOULD: Consider using Laravel's validation rule `Password::min(8)->mixedCase()->numbers()` to enforce password complexity before hashing.

### Verify

```bash
# Check for unhashed password assignments
grep -r "'password'\s*=>\s*\$" app/ --include='*.php' | grep -v 'Hash::make' | grep -v 'bcrypt(' | grep -v '// ' || echo 'No unhashed password assignments found'

# Count password hashing usage in authentication code
grep -r "Hash::make\|bcrypt(" app/Actions/Fortify/ app/Domains/Settings/ --include='*.php' | wc -l

# Run password-related tests
php artisan test --filter=Password --coverage-text | grep -E '(UpdatePasswordTest|ResetPasswordTest)'
```

**Accept when:**
- All password assignment operations in authentication code paths use `Hash::make()` or `bcrypt()` helper
- Feature tests verify that stored passwords are hashed (`Hash::check` returns true for original password)
- Code review checklist includes verification of password hashing for any authentication-related changes

<enforcement>
Claude Code MUST NOT skip or defer verification.

**Verification methods:**
- Automated feature tests that verify password hashing in UpdatePasswordTest and similar test classes
- Code review process with security-focused checklist for authentication changes
- Static analysis using grep patterns in CI pipeline to detect potential unhashed password assignments

**Violation handling:**
- CI pipeline fails if grep patterns detect potential unhashed password assignments
- Code review blocks merge if password hashing is not verified in authentication code
- Security audit flags any user records with passwords that don't match bcrypt hash format

**Exceptions:**
- No exceptions permitted for production authentication code; password hashing is a non-negotiable security requirement
- Test fixtures and seeding may use simplified hashing with documented security warnings
- Any deviation requires security team approval and must be documented in ADR amendment
</enforcement>
