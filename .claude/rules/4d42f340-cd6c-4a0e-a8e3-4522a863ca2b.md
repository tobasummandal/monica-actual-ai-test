<rule_activation id="4d42f340-cd6c-4a0e-a8e3-4522a863ca2b" title="Adopt Laravel Fortify for Authentication Action Standardization: Controllers Delegate Domain" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in the Laravel application, particularly authentication and user management code.
</rule_activation>

### Rules

- **R-LFORT-001** MAY: Controllers MAY delegate to domain services or Fortify actions based on the complexity and domain-specificity of the operation.
- **R-LFORT-002** MUST: Fortify action classes MUST extend appropriate Fortify contracts (ResetUserPassword, UpdateUserPassword) and be registered in FortifyServiceProvider.
- **R-LFORT-003** MUST: Domain services MUST be placed in `app/Domains/{DomainName}/Services` and follow single-responsibility principle, handling one user lifecycle operation per service.
- **R-LFORT-004** MUST: Password validation MUST use Laravel's Hash facade consistently across all authentication actions (never implement direct password hashing).
- **R-LFORT-005** MUST: Feature tests MUST use Laravel's authentication testing helpers (actingAs, assertAuthenticated) and test both success and failure scenarios.
- **R-LFORT-006** MUST: Password requirements MUST use Laravel's validation rules (min:8, confirmed, etc.) consistently across all authentication actions.
- **R-LFORT-007** MUST NOT: Authentication logic MUST NOT be implemented directly in controllers without Fortify abstraction or domain service delegation.

### Scope

**In scope:**
- All password management operations (reset, update, validation)
- User account lifecycle operations (creation, cancellation, invitation acceptance)
- Authentication action classes in `app/Actions/Fortify`
- Domain service classes handling user management in `app/Domains/Settings`
- Feature tests validating authentication behavior

**Out of scope:**
- Frontend authentication UI components
- Session management and cookie handling
- OAuth and social authentication providers
- Authorization and permission logic
- API token generation and management

### Verify

```bash
# Count Fortify action classes extending Fortify contracts
grep -r "extends.*Fortify" app/Actions/Fortify/ | wc -l

# Count domain service classes in proper directory structure
find app/Domains -name "*Service.php" -path "*/Services/*" | wc -l

# Verify consistent use of Hash facade
grep -r "use Illuminate\\Support\\Facades\\Hash" app/Actions/Fortify app/Domains/Settings | wc -l

# Run authentication feature tests
php artisan test --filter=Auth --filter=Password --filter=Account
```

**Accept when:**
- All authentication actions in `app/Actions/Fortify` extend appropriate Fortify contracts and are registered in FortifyServiceProvider
- Domain-specific user management services exist in `app/Domains/*/Services` and delegate to Fortify actions for password operations
- Feature tests for authentication operations pass and cover both web and API scenarios without presentation layer dependencies
- Password validation uses Laravel Hash facade consistently across all authentication touchpoints

### Implementation Guidance

**Decision boundary:**
- **Fortify actions** (framework-level): Password resets, password updates, authentication mechanics
- **Domain services** (business-specific): Account creation, account cancellation, invitation acceptance, user lifecycle management

**When to use each:**
- Use Fortify actions for operations defined by Laravel authentication contracts
- Use domain services for business-specific user management workflows
- Domain services should delegate to Fortify actions for password-related operations

### Rationale

This pattern enables:
- Authentication logic deployment to multiple targets (web, API, mobile) without modification
- Clear separation between authentication mechanics and presentation layer
- Standardized password handling through Laravel's Hash facade
- Independent evolution of frontend and backend components
- Deployment-agnostic testing that validates behavior independent of target environment
