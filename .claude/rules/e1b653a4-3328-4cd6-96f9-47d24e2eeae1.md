<rule_activation id="e1b653a4-3328-4cd6-96f9-47d24e2eeae1" title="Adopt Laravel Migrations as Standard Database Schema Management: Each Migration File" applies_to="**/*">
These rules are ALWAYS ACTIVE for all database schema changes across the application. All schema modifications MUST be implemented through Laravel migration files.
</rule_activation>

### Rules

- **R-MIG-001** MUST: All database schema modifications MUST be implemented through Laravel migration files in the `database/migrations` directory.
- **R-MIG-002** MUST: Each migration file MUST implement both `up()` and `down()` methods to support forward migration and rollback operations.
- **R-MIG-003** MUST: Migration files MUST follow Laravel's timestamp-based naming convention (YYYY_MM_DD_HHMMSS_description.php).
- **R-MIG-004** MUST: Schema changes MUST use Laravel's Schema Builder API (Schema::create, Schema::table, Schema::drop).
- **R-MIG-005** MUST: No direct SQL schema modifications outside migration files are permitted.
- **R-MIG-006** SHOULD: Use `php artisan make:migration` command to generate new migration files with proper timestamp and structure.
- **R-MIG-007** SHOULD: Always test migrations locally with both `migrate` and `migrate:rollback` commands before committing.
- **R-MIG-008** SHOULD: For complex data transformations, separate schema changes from data migrations into distinct migration files.
- **R-MIG-009** SHOULD: Document any database-specific SQL used in migrations with comments explaining compatibility implications.
- **R-MIG-010** SHOULD: Use Laravel's migration methods like `foreignId()`, `timestamps()`, `softDeletes()` for consistency with framework conventions.

### Scope

**In scope:**
- All table creation, modification, and deletion operations
- Column additions, modifications, and removals
- Index creation and removal
- Foreign key constraint definitions
- Database-level configuration changes that affect schema structure

**Out of scope:**
- Application data seeding for testing purposes (use database/seeders instead)
- Data migration or transformation scripts that don't modify schema structure
- Database performance tuning that doesn't affect schema (query optimization, connection pooling)
- Backup and restore operations

**Exceptions:**
- EXC-001: Emergency production hotfix requiring immediate schema change to resolve critical outage
- EXC-002: Database-specific optimizations requiring raw SQL that cannot be expressed through Schema Builder

### Verify

```bash
# Count migration files in standard location
find database/migrations -name '*.php' -type f | wc -l | grep -E '^[0-9]+$'

# Verify Schema Builder usage in migrations
grep -r 'Schema::create\|Schema::table\|Schema::drop' database/migrations/ | wc -l

# Check migration status
php artisan migrate:status 2>&1 | grep -E 'Ran|Pending'

# Verify up() and down() methods exist in migration files
ls database/migrations/*.php 2>/dev/null | head -5 | xargs grep -l 'function up()' | xargs grep -l 'function down()'
```

**Accept when:**
- All migration files exist in `database/migrations` directory and follow Laravel naming convention with timestamps
- Each migration file contains both `up()` and `down()` methods using Schema Builder API
- Migration status command executes successfully showing tracked migrations
- No direct SQL schema modifications are found in application code outside migration files

<enforcement>
Claude Code MUST NOT skip or defer verification. All schema changes require:
- Automated CI pipeline checks to verify migration file structure and naming conventions
- Code review process to ensure all schema changes are implemented through migrations
- Pre-deployment checks running `php artisan migrate:status` to verify migration state
- Static analysis to scan for direct SQL schema modification patterns outside migrations

Violations result in:
- Pull requests containing direct SQL schema changes are automatically flagged and rejected by CI
- Production deployments are blocked if migration status shows inconsistencies
- Manual schema changes detected in production trigger alerts to DevOps team for remediation
- All violations require creation of corresponding migration file and documentation of incident

Exception process:
- Exception requests must be submitted through architecture review board with detailed justification
- Emergency exceptions require post-incident review and creation of compensating migration within 24 hours
- All exceptions must be documented in ADR updates or exception log with rationale and approval chain
- Temporary exceptions are reviewed quarterly to determine if they can be brought into compliance
</enforcement>
