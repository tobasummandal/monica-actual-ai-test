<rule_activation id="e1b653a4-3328-4cd6-96f9-47d24e2eeae1" title="Adopt Laravel Migrations as Standard Database Schema Management: Each Migration File" applies_to="database/migrations/**/*.php">
These rules are ALWAYS ACTIVE for all database schema changes across the application. All schema modifications MUST be implemented through Laravel migration files.
</rule_activation>

### Rules

- **R-LMIG-001** MUST: Each migration file MUST implement both up() and down() methods to support forward migration and rollback operations.
- **R-LMIG-002** MUST: All table creation, modification, and deletion operations MUST be implemented through migration files.
- **R-LMIG-003** MUST: Column additions, modifications, and removals MUST be implemented through migration files.
- **R-LMIG-004** MUST: Index creation and removal MUST be implemented through migration files.
- **R-LMIG-005** MUST: Foreign key constraint definitions MUST be implemented through migration files.
- **R-LMIG-006** MUST: Database-level configuration changes affecting schema structure MUST be implemented through migration files.
- **R-LMIG-007** MUST: Migration files MUST follow Laravel's timestamp-based naming convention (YYYY_MM_DD_HHMMSS_description.php).
- **R-LMIG-008** SHOULD: Use Laravel's Schema Builder API for database abstraction to support multiple database engines.
- **R-LMIG-009** SHOULD: Use Laravel's migration methods like 'foreignId()', 'timestamps()', 'softDeletes()' for consistency with framework conventions.
- **R-LMIG-010** SHOULD: Document any database-specific SQL used in migrations with comments explaining compatibility implications.
- **R-LMIG-011** MAY: Application data seeding for testing purposes should use database/seeders instead of migrations.
- **R-LMIG-012** MAY: Data migration or transformation scripts that don't modify schema structure should be separated from schema migrations.

### Verify

```bash
# Count migration files in standard location
find database/migrations -name '*.php' -type f | wc -l | grep -E '^[0-9]+$'

# Verify Schema Builder API usage across migrations
grep -r 'Schema::create\|Schema::table\|Schema::drop' database/migrations/ | wc -l

# Check migration status
php artisan migrate:status 2>&1 | grep -E 'Ran|Pending'

# Verify all migrations have both up() and down() methods
ls database/migrations/*.php 2>/dev/null | head -5 | xargs grep -l 'function up()' | xargs grep -l 'function down()'
```

**Accept when:**
- All migration files exist in database/migrations directory and follow Laravel naming convention with timestamps
- Each migration file contains both up() and down() methods using Schema Builder API
- Migration status command executes successfully showing tracked migrations
- No direct SQL schema modifications are found in application code outside migration files
- All schema changes are implemented through migrations, not raw SQL scripts
