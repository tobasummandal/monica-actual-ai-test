<rule_activation id="6a12618a-f2c7-4302-a538-b872e72ba904" title="Adopt Domain-Driven Service Layer Architecture for Business Operations: Service Classes Encapsulate" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in the codebase to ensure proper domain-driven service layer architecture.
</rule_activation>

### Rules

- **R-DDS-001** SHOULD: Service classes SHOULD encapsulate a single business operation or use case to maintain single responsibility principle.
- **R-DDS-002** SHOULD: Create domain folders under app/Domains/ with subfolders for each feature area (e.g., CreateAccount, CancelAccount).
- **R-DDS-003** SHOULD: Place service classes in Services/ subdirectories within each domain feature (app/Domains/{Domain}/{Feature}/Services/).
- **R-DDS-004** SHOULD: Place controllers in Web/Controllers/ subdirectories within each domain feature (app/Domains/{Domain}/{Feature}/Web/Controllers/).
- **R-DDS-005** SHOULD: Use dependency injection to provide services to controllers, avoiding direct instantiation.
- **R-DDS-006** SHOULD: Name service classes after the business operation they perform (e.g., CreateAccount, AcceptInvitation).
- **R-DDS-007** SHOULD: Keep controllers thin by limiting them to request validation, service invocation, and response formatting.
- **R-DDS-008** SHOULD NOT: Implement business logic directly in controller methods.
- **R-DDS-009** SHOULD NOT: Place infrastructure-level services, third-party API integrations, utility classes, or framework middleware in domain service directories.

### In Scope

- All business logic for account management operations
- User invitation and acceptance workflows
- Domain-specific service classes handling core business rules
- Web controllers that serve as entry points for HTTP requests

### Out of Scope

- Infrastructure-level services (database, caching, queuing)
- Third-party API integrations that don't represent core business logic
- Utility classes and helpers that provide cross-cutting concerns
- Framework-level middleware and request handling

### Verify

```bash
# Count service classes in domain service directories
find app/Domains -type f -name '*.php' -path '*/Services/*' | wc -l

# Count namespace declarations matching domain service pattern
grep -r 'namespace.*Domains.*Services' app/Domains --include='*.php' | wc -l

# Count controllers in domain web controller directories
find app/Domains -type f -name '*Controller.php' -path '*/Web/Controllers/*' | wc -l
```

**Accept when:**

- Service classes exist in app/Domains/{Domain}/{Feature}/Services/ directories
- Controllers exist in app/Domains/{Domain}/{Feature}/Web/Controllers/ directories
- At least 3 domain service classes follow the established pattern (matching detected evidence)
- Controllers delegate to domain services rather than containing business logic
- Service classes are named after their business operations

<enforcement>
Claude Code MUST verify domain-driven service architecture compliance before completing tasks that create or modify service classes or controllers. Verification MUST NOT be skipped or deferred.

Violation handling:
- CI build fails if controllers contain business logic exceeding complexity thresholds
- Pull requests are blocked if service classes are not placed in correct domain directories
- Architecture review required for new domains or significant deviations from pattern

Exception process:
- Document exception rationale in ADR amendment or inline code comments
- Obtain approval from tech lead or architecture review board
- Add technical debt ticket if exception is temporary workaround
</enforcement>
