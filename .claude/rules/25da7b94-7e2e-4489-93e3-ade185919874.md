<rule_activation id="25da7b94-7e2e-4489-93e3-ade185919874" title="Adopt HTTP Client Libraries for External API Integration: External Http Communications" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in the project.

**Scope:**
- All outbound HTTP/HTTPS requests to external APIs and services
- OAuth provider integrations (Google, Facebook, GitHub, etc.)
- WebDAV, CalDAV, and CardDAV protocol communications
- Third-party REST API consumption (Wikipedia, documentation services, etc.)
- vCard and vCalendar data import/export operations

**Out of scope:**
- Internal service-to-service communication within the same application
- Database connections and queries
- File system operations
- Message queue or event bus communications
- WebSocket connections (unless using HTTP upgrade mechanism)

**Exceptions:**
- EXC-001: Legacy code maintenance where refactoring risk exceeds benefit
- EXC-002: Performance-critical scenarios where library overhead is demonstrably prohibitive (requires benchmarking)
</rule_activation>

### Rules

- **R-HTTP-001** MUST: All external HTTP API communications MUST use established HTTP client libraries (Socialite for OAuth, Sabre DAV/VObject for DAV/vCard/vCalendar) rather than raw socket or curl implementations.

- **R-HTTP-002** SHOULD: Wrap HTTP client library usage in service classes (e.g., WikipediaHelper, DavClient) to encapsulate external API logic and provide domain-specific interfaces.

- **R-HTTP-003** SHOULD: Configure HTTP clients with appropriate timeouts, retry policies, and error handling strategies based on the reliability requirements of each external service.

- **R-HTTP-004** SHOULD: Use dependency injection to provide HTTP client instances, enabling easy mocking in unit tests and configuration flexibility across environments.

- **R-HTTP-005** SHOULD: Document authentication patterns for each integration type (OAuth, Basic Auth, API keys) with examples in the codebase.

- **R-HTTP-006** SHOULD: Implement logging and monitoring for external API calls to track performance, errors, and usage patterns.

### Verify

```bash
# Check for Socialite library usage (OAuth integrations)
grep -r "use.*Socialite" app/ --include="*.php" | wc -l

# Check for Sabre DAV/VObject libraries (DAV protocol and vCard/vCalendar)
grep -r "use.*Sabre" app/ --include="*.php" | wc -l

# Check for raw cURL or socket implementations (should be minimal/none in new code)
grep -r "curl_exec\|fsockopen" app/ --include="*.php" | wc -l
```

**Accept when:**
- Socialite library usage is detected in OAuth authentication flows
- Sabre DAV/VObject libraries are used for DAV protocol and vCard/vCalendar operations
- No raw cURL or socket implementations are found in new external API integration code
- Service classes encapsulate HTTP client library usage with clear domain interfaces
- HTTP clients are configured with appropriate timeouts and error handling
- External API calls have logging and monitoring in place

<enforcement>
Claude Code MUST NOT skip or defer verification.

**Automated verification:**
- CI pipeline fails if raw HTTP implementations (curl_exec, fsockopen) are detected in new code without documented exceptions
- Dependency analysis ensures approved HTTP client libraries are present in composer.json
- Code review process flags non-compliant external API integrations for revision
- Unit test coverage requirements for service classes wrapping external API calls

**Exception process:**
1. Developer submits exception request with performance benchmarks or technical justification to Technical Lead
2. Technical Lead reviews request and approves/rejects with documented rationale
3. Approved exceptions are documented in code comments with issue tracking reference and future migration plan
4. Exception registry is maintained and reviewed quarterly to identify patterns requiring policy updates

**Violation handling:**
- Technical debt tickets created for legacy code that doesn't comply, prioritized based on risk assessment
</enforcement>
