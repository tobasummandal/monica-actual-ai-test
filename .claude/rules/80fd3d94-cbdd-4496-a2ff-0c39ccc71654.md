<rule_activation id="80fd3d94-cbdd-4496-a2ff-0c39ccc71654" title="Adopt Mock-Based Unit Testing for External Service Dependencies in CI/CD Pipeline: Teams Use Contract" applies_to="**/tests/Unit/**/*">
These rules are ALWAYS ACTIVE for unit tests that interact with external service dependencies (CardDAV/WebDAV services, HTTP clients, API wrappers, background workers, authentication providers).

**In scope:**
- Unit tests for HTTP clients, API wrappers, and service integrations
- Tests for jobs and background workers that call external services
- Tests for synchronization utilities that interact with remote data sources
- Tests for authentication and authorization flows involving external providers

**Out of scope:**
- Integration tests explicitly designed to verify real service connectivity
- End-to-end tests that validate full system behavior
- Smoke tests run against staging or production environments
- Performance tests that measure real network latency and throughput

**Exception:** EXC-001: Testing framework-level HTTP client configuration or connection pooling behavior that cannot be adequately simulated
</rule_activation>

### Rules

- **R-MOCK-001** MUST: Unit tests for external service dependencies MUST use test doubles (mocks, stubs, fakes) to simulate external service behavior instead of making real network calls to external services.

- **R-MOCK-002** MUST: Unit tests MUST NOT depend on real external services (CardDAV servers, WebDAV endpoints, authentication providers) that require network access, service availability, or authentication credentials.

- **R-MOCK-003** MAY: Teams MAY use contract testing or recorded fixtures to validate mock behavior against real service responses.

- **R-MOCK-004** SHOULD: Use the testing framework's native mocking capabilities (e.g., PHPUnit's createMock/getMockBuilder) for consistency.

- **R-MOCK-005** SHOULD: Create reusable mock factories or test helpers for commonly mocked external services to reduce duplication.

- **R-MOCK-006** SHOULD: Document expected external service behavior in test comments to help future maintainers understand mock setup.

- **R-MOCK-007** SHOULD: Organize tests into clear unit test and integration test directories with separate CI/CD execution stages.

### Verify

```bash
# Check for direct external service instantiation in unit tests (should return 0 or low count)
grep -r "new.*Client\|->connect\|->request" tests/Unit/ | grep -v "Mock\|Stub\|Fake" | wc -l

# Count unit tests using mock patterns (should match total unit test count)
find tests/Unit -name '*Test.php' -exec grep -l 'createMock\|getMockBuilder\|shouldReceive' {} \; | wc -l

# Verify no network-dependent tests in unit suite
phpunit --testsuite=unit --no-coverage --testdox | grep -i 'network\|connection\|timeout' || echo 'No network-dependent tests found'
```

**Accept when:**
- Unit tests execute successfully without network connectivity (verified by running tests with network disabled)
- Unit test suite completes in under 30 seconds for typical project size, indicating no real external service calls
- Grep verification shows that unit tests use mock/stub/fake patterns for external service dependencies
- CI/CD pipeline unit test stage has >95% success rate over 30-day period, indicating stable, non-flaky tests

<enforcement>
Claude Code MUST NOT skip or defer verification when modifying unit tests that interact with external services.

**Verification process:**
- Automated CI/CD pipeline checks that unit tests complete within time thresholds (e.g., <30s)
- Code review checklist includes verification that new unit tests use appropriate mocking for external dependencies
- Static analysis or linting rules detect direct instantiation of HTTP clients or external service classes in unit test files
- Periodic manual review of test suite structure and organization

**Violation handling:**
- CI/CD pipeline fails if unit tests exceed execution time threshold, indicating potential real service calls
- Code review blocks merge if unit tests contain direct external service calls without documented exception approval
- Tech lead review required for any unit test that requires network access or external credentials
- Quarterly test suite audit identifies and refactors tests that violate mocking standards

**Exception process:**
- Developer documents specific technical reason why mocking is insufficient in test file comments
- Tech lead reviews exception request and approves if justified (e.g., testing framework-level behavior per EXC-001)
- Exception is tracked in technical debt register with plan for future resolution if possible
- Exceptional tests are clearly marked and isolated to prevent pattern spread
</enforcement>
