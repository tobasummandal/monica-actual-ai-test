<rule_activation id="f860e50a-8705-4fae-80aa-464861bfa2e0" title="Enforce Public API Contract Testing in CI/CD Pipeline: Test Coverage Public" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files. Public API contract testing requirements must be enforced across service layers, API controllers, and ViewHelper contracts to prevent breaking changes from reaching production.

**In scope:**
- All public API endpoints exposed to external consumers or other services
- Service layer contracts that form domain boundaries
- API controllers handling HTTP requests and responses
- ViewHelper contracts that provide data transformation for presentation layers
- Any interface or contract marked as @api or explicitly documented as public

**Out of scope:**
- Internal private methods not exposed outside their containing class
- Implementation details that do not affect external contracts
- Database schema changes that do not impact API response structures
- UI-only changes that do not modify underlying API contracts
- Experimental or feature-flagged APIs not yet released to production

**Exceptions:**
- EXC-001: Emergency hotfixes addressing critical production incidents where contract changes are unavoidable
- EXC-002: Deprecated APIs scheduled for removal where breaking changes are intentional and communicated
</rule_activation>

### Rules

- **R-API-001** MUST: Test coverage for public API contracts MUST include all CRUD operations (Create, Read, Update, Delete) where applicable.
- **R-API-002** MUST: All public API endpoints must have corresponding unit tests with at least 80% code coverage.
- **R-API-003** MUST: Contract tests must validate behavior at service layers, API controllers, and ViewHelper interfaces.
- **R-API-004** MUST: New or modified public APIs must include contract tests before merge approval.
- **R-API-005** SHOULD: Contract test execution should complete within acceptable time limits (under 5 minutes for the full suite).

### Verify

```bash
# Count contract test files across Controllers, Services, and ViewHelpers
find tests/Unit -name '*ControllerTest.php' -o -name '*ServiceTest.php' -o -name '*ViewHelperTest.php' | wc -l

# Count individual test methods in Settings domain
grep -r 'public function test' tests/Unit/Domains/Settings/ | wc -l

# Check code coverage for public API controllers
phpunit --testsuite=unit --coverage-text --coverage-filter='app/Domains/*/Api/Controllers' | grep 'Lines:' | awk '{print $2}'
```

**Accept when:**
- All public API endpoints in relevant domains have corresponding unit tests with at least 80% code coverage
- CI/CD pipeline includes a dedicated stage for contract tests that must pass before merge approval
- Contract test execution completes within acceptable time limits (e.g., under 5 minutes for the full suite)
- Code review checklist includes verification that new or modified public APIs have corresponding contract tests
- Contract tests validate all CRUD operations where applicable
- Tests cover service layers, API controllers, and ViewHelper contracts comprehensively

<enforcement>
Claude Code MUST NOT skip or defer verification of public API contract testing requirements. All modifications to public API surfaces must include corresponding contract tests validated through CI/CD pipeline execution. Breaking changes must be caught before merge through automated testing.

**Verification methods:**
- Automated CI/CD pipeline execution on every pull request and commit to protected branches
- Code coverage analysis tools integrated into CI pipeline with minimum 80% threshold enforcement
- Mandatory code review process requiring reviewer verification of contract test presence and quality
- Static analysis tools to detect public API methods without corresponding test coverage

**Violation handling:**
- CI/CD pipeline fails and prevents merge if contract tests fail or coverage thresholds are not met
- Pull requests without contract tests for modified public APIs are automatically flagged for reviewer attention
- Quarterly audits identify public APIs lacking contract tests, with remediation tickets created and prioritized
- Metrics dashboard tracks contract test coverage trends, with alerts for declining coverage

**Exception process:**
- Developer submits exception request via documented process with justification
- Tech lead reviews and approves only for valid scenarios (EXC-001: emergency hotfix, EXC-002: deprecated API)
- Approved exceptions are time-limited (48-72 hours) with automatic follow-up ticket creation for remediation
- All exceptions are logged and reviewed in monthly architecture review meetings
</enforcement>
